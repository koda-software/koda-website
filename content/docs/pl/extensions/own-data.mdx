Ten przewodnik buduje paczkę **Zamówienia**, która przechowuje zamówienia we własnym obiekcie. Przynosi słownik **Priority**, obiekt **Order**, którego pole priorytetu z niego korzysta, oraz zapisane zapytanie **Orders by day** dla list i raportów organizacji. Jej krok **Synchronizuj zamówienie** (`x-orders-ext.sync_order`) pobiera pierwsze otwarte zamówienie, wysyła je do API przewoźnika i zapisuje status, który zwróci przewoźnik.

<Steps>
<Step>
### Napisz manifest [#write-the-manifest]

Zacznij od `opero-ext init orders-ext` albo od pustego folderu. Dla obiektów, słowników i zapytań nie ma polecenia `add`, więc ich foldery tworzysz ręcznie.

```yaml title="extension.yaml"
manifestVersion: 2
extension: orders-ext
version: 0.1.0
name: Orders
description: Keeps orders and sends the open ones to the carrier.
publisher: Your company
requires:
  modules: [rules, objects, queries]
permissions:
  network:
    - host: api.example.com
      reason: Sends each order to the carrier.
  data:
    - scope: records:read
      reason: Reads the open orders.
    - scope: records:write
      reason: Stores the status the carrier answers.

dictionaries:
  - dictionaries/priority
objects:
  - objects/orders
queries:
  - queries/orders-by-day
actions:
  - actions/sync-order

locales: [pl]
```

Krok odczytuje zamówienia i zmienia jedno z nich, więc paczka prosi dokładnie o te dwa [zakresy danych](/docs/pl/extensions/reference/data-permissions); zakres, z którego nic nie korzysta, jest odrzucany. Ponieważ paczka prosi o dostęp do danych, zainstalować ją może tylko właściciel organizacji.
</Step>

<Step>
### Dodaj słownik [#add-the-dictionary]

```yaml title="dictionaries/priority/dictionary.yaml"
dictionary: priority
name: Priority
entries:
  - { key: low, label: Low }
  - { key: high, label: High, color: "#DC2626" }
```

Zostaje zainstalowany jako `x-orders-ext-priority`. Zobacz [Słowniki](/docs/pl/extensions/reference/dictionaries).
</Step>

<Step>
### Dodaj obiekt [#add-the-object]

```yaml title="objects/orders/object.yaml"
object: orders
name: Order
namePlural: Orders
icon: package
fields:
  - { key: number, name: Number, type: TEXT }
  - { key: status, name: Status, type: TEXT }
  - { key: ordered_on, name: Ordered on, type: DATE }
  - key: priority
    name: Priority
    type: SELECT
    options: { dictionary: priority }
```

`options: { dictionary: priority }` wskazuje własny słownik paczki. Obiekt zostaje zainstalowany w module `x-orders-ext`, bez formularza. Zobacz [Obiekty](/docs/pl/extensions/reference/objects).
</Step>

<Step>
### Dodaj zapytanie [#add-the-query]

```yaml title="queries/orders-by-day/query.yaml"
query: orders_by_day
name: Orders by day
kind: FETCH
sql: query.sql
```

```sql title="queries/orders-by-day/query.sql"
SELECT f_ordered_on AS day, count(*) AS orders
FROM {{object.orders}}
GROUP BY f_ordered_on
```

`{{object.orders}}` oznacza tabelę obiektu `orders`, a `f_ordered_on` to jego pole `ordered_on`. Zapytanie zostaje zainstalowane jako `x_orders_ext_orders_by_day`. Zobacz [Zapytania](/docs/pl/extensions/reference/queries).
</Step>

<Step>
### Opisz akcję [#describe-the-action]

```yaml title="actions/sync-order/action.yaml"
action: sync_order
label: Sync order
description: Sends the first open order to the carrier and stores the status it answers.

input:
  status: { type: text, label: Status, required: true }

run: rule.yaml
tests: tests.yaml

expose:
  ruleStep: { category: data }
```
</Step>

<Step>
### Napisz regułę [#write-the-rule]

Reguła pobiera, wywołuje i aktualizuje:

```yaml title="actions/sync-order/rule.yaml"
entryStepId: fetch
steps:
  - id: fetch
    type: FETCH_RECORDS
    name: Open orders
    contextKey: orders
    config:
      moduleKey: x-orders-ext
      objectKey: orders
      filters:
        - { field: status, operator: eq, value: open }
      limit: 1
  - id: send
    type: CALL_WEBHOOK
    name: Send to the carrier
    contextKey: sent
    config:
      url: https://api.example.com/v1/orders
      method: POST
      body:
        number: "{{ orders.rows[0].number }}"
        status: "{{ trigger.data.status }}"
  - id: mark
    type: UPDATE_RECORD
    name: Mark the order
    contextKey: output
    config:
      target: "{{ orders.rows[0].id }}"
      targetModuleKey: x-orders-ext
      targetObjectKey: orders
      fieldUpdates: { status: "{{ sent.body.status }}" }
edges:
  - { fromStepId: fetch, toStepId: send }
  - { fromStepId: send, toStepId: mark }
```

Moduł i obiekt są wpisane wprost jako `x-orders-ext` i `orders`, bo szablon w tym miejscu jest odrzucany. `UPDATE_RECORD` wskazuje rekord po identyfikatorze pobranego wiersza. Zobacz [Kroki danych](/docs/pl/extensions/reference/data-steps).
</Step>

<Step>
### Przetestuj [#test-it]

Przypadek opisuje wymianę HTTP w `http`, a dwa kroki danych w `effects`. Każda z list jest dopasowywana we własnej kolejności.

```yaml title="actions/sync-order/tests.yaml"
- name: the open order gets the status the carrier answers
  input: { status: synced }
  http:
    - request:
        method: POST
        url: https://api.example.com/v1/orders
        body: { number: A-1, status: synced }
      response: { status: 200, body: { status: synced } }
  effects:
    - request: { step: FETCH_RECORDS, objectKey: orders }
      response:
        rows: [{ id: 7d1c2a34-0000-4000-8000-000000000001, number: A-1, status: open }]
        rowCount: 1
        truncated: false
    - request:
        step: UPDATE_RECORD
        targetObjectKey: orders
        fieldUpdates: { status: synced }
  succeeds: true
```

Efekt pobrania daje krokowi wiersz, który by odczytał. Efekt aktualizacji sprawdza obiekt i nowy status; nie ma `response`, bo `UPDATE_RECORD` niczego nie zwraca. Podczas testu żaden rekord nie jest odczytywany ani zapisywany. Zobacz [Testy](/docs/pl/extensions/reference/tests#data-and-messaging-steps).
</Step>

<Step>
### Przetłumacz [#translate-it]

```yaml title="locales/pl.yaml"
extension:
  name: Zamówienia
  description: Przechowuje zamówienia i wysyła otwarte do przewoźnika.
permissions:
  network:
    api.example.com: { reason: Wysyła każde zamówienie do przewoźnika. }
  data:
    records:read: { reason: Odczytuje otwarte zamówienia. }
    records:write: { reason: Zapisuje status zwrócony przez przewoźnika. }
actions:
  sync_order:
    label: Synchronizuj zamówienie
    description: Wysyła pierwsze otwarte zamówienie do przewoźnika i zapisuje zwrócony status.
    input: { status: { label: Status } }
dictionaries:
  priority:
    entries:
      low: { label: Niski }
      high: { label: Wysoki }
```

Etykiety pozycji słownika można tłumaczyć. Nazwy obiektu, jego pól, słownika i zapytania są tylko po angielsku.
</Step>

<Step>
### Zwaliduj, przetestuj i spakuj [#validate-test-and-pack]

```bash title="Terminal"
opero-ext validate .
opero-ext test . --server https://opero.example.com/mcp
opero-ext pack .
```

</Step>

## Po instalacji [#after-install]

Właściciel organizacji [instaluje](/docs/pl/extensions/install) plik zip; każdemu innemu przegląd mówi, że zainstalować go może tylko właściciel, z powodu [zakresów danych](/docs/pl/extensions/install#access-to-data). Nie ma połączenia do skonfigurowania. W sekcji **Co dodaje** strona rozszerzenia wymienia obiekt, słownik i zapytanie. Każde z nich otwiera się tylko do odczytu, a zapytanie pokazuje swój SQL z symbolem zastępczym zamienionym na zainstalowaną tabelę:

![Zainstalowane zapytanie Orders by day z jego SQL, tylko do odczytu i zarządzane przez rozszerzenie](/docs/_assets/extensions/own-data/query-overlay.webp)

Organizacja buduje na obiekcie własne formularze i listy, a zapytania używa w swoich listach SQL i raportach. Jej reguły dostają krok **Synchronizuj zamówienie**, zapisywany tak:

```json title="Krok w jednej z reguł organizacji"
{
  "type": "x-orders-ext.sync_order",
  "contextKey": "synced",
  "config": { "status": "sent" }
}
```

Niezależnie od tego, kto napisze tę regułę, krok odczytuje i zapisuje tylko rekordy `orders`, w firmie, dla której reguła działa.

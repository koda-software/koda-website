title: Dane z konta każdego członka
description: "Zbuduj rozszerzenie Opero, w którym każdy członek łączy własne konto w usłudze, a harmonogram przynosi do reguł nowe dane każdego członka."
---

Niektóre dane należą do ludzi, a nie do firm, na przykład aktywności każdego członka w usłudze sportowej albo podróżnej. Ten przewodnik buduje paczkę **Aktywności członków**. Organizacja raz wpisuje klienta OAuth usługi. Potem każdy członek łączy własne konto, a co godzinę harmonogram odczytuje nowe aktywności każdego połączonego członka jego tokenem i zgłasza wyzwalacz **Zsynchronizowana aktywność** (`x-member-activities.activity`).

Działa to jak [Zdarzenia z usługi](/docs/pl/extensions/scheduled-events), z trzema różnicami: połączeniem członka, wyzwalaczem, który wskazuje członka, i harmonogramem uruchamianym dla każdego połączonego członka.

<Steps>
<Step>
### Napisz manifest [#write-the-manifest]

```yaml title="extension.yaml"
manifestVersion: 2
extension: member-activities
version: 1.0.0
name: Member activities
description: Members connect their sandbox account; their new activities reach the company's rules every hour.
publisher: Your company
requires:
  modules: [rules]
permissions:
  network:
    - host: auth.example.com
      reason: Members sign in to the sandbox here.
    - host: api.example.com
      reason: Exchanges a member's sign-in for a token, registers members and reads their activities.

connection: connection

actions:
  - actions/verify-client
  - actions/register-member
  - actions/sync-member
triggers:
  - triggers/activity
schedules:
  - schedules/sync-members

locales: [pl]
```

Wymienione są oba hosty: na pierwszym członkowie się logują, a wymiana tokenu i API są na drugim.
</Step>

<Step>
### Dodaj połączenie z klientem OAuth [#add-the-connection-with-the-oauth-client]

Połączenie organizacji przechowuje klienta OAuth usługi. Jego akcja weryfikująca sprawdza klienta, wysyłając go jako HTTP Basic przez `auth: connection`.

```yaml title="connection/connection.yaml"
methods:
  - method: client
    kind: custom
    label: Sandbox API client
    fields:
      clientId: { type: text, label: Client ID, required: true, secret: false }
      clientSecret: { type: text, label: Client secret, required: true }
    scheme: { kind: basic, username: clientId, password: clientSecret }
verify: verify_client
member: member.yaml
```

```yaml title="actions/verify-client/action.yaml"
action: verify_client
label: Check the API client
run: rule.yaml
tests: tests.yaml
```

```yaml title="actions/verify-client/rule.yaml"
entryStepId: check
steps:
  - id: check
    type: CALL_WEBHOOK
    name: Check the client
    config:
      method: GET
      url: https://api.example.com/v1/client
      auth: connection
edges: []
```

```yaml title="actions/verify-client/tests.yaml"
- name: the client is sent as HTTP Basic
  connection: { clientId: client-1, clientSecret: secret-1 }
  http:
    - request:
        method: GET
        url: https://api.example.com/v1/client
        headers: { authorization: Basic Y2xpZW50LTE6c2VjcmV0LTE= }
      response: { status: 200 }
  succeeds: true
```

Zobacz [HTTP Basic z połączenia](/docs/pl/extensions/reference/connection-and-secrets#http-basic-from-the-connection).
</Step>

<Step>
### Opisz, jak łączą się członkowie [#describe-how-members-connect]

`member.yaml` to to, co członkowie widzą i na co się zgadzają: adresy i zakresy OAuth, formularz, który wypełniają, i dane, które trafiają do Opero.

```yaml title="connection/member.yaml"
label: Sandbox account
description: Sends your sandbox activities to your company's rules.
oauth:
  authorize: https://auth.example.com/oauth2/authorize
  token: https://api.example.com/oauth2/token
  scopes: [activities.read]
  client: { id: clientId, secret: clientSecret }
config:
  companyId: { type: company, label: Company receiving your data, required: true }
data:
  - Activities
afterConnect:
  action: register_member
  output:
    sandboxUserId: meta
```

`client` bierze klienta OAuth z pól połączenia. `config.companyId` pyta każdego członka, do której firmy mają trafiać jego dane. Gdy członek się zgodzi, `afterConnect` uruchamia `register_member` i zapisuje jej wynik `sandboxUserId` jako publiczną informację o połączeniu. Zobacz [member.yaml](/docs/pl/extensions/reference/member-connections#memberyaml).
</Step>

<Step>
### Zarejestruj członka [#register-the-member]

```yaml title="actions/register-member/action.yaml"
action: register_member
label: Register a member
input: input.yaml
output:
  sandboxUserId: { type: text, label: Sandbox user }
run: rule.yaml
tests: tests.yaml
```

```yaml title="actions/register-member/input.yaml"
type: object
properties:
  credentialId: { type: string }
  token: { type: object }
  config: { type: object }
required: [credentialId]
```

```yaml title="actions/register-member/rule.yaml"
entryStepId: register
steps:
  - id: register
    type: CALL_WEBHOOK
    name: Register
    contextKey: registered
    config:
      method: POST
      url: https://api.example.com/v1/users
      headers: { Authorization: "Bearer {{ userConnection.accessToken }}" }
      body: { memberId: "{{ trigger.data.credentialId }}" }
  - id: keep
    type: SAVE_TO_CONTEXT
    name: Keep the id
    contextKey: output
    config:
      value: { sandboxUserId: "{{ registered.body.id }}" }
edges:
  - { fromStepId: register, toStepId: keep }
```

```yaml title="actions/register-member/tests.yaml"
- name: a member is registered
  input: { credentialId: c_1, token: { scopes: [activities.read] }, config: { companyId: co_1 } }
  userConnection: { accessToken: test-token }
  http:
    - request:
        method: POST
        url: https://api.example.com/v1/users
        headers: { authorization: Bearer test-token }
        body: { memberId: c_1 }
      response: { status: 201, body: { id: "1234" } }
  returns: { sandboxUserId: "1234" }
```

`{{ userConnection.accessToken }}` to token członka, wstawiany tylko na czas wysłania żądania. Akcja, która go używa, jest akcją członka: działa tylko dla jednego członka i nigdy nie jest krokiem reguły. W teście ten token podaje `userConnection`. Zobacz [Łączenie: afterConnect](/docs/pl/extensions/reference/member-connections#connecting-afterconnect).
</Step>

<Step>
### Zadeklaruj wyzwalacz, który wskazuje członka [#declare-a-trigger-that-names-the-member]

```yaml title="triggers/activity/trigger.yaml"
trigger: activity
label: Activity synced
description: A member's activity is new or changed in the sandbox.
data:
  userId: { type: text, label: Member, required: true }
  id: { type: text, label: Activity, required: true }
  kind: { type: text, label: Kind, required: true }
  distanceMeters: { type: number, label: Distance in meters, nullable: true }
config:
  member: { type: text, label: Only this member, match: userId }
```

Dane niosą członka (`userId`), a filtr **Tylko ten członek** pozwala regule śledzić jedną osobę.
</Step>

<Step>
### Uruchamiaj harmonogram dla każdego członka [#run-the-schedule-for-each-member]

```yaml title="schedules/sync-members/schedule.yaml"
schedule: sync_members
label: Sync connected members
description: Reads each connected member's new activities every hour.
every: 1h
forEach: userConnection
action: sync_member
```

`forEach: userConnection` daje każdemu połączonemu członkowi osobne uruchomienie. `subject` uruchomienia niesie `meta` członka, a reguła wysyła token tego członka:

```yaml title="actions/sync-member/action.yaml"
action: sync_member
label: Sync one member
input: input.yaml
run: rule.yaml
tests: tests.yaml
```

```yaml title="actions/sync-member/input.yaml"
type: object
properties:
  subject: { type: object }
  lastSucceededAt: { type: [string, "null"] }
  firstRun: { type: boolean }
required: [subject, firstRun]
```

```yaml title="actions/sync-member/rule.yaml"
entryStepId: fetch
steps:
  - id: fetch
    type: CALL_WEBHOOK
    name: New activities
    contextKey: activities
    config:
      method: GET
      url: "https://api.example.com/v1/activities?user={{ trigger.data.subject.meta.sandboxUserId }}"
      headers: { Authorization: "Bearer {{ userConnection.accessToken }}" }
  - id: emit
    type: EMIT_EVENT
    name: Raise activity events
    config:
      event: activity
      items: "{{ activities.body.items }}"
      key: id
      dedupe: true
edges:
  - { fromStepId: fetch, toStepId: emit }
```

Zdarzenia każdego członka trafiają do wybranej przez niego firmy, a deduplikacja pamięta aktywności każdego członka osobno. Zobacz [Harmonogramy](/docs/pl/extensions/reference/schedules).
</Step>

<Step>
### Testuj z wartościami członka [#test-with-the-members-values]

```yaml title="actions/sync-member/tests.yaml"
- name: a new activity raises an event
  input:
    subject: { kind: userConnection, userId: u_1, credentialId: c_1, companyId: co_1, config: { companyId: co_1 }, meta: { sandboxUserId: "1234" } }
    lastSucceededAt: null
    firstRun: true
  userConnection: { accessToken: test-token }
  http:
    - request:
        method: GET
        url: https://api.example.com/v1/activities?user=1234
        headers: { authorization: Bearer test-token }
      response:
        status: 200
        body: { items: [{ userId: u_1, id: a-1, kind: run, distanceMeters: 5200 }] }
  events:
    - event: activity
      key: a-1
      data: { userId: u_1, id: a-1, kind: run, distanceMeters: 5200 }
  succeeds: true

- name: a revoked token
  input:
    subject: { kind: userConnection, userId: u_1, credentialId: c_1, companyId: co_1, config: { companyId: co_1 }, meta: { sandboxUserId: "1234" } }
    lastSucceededAt: "2026-11-02T10:00:00Z"
    firstRun: false
  userConnection: { accessToken: revoked-token }
  http:
    - request:
        method: GET
        url: https://api.example.com/v1/activities?user=1234
        headers: { authorization: Bearer revoked-token }
      response: { status: 401 }
  credentialRevoked: true
```

Drugi przypadek pokazuje usługę, która odrzuca token członka. W prawdziwym uruchomieniu nic więcej nie działa dla tego członka, dopóki nie połączy się ponownie. Zobacz [Odrzucony token](/docs/pl/extensions/reference/member-connections#a-refused-token).
</Step>

<Step>
### Przetłumacz [#translate-it]

```yaml title="locales/pl.yaml"
extension:
  name: Aktywności członków
  description: Członkowie łączą swoje konto w sandboksie, a ich nowe aktywności co godzinę trafiają do reguł firmy.
permissions:
  network:
    auth.example.com: { reason: Tutaj członkowie logują się do sandboksa. }
    api.example.com: { reason: "Wymienia logowanie członka na token, rejestruje członków i odczytuje ich aktywności." }
member:
  label: Konto sandboksa
  description: Wysyła Twoje aktywności z sandboksa do reguł Twojej firmy.
  data:
    "0": Aktywności
  config:
    companyId: { label: Firma otrzymująca Twoje dane }
triggers:
  activity:
    label: Zsynchronizowana aktywność
    description: Aktywność członka jest nowa albo zmieniła się w sandboksie.
    data:
      userId: { label: Członek }
      id: { label: Aktywność }
      kind: { label: Rodzaj }
      distanceMeters: { label: Dystans w metrach }
    config:
      member: { label: Tylko ten członek }
schedules:
  sync_members:
    label: Synchronizacja połączonych członków
    description: Co godzinę odczytuje nowe aktywności każdego połączonego członka.
```
</Step>

## Co robią członkowie [#what-members-do]

Dopóki rozszerzenie działa, każdy członek znajduje **Konto sandboksa** w sekcji **Połączone aplikacje** ustawień swojego konta. Członek klika **Połącz**, loguje się w usłudze i wybiera firmę, która otrzyma jego dane. Po otwarciu połączenia widzi **Data połączenia**, **Ostatnio zsynchronizowano** i **Co trafia do Opero**, a **Odłącz** usuwa połączenie. Połączenie, które przestało działać, jest w sekcji **Wymagają uwagi**, z przyciskiem **Połącz konto ponownie**.

Administrator śledzi członków na karcie **Aktywność** rozszerzenia, w sekcji **Połączeni członkowie**: zobacz [Połączeni członkowie](/docs/pl/extensions/after-install#connected-members).

Obiekt to tabela rekordów, którą rozszerzenie przynosi ze sobą, na przykład zamówienia albo przesyłki. Przy instalacji paczki Opero tworzy prawdziwą tabelę dla każdego obiektu, w jednym module nazwanym od rozszerzenia: `x-<key>`. Organizacja pracuje potem z rekordami jak z każdym innym obiektem, a własne reguły paczki mogą je odczytywać i zapisywać [krokami danych](/docs/pl/extensions/reference/data-steps).

```yaml title="objects/orders/object.yaml"
object: orders
name: Order
namePlural: Orders
icon: package
fields:
  - { key: number, name: Number, type: TEXT, isIndexed: true }
  - key: status
    name: Status
    type: SELECT
    options: { dictionary: status }
  - { key: ordered_on, name: Ordered on, type: DATE }
  - key: last_note
    name: Last note
    type: REFERENCE
    options: { toObject: order-notes }
```

Każdy obiekt ma własny folder w `objects/`, wymieniony w `extension.yaml`. Paczka z obiektami wymienia moduł `objects` w `requires.modules`:

```yaml title="extension.yaml"
requires:
  modules: [rules, objects]
objects:
  - objects/orders
  - objects/order-notes
```

## Odwołania wewnątrz paczki [#references-inside-the-package]

Pole może wskazywać słownik albo inny obiekt, ale tylko z tej samej paczki. Wpisz nazwę celu, nie id:

| Opcja | W polu typu | Wskazuje |
| --- | --- | --- |
| `dictionary: <name>` | `SELECT`, `MULTI_SELECT` | [Słownik](/docs/pl/extensions/reference/dictionaries) paczki, po nazwie z jego `dictionary.yaml`. |
| `toObject: <object>` | `REFERENCE`, `SUBORDINATE_OBJECT_REFERENCE` | Obiekt paczki, po jego kluczu `object`. Dwa obiekty mogą wskazywać na siebie nawzajem, a obiekt na samego siebie. |

```yaml title="objects/order-notes/object.yaml"
object: order-notes
name: Order note
namePlural: Order notes
fields:
  - { key: text, name: Text, type: TEXT }
  - key: order
    name: Order
    type: REFERENCE
    options: { toObject: orders }
```

Przy instalacji paczki Opero zamienia te nazwy na id zainstalowanych zasobów. Pole nie może zawierać `dictionaryId`, `toObjectId`, `toObjectClientId`, `toModuleKey` ani `toObjectKey`: paczka nie może wskazywać własnych słowników ani obiektów organizacji.

## Obiekt nie przychodzi z formularzem [#no-form-comes-with-an-object]

Instalacja obiektu tworzy tylko jego tabelę i pola. Nie powstaje dla niego żaden formularz, lista, strona ani pozycja menu, a `createDefaultForm` w `object.yaml` jest odrzucane.

Żeby obiekt miał swoje ekrany, dostarcz je w paczce: [formularze, listy i strony](/docs/pl/extensions/reference/screens). Organizacja może też zbudować na obiekcie własne formularze, listy własne i strony, jak na każdym innym obiekcie.

## Gdzie widzi je administrator [#where-the-administrator-sees-them]

- **Plan instalacji.** W sekcji **Co się zmieni** moduł i każdy obiekt są wymienione razem z tym, co zrobi z nimi instalacja (**Zostanie utworzone**, **Zostanie zmienione** i tak dalej).
- **Strona rozszerzenia.** Karta **Zainstalowane dane** wymienia w sekcji **Zainstalowane obiekty** każdy obiekt tylko do odczytu, z kluczem, liczbą rekordów i tabelą pól (klucz, nazwa, typ). Nazwa obiektu prowadzi do jego strony.
- **Ekran Moduły własne.** Moduł rozszerzenia jest pominięty na liście zarządzania **Moduły własne**.
- **Własna strona obiektu**, otwarta z odnośnika, zaczyna się od „Tylko do odczytu: zarządza tym rozszerzenie `<key>`.” i odnośnika **Otwórz rozszerzenie**. Jego pola są tabelą tylko do odczytu, a **Usuń obiekt** nie jest dostępne; formularze, udostępnienie firmom i dostęp do rekordów można nadal zmieniać. Strona modułu nie oferuje **Edytuj**, **Szkice**, **Usuń** ani nowych obiektów.
- **Wszędzie, gdzie wybiera się obiekt.** Reguły, źródła list własnych, raporty, formularze i pola referencji oferują te obiekty jak każde inne.

Budowa obiektu należy do rozszerzenia: jego pól nie da się dodać, zmienić ani usunąć, a obiektu i modułu nie da się usunąć, chyba że przez aktualizację albo odinstalowanie. Cała reszta należy do organizacji: rekordy, to, które firmy widzą obiekt, kto widzi wszystkie rekordy, zbudowane na nim formularze, dostęp z portalu i profil zewnętrznego API.

Organizacja nie może utworzyć modułu, którego klucz zaczyna się od `x-`, więc moduł `x-<key>` może należeć tylko do tego rozszerzenia.

## Aktualizacje i odinstalowanie [#upgrades-and-uninstalling]

| Nowa wersja | Co się dzieje |
| --- | --- |
| Dodaje obiekt albo pole | Zostaje utworzone. |
| Usuwa pole albo obiekt | Plan wymienia, co zostanie utracone, z liczbą rekordów. Administrator musi to potwierdzić, zanim aktualizacja się wykona. |
| Zmienia pole tak, że jego zapisane wartości trzeba wyczyścić | Wymienione i potwierdzane w ten sam sposób. |

Odinstalowanie domyślnie zachowuje moduł, obiekty i ich rekordy; stają się one własnymi zasobami organizacji. Ponowna instalacja rozszerzenia je przejmuje. Administrator może też zdecydować, że zostaną usunięte razem z rozszerzeniem. Zobacz [Po instalacji](/docs/pl/extensions/after-install#data).

## Problemy [#problems]

| Kod | Co jest nie tak |
| --- | --- |
| `object.invalid` | Nieznany klucz, klucz albo pole o złej postaci, `createDefaultForm`, opcja wskazująca id albo inny moduł, `dictionary` w polu, które nie jest polem wyboru, `toObject` w polu, które nie jest referencją, albo więcej niż 50 obiektów. |
| `object.unknown_reference` | `dictionary` albo `toObject` nie wskazuje niczego w paczce. |
| `name.duplicate` | Dwa obiekty o tym samym kluczu `object`. |
| `requires.module_undeclared` | Paczka ma obiekty, ale w `requires.modules` brakuje `objects`. |
| `object.save_validation` | W planie instalacji: obiektu albo pola nie da się zapisać, np. przez nieznany typ pola albo złe opcje. Blokuje instalację. |
| `object.adopts_existing` | W planie instalacji: przejmowany jest obiekt zachowany przy wcześniejszym odinstalowaniu. Ostrzeżenie. |

Skrypt to moduł JavaScript albo TypeScript z dokładnie jedną funkcją `export default`, bez `import` i bez innych eksportów. Działa samodzielnie w piaskownicy, bez dostępu do sieci i bazy danych. Skryptów używają akcje, kroki plików reguł, filtry szablonów i bloki; na skrypcie opiera się [Krok, który tylko liczy](/docs/pl/extensions/calculating-step).

<Tabs items={['JavaScript', 'TypeScript']}>
<Tab value="JavaScript">

```js title="actions/lookup/run.js"
/** @type {import('../../.opero/types').Action<'lookup'>} */
const run = async ({ input, settings, user }) => {
  const email = input.email.trim().toLowerCase();
  return {
    email,
    language: settings.language ?? 'en',
    requestedBy: user.email,
  };
};
export default run;
```

</Tab>
<Tab value="TypeScript">

```ts title="actions/lookup/run.ts"
import type { Action } from '../../.opero/types';

const run: Action<'lookup'> = async ({ input, settings, user }) => {
  const email = input.email.trim().toLowerCase();
  return {
    email,
    language: settings.language ?? 'en',
    requestedBy: user.email,
  };
};
export default run;
```

</Tab>
</Tabs>

Napisz `export default function name(…)` albo stałą, a po niej `export default name;`, tak jak robi to szkielet.

## Rodzaje skryptów [#kinds-of-script]

| Skrypt | Wskazuje go | Dostaje | Zwraca |
| --- | --- | --- | --- |
| Skrypt akcji | `run: run.js` w `action.yaml` | Argument opisany niżej | Wynik akcji. Może być `async`. |
| Skrypt kroku | `code: { $file: step.js }` w pliku reguły | Argument opisany niżej | Wynik kroku, pod jego `contextKey`. Może być `async`. |
| Skrypt filtra | `script` w `filter.yaml` | `(value, args, context)` | Przefiltrowaną wartość, od razu: nie `async`. Zobacz [Filtry szablonów](/docs/pl/extensions/reference/filters#the-function). |
| Skrypt bloku | `script` w `block.yaml` | `ctx`, w przeglądarce oglądającego. Zobacz [Bloki](/docs/pl/extensions/reference/blocks#the-script). | Nic albo funkcję, która sprząta przed kolejnym uruchomieniem bloku. |

## Argument [#the-argument]

Skrypt akcji i skrypt kroku dostają jeden obiekt:

<Callout title="Brak pomocników danych w paczce">
Skrypt paczki nie może odczytywać ani zapisywać rekordów, uruchamiać zapytań ani wysyłać powiadomień: nie dostaje pomocników danych. To, czego potrzebuje, pobierz najpierw [krokiem danych](/docs/pl/extensions/reference/data-steps) i odczytaj z `context`; jego wynik zapisz kolejnym krokiem.
</Callout>

## Błędy [#errors]

Rzucenie błędu powoduje błąd akcji, a więc i kroku, który ją wywołał:

```js
if (!Number.isFinite(price)) {
  throw new Error('The price is not a number.');
}
```

Problem wykryty przy odczycie paczki jest zgłaszany w swoim wierszu twojego skryptu: Opero zostawia każdy wiersz tam, gdzie go napisałeś.

<Callout type="warn">
Gdy skrypt rzuci błąd w trakcie działania, krok zgłasza „Script execution failed” bez numeru wiersza. Pokryj ścieżki błędów [testami](/docs/pl/extensions/reference/tests).
</Callout>

## Generowane typy [#generated-types]

`opero-ext types` zapisuje `.opero/types/index.d.ts` na podstawie deskryptorów. Zapisują go też `init` i `add`, a `validate` i `pack` odświeżają go, gdy paczka jest poprawna i ma już folder `.opero/`.

| Typ | Dla |
| --- | --- |
| `Action<'name'>` | Skryptu akcji. |
| `StepScript<'name'>` | Skryptu kroku w pliku reguły tej akcji. |
| `Filter` | Skryptu filtra. |
| `Block` | Skryptu [bloku](/docs/pl/extensions/reference/blocks#the-script), funkcji od `ctx`. Tylko w paczce z blokami. |
| `Settings` | Ustawień rozszerzenia z `settings.yaml`. Pole z wartością domyślną nie jest opcjonalne. |
| `ScriptArgument<'name'>` | Argumentu skryptów akcji. |
| `Triggers` | Danych zdarzeń każdego wyzwalacza. |

W JavaScripcie użyj typu przez linię JSDoc, którą zapisuje szkielet, i sprawdź skrypty poleceniem:

```bash title="Terminal"
npx tsc -p jsconfig.json
```

Pole z [pliku schematu](/docs/pl/extensions/reference/actions#schema-files) nie ma typu.

## TypeScript [#typescript]

Deskryptor może wskazywać plik `.ts`. `opero-ext` usuwa typy i pakuje obok niego plik `.js` z tymi samymi wierszami.

Akceptowany jest tylko TypeScript, który staje się JavaScriptem po usunięciu typów:

- bez `enum`, `namespace`, właściwości parametrów i rzutowań `<T>`;
- wiersze `import type` są usuwane razem z typami; każdy inny `import` jest odrzucany;
- plik `.js` trzymany obok `.ts` nie jest używany.

Problem z modułem, np. brak domyślnego eksportu, jest zgłaszany w pliku `.js` zbudowanym przez narzędzie. To, co odrzuca usuwanie typów, jest zgłaszane w pliku `.ts`.

<Callout type="warn" title="Kontrola modułu czyta wiersze">
Wiersz wewnątrz literału szablonowego albo komentarza blokowego, który zaczyna się od `export` lub `import` w pierwszej kolumnie, jest odczytywany jako instrukcja modułu i odrzucany. Dodaj wcięcie do takich wierszy.
</Callout>

## Problemy [#problems]

| Kod | Przyczyna | Rozwiązanie |
| --- | --- | --- |
| `script.invalid` | Żaden wiersz albo więcej niż jeden zaczyna się od `export default`, wiersz importuje lub eksportuje coś innego, plik jest pusty, domyślny eksport filtra jest `async` albo TypeScript nie daje się oczyścić z typów. | Zostaw jedną funkcję `export default` i żadnego innego `import` ani `export`. |
| `script.not_built` | Plik zip wskazuje skrypt `.ts` bez pliku `.js` obok niego. | Spakuj poleceniem `opero-ext pack`. |
| `script.missing_file` | Skrypt `$file`, którego nie ma w paczce. | Dodaj plik albo popraw nazwę. |
| `script.invalid_path` | Wartość `$file`, która nie jest plikiem `.js` ani `.ts` w folderze akcji. | Wskaż plik skryptu w tym folderze, względem niego. |
| `manifest.missing_file` | `run` albo `script` filtra wskazuje plik `.js`, którego nie ma w paczce. | Dodaj plik albo popraw nazwę. |

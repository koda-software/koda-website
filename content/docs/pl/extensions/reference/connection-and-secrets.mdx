Połączenie przechowuje dane uwierzytelniające zewnętrznej usługi. Administrator wypełnia je po instalacji, klika **Zweryfikuj** i je włącza. Do tego czasu rozszerzenie nie działa.

```yaml title="connection/connection.yaml"
methods:
  - method: token
    kind: api_token
    label: API token
    fields:
      token: { type: text, label: API token, required: true, hint: true }
verify: verify
```

`extension.yaml` wskazuje folder przez `connection: connection` i wymienia co najmniej jeden host w `permissions.network`.

Wartości, które nie są sekretne, np. język albo numer konta, nie należą do połączenia: to [ustawienia](/docs/pl/extensions/reference/settings) w `settings.yaml`. Klucz `settings` w `connection.yaml` jest odrzucany z kodem `connection.invalid`.

Każde pole metody jest sekretne, chyba że ma `secret: false`. `hint: true` pozwala Opero pokazać ostatnie cztery znaki zapisanej wartości, żeby administrator wiedział, która jest zapisana; bez tego wartość widać tylko jako `***`.

## Dane uwierzytelniające organizacji lub firmy

`scopes` decyduje, czy jest jeden zestaw danych uwierzytelniających dla całej organizacji, czy osobny dla każdej firmy.

| `supported` | `active` | Wynik |
| --- | --- | --- |
| `[organization]` | `organization` | Jedne dane uwierzytelniające dla wszystkich firm. Domyślnie. |
| `[company]` | `company` | Osobne dane uwierzytelniające dla każdej firmy. |
| `[organization, company]` | `selectable` | Wybiera administrator. |

```yaml title="connection/connection.yaml"
scopes:
  supported: [organization, company]
  active: selectable
```

Przy danych uwierzytelniających firmy krok używa danych firmy, dla której działa wywołująca reguła. Testy takiej paczki podają `companyId`.

## Weryfikacja

`verify` wskazuje zwykłą akcję, zwykle taką, której nic nie udostępnia. Gdy administrator kliknie **Zweryfikuj**, Opero uruchamia ją z zapisanymi danymi uwierzytelniającymi i ustawieniami rozszerzenia. Jeśli się nie powiedzie, połączenia nie da się włączyć.

Napisz ją jako tanie wywołanie tylko do odczytu, które dowodzi, że dane uwierzytelniające działają, np. pobranie bieżącego konta:

```yaml title="actions/verify/rule.yaml"
entryStepId: call
steps:
  - id: call
    type: CALL_WEBHOOK
    name: Check token
    contextKey: output
    config:
      url: https://api.example.com/v1/me
      method: GET
      headers: { Authorization: "Bearer {{ connection.token }}" }
edges: []
```

Jeśli nowa wersja zmienia pola danych uwierzytelniających, po aktualizacji połączenie jest wyłączone, dopóki znów nie przejdzie weryfikacji. Zmiany ustawień nigdy tego nie powodują.

## Sekrety [#secrets]

Wpisz sekret jako `{{ connection.<field> }}`, sam w nawiasach klamrowych, w wartości nagłówka albo wartości parametru zapytania w URL kroku **Wywołaj webhook**.

| Przykład | Akceptowane |
| --- | --- |
| `Authorization: "Bearer {{ connection.token }}"` | Tak |
| `url: "https://api.example.com/v1/items?key={{ connection.token }}"` | Tak |
| `X-Key: "{{ connection.token \| upcase }}"` | Nie: użyto filtra |
| `body: { key: "{{ connection.token }}" }` | Tylko z `secretsInBody: true` |
| W skrypcie, warunku, logu albo przekształceniu | Nie |
| `{{ connection.other }}` dla pola, którego nie deklaruje żadna metoda | Nie |

<Callout type="success" title="Co gwarantuje Opero">
- Prawdziwa wartość jest wstawiana dopiero przy wysyłaniu żądania, więc nigdy nie pojawia się w logu, historii uruchomień ani w skrypcie.
- Sekret jest wysyłany tylko do hostów z `permissions.network` i tylko wtedy, gdy działa twoja własna akcja.
- Reguła napisana przez organizację nie może odwołać się do twojego połączenia, a ręczne uruchomienie jednej z twoich zainstalowanych reguł nigdy nie wysyła sekretu.
- Komunikat błędu nigdy nie cytuje tego, co odesłała usługa, bo treść błędu mogłaby powtórzyć sekret.
</Callout>

Ustawienia nie są sekretne i nic z tego ich nie dotyczy. Odczytuj je jako `{{ trigger.settings.<field> }}` w pliku reguły i jako `settings` w skrypcie; zobacz [Ustawienia](/docs/pl/extensions/reference/settings#reading-settings).

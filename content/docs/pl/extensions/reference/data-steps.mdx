---
title: Kroki danych
description: Napisz kroki, które czytają i zapisują rekordy paczki, uruchamiają jej zapytania, wysyłają e-maile i powiadomienia oraz generują dokumenty.
---

Kroki danych to kroki reguł, które dotykają danych Opero albo coś wysyłają. Plik reguły twojej paczki może użyć takiego kroku, gdy paczka deklaruje [zakres danych](/docs/pl/extensions/reference/data-permissions), którego on potrzebuje. Każdy krok poniżej ma swoje klucze i efekt, który planuje dla niego [przypadek testowy](/docs/pl/extensions/reference/tests#data-and-messaging-steps). Kroków rekordów używa przewodnik [Paczka z własnymi danymi](/docs/pl/extensions/own-data).

| Krok | Zakres | Wynik pod jego `contextKey` |
| --- | --- | --- |
| [`FETCH_RECORDS`](#fetch-records) | `records:read` | `{ rows, rowCount, truncated }` |
| [`CREATE_RECORD`](#create-a-record) | `records:write` | `{ id }` |
| [`UPDATE_RECORD`](#update-a-record) | `records:write` | Brak |
| [`RUN_QUERY`](#run-a-query) | `queries:run` albo `queries:mutate` | Wiersze albo `{ operation, rowCount, rows }` |
| [`UPDATE_CONTRACTOR`](#update-a-contractor) | `contractors:write` | Brak |
| [`GENERATE_DOCUMENT`](#generate-a-document) | `documents:generate` | `{ fileId, … }` |
| [`SEND_EMAIL`](#send-an-email) | `email:send` | Brak |
| [`SEND_NOTIFICATION`](#send-a-notification) | `notifications:send` | `{ notificationId, … }` |

## Zasady dla każdego kroku danych [#rules-for-every-data-step]

- Krok działa w firmie, dla której działa reguła organizacji używająca twojego kroku. Uruchomienie bez firmy kończy się błędem na tym kroku.
- Każdy klucz modułu, obiektu i zapytania jest wpisany wprost. Szablon w jego miejscu jest odrzucany.
- Przykłady poniżej należą do paczki o kluczu `shop-ext`, więc jej moduł to `x-shop-ext`.

## Pobranie rekordów [#fetch-records]

`FETCH_RECORDS` odczytuje rekordy jednego obiektu paczki.

```yaml title="actions/note-order/rule.yaml (part)"
  - id: fetch
    type: FETCH_RECORDS
    name: First open order
    contextKey: orders
    config:
      moduleKey: x-shop-ext
      objectKey: orders
      filters:
        - { field: status, operator: eq, value: open }
      sortBy: ordered_on
      sortDirection: asc
      limit: 1
```

| Klucz | Wymagany | Znaczenie |
| --- | --- | --- |
| `moduleKey` | Tak | Zawsze `x-<key>`. |
| `objectKey` | Tak | Obiekt paczki. |
| `limit` | Tak | Od 1 do 100. |
| `filters` | Nie | Do 20 warunków `{ field, operator, value }`, które wszystkie muszą być spełnione. `operator` to jeden z: `eq`, `neq`, `contains`, `startsWith`, `endsWith`, `in`, `notIn`, `gt`, `gte`, `lt`, `lte`, `between`, `isNull`, `isNotNull`, `isEmpty`, `isNotEmpty`, `hasAny`, `hasAll`, `hasNone`, `near`. |
| `sortBy`, `sortDirection` | Nie | Klucz pola oraz `asc` (domyślnie) albo `desc`. |

Każdy wiersz ma `id` rekordu i jego pola według klucza, więc późniejszy krok odczytuje `{{ orders.rows[0].id }}`. `truncated` ma wartość true, gdy pasowało więcej rekordów niż `limit`. W teście efektem jest `{ step: FETCH_RECORDS, objectKey: orders }` z wierszami jako `response`.

## Utworzenie rekordu [#create-a-record]

`CREATE_RECORD` dodaje jeden rekord do obiektu paczki.

```yaml title="actions/note-order/rule.yaml (part)"
  - id: note
    type: CREATE_RECORD
    name: Add the note
    contextKey: note
    config:
      targetModuleKey: x-shop-ext
      targetObjectKey: order-notes
      fieldMapping:
        text: "{{ trigger.data.text }}"
        order: "{{ orders.rows[0].id }}"
```

| Klucz | Wymagany | Znaczenie |
| --- | --- | --- |
| `targetModuleKey` | Tak | Zawsze `x-<key>`. |
| `targetObjectKey` | Tak | Obiekt paczki. |
| `fieldMapping` | Tak | Klucze pól i ich wartości. Pole odwołania przyjmuje identyfikator rekordu, na który wskazuje. |

Wynikiem jest `{ id }`, identyfikator nowego rekordu. W teście `response` efektu to `{ id: … }`.

## Aktualizacja rekordu [#update-a-record]

`UPDATE_RECORD` zmienia jeden rekord obiektów paczki, wskazany identyfikatorem.

```yaml title="actions/note-order/rule.yaml (part)"
  - id: mark
    type: UPDATE_RECORD
    name: Mark the order
    contextKey: output
    config:
      target: "{{ orders.rows[0].id }}"
      targetModuleKey: x-shop-ext
      targetObjectKey: orders
      fieldUpdates:
        status: noted
        last_note: "{{ note.id }}"
```

| Klucz | Wymagany | Znaczenie |
| --- | --- | --- |
| `target` | Tak | Identyfikator rekordu. `target: self` jest odrzucane, bo krok paczki nie ma rekordu wyzwalającego. |
| `targetModuleKey` | Tak | Zawsze `x-<key>`. |
| `targetObjectKey` | Tak | Obiekt paczki. |
| `fieldUpdates` | Tak | Klucze pól i ich nowe wartości. |

Krok nie ma wyniku, więc jego efekt w teście nie ma `response`. Trzy kroki rekordów powyżej, zaplanowane po kolei:

```yaml title="actions/note-order/tests.yaml"
- name: the note is added and the order marked
  input: { text: Call back on Monday }
  effects:
    - request: { step: FETCH_RECORDS, objectKey: orders }
      response:
        rows: [{ id: 7d1c2a34-0000-4000-8000-000000000001, number: A-1, status: open }]
        rowCount: 1
        truncated: false
    - request:
        step: CREATE_RECORD
        targetObjectKey: order-notes
        fieldMapping: { text: Call back on Monday, order: 7d1c2a34-0000-4000-8000-000000000001 }
      response: { id: 9b0e1f22-0000-4000-8000-000000000002 }
    - request:
        step: UPDATE_RECORD
        targetObjectKey: orders
        fieldUpdates: { status: noted, last_note: 9b0e1f22-0000-4000-8000-000000000002 }
  succeeds: true
```

## Uruchomienie zapytania [#run-a-query]

`RUN_QUERY` uruchamia jedno z [zapytań](/docs/pl/extensions/reference/queries) paczki według klucza po instalacji. Zapytanie FETCH potrzebuje `queries:run`, zapytanie MUTATION `queries:mutate`.

```yaml title="actions/count-open/rule.yaml"
entryStepId: close
steps:
  - id: close
    type: RUN_QUERY
    name: Close old orders
    contextKey: closed
    config:
      queryKey: x_shop_ext_close_old_orders
      params: { before: "{{ trigger.data.before }}" }
  - id: count
    type: RUN_QUERY
    name: Count open orders
    contextKey: output
    config:
      queryKey: x_shop_ext_open_orders
edges:
  - { fromStepId: close, toStepId: count }
```

| Klucz | Wymagany | Znaczenie |
| --- | --- | --- |
| `queryKey` | Tak | `x_<key z _>_<name>`, klucz zapytania paczki po instalacji. `queryId` jest odrzucane. |
| `params` | Nie | Parametry zapytania według nazwy. Ich wartości mogą używać szablonów. |

Wynikiem zapytania FETCH jest lista wierszy, tu `[{ open: 3 }]`. Wynikiem zapytania MUTATION jest `{ operation, rowCount, rows }`. Akcja, która deklaruje pola wyjścia, zwraca obiekt, więc wybierz wartości krokiem `SAVE_TO_CONTEXT` pod `output`, zamiast zwracać wiersze.

```yaml title="actions/count-open/tests.yaml"
- name: the old orders are closed and the open ones counted
  input: { before: "2025-11-01" }
  effects:
    - request:
        step: RUN_QUERY
        queryKey: x_shop_ext_close_old_orders
        params: { before: "2025-11-01" }
      response: { operation: UPDATE, rowCount: 2, rows: [] }
    - request: { step: RUN_QUERY, queryKey: x_shop_ext_open_orders }
      response: [{ open: 3 }]
  succeeds: true
```

## Aktualizacja kontrahenta [#update-a-contractor]

`UPDATE_CONTRACTOR` zmienia jednego z kontrahentów organizacji. Poprzedzony wywołaniem usługi utrzymuje dane kontrahenta w zgodzie z tą usługą.

```yaml title="actions/refresh-contractor/rule.yaml"
entryStepId: lookup
steps:
  - id: lookup
    type: CALL_WEBHOOK
    name: Ask the shop
    contextKey: customer
    config:
      url: "https://api.example.com/v1/customers?email={{ trigger.data.email }}"
      method: GET
  - id: store
    type: UPDATE_CONTRACTOR
    name: Store the phone
    config:
      contractorId: "{{ trigger.data.contractorId }}"
      fields: { phone: "{{ customer.body.phone }}" }
edges:
  - { fromStepId: lookup, toStepId: store }
```

| Klucz | Wymagany | Znaczenie |
| --- | --- | --- |
| `contractorId` | Tak | Kontrahent, zwykle z wejścia kroku. |
| `fields` | Tak | Pola kontrahenta do zmiany, na przykład `email`, `phone` albo `website`. |

Krok nie ma wyniku, więc jego efekt nie ma `response`:

```yaml title="actions/refresh-contractor/tests.yaml"
- name: the phone the shop has is stored
  input: { contractorId: c-1, email: ada@example.com }
  http:
    - request: { method: GET, url: "https://api.example.com/v1/customers?email=ada@example.com" }
      response: { status: 200, body: { phone: "+48 600 100 200" } }
  effects:
    - request:
        step: UPDATE_CONTRACTOR
        contractorId: c-1
        fields: { phone: "+48 600 100 200" }
  succeeds: true
```

## Wygenerowanie dokumentu [#generate-a-document]

`GENERATE_DOCUMENT` renderuje szablon dokumentu danych organizacji. Szablonu nigdy nie wybiera paczka: wybiera go autor reguły organizacji w wejściu twojego kroku. Paczka z tym krokiem wymienia `documents` w `requires.modules`.

| Klucz | Wymagany | Znaczenie |
| --- | --- | --- |
| `templateId` | Tak | Dokładnie `{{ trigger.data.<field> }}`. Każda inna postać jest odrzucana. |
| `data` | Nie | To, co renderuje szablon. |
| `templateVersionId` | Nie | Wersja szablonu; renderuje się tylko jego bieżąca opublikowana wersja. |
| `metadata` | Nie | Zapisywane z wygenerowanym plikiem. |
| `entityId`, `invoiceId` | Odrzucane | Paczka renderuje tylko szablony danych, nigdy rekord. |

Wynik ma `fileId`, `documentGenerationJobId`, `templateId`, `templateVersionId`, `mimeType` i `originalName`; przekaż `fileId` dalej, żeby dołączyć plik. Gdy generowanie dokumentów jest w organizacji wyłączone, krok kończy się błędem.

## Wysłanie e-maila [#send-an-email]

`SEND_EMAIL` wysyła przez usługę e-mail instalacji.

| Klucz | Wymagany | Znaczenie |
| --- | --- | --- |
| `to` | Tak | Adres. |
| `subject`, `html` | Nie | Wpisane w kroku. Dozwolone są też `bodyFormat`, `locale` i `data`. |
| `attachmentFileIds` | Nie | Identyfikatory plików do dołączenia, na przykład dokumentu wygenerowanego we wcześniejszym kroku. `fileIds` to starsza nazwa. Można dołączyć dowolny plik organizacji; zobacz [Załączniki](/docs/pl/extensions/reference/data-permissions#the-scopes). |
| `accountId`, `templateId`, `cc`, `bcc`, `text`, `saveAsDraft` | Odrzucane | Paczka nie wysyła poczty ze skrzynki i nie wybiera szablonu e-maila. |

Krok nie ma wyniku. Bez usługi e-mail w instalacji kończy się błędem `service_connection_not_configured`.

## Wysłanie powiadomienia [#send-a-notification]

`SEND_NOTIFICATION` wysyła ogólne powiadomienie, z tytułem i treścią, do członków organizacji.

| Klucz | Wymagany | Znaczenie |
| --- | --- | --- |
| `recipients` | Tak | Kto je dostaje, na przykład `userIds`. Dostają je tylko aktywni członkowie organizacji. |
| `title`, `body` | Nie | Teksty powiadomienia. |
| `linkUrl`, `payload`, `entityRef`, `dedupeKey`, `collapseWindowMinutes` | Nie | Jak w edytorze reguł. |
| `typeKey` | Odrzucane | Paczka wysyła tylko ogólne powiadomienie. |

Wynikiem jest `{ notificationId, recipientCount, collapsed, suppressed }`.

## Dokument, e-mail i powiadomienie [#a-document-an-email-and-a-notification]

Ta akcja renderuje potwierdzenie zamówienia, wysyła je klientowi e-mailem jako załącznik i powiadamia współpracownika. Potrzebuje zakresów `documents:generate`, `email:send` i `notifications:send`. Jej krawędzie błędów zachowują przyczynę, gdy krok się nie powiedzie.

```yaml title="actions/confirm-order/action.yaml"
action: confirm_order
label: Confirm order
description: Renders the confirmation, emails it to the customer and notifies a colleague.
input:
  templateId:
    type: text
    label: Document template
    help: A data document template of your organization.
    required: true
  number: { type: text, label: Order number, required: true }
  email: { type: text, label: Customer email, required: true }
  colleagueId: { type: text, label: Colleague to notify, required: true }
run: rule.yaml
tests: tests.yaml
expose:
  ruleStep: { category: notifications }
```

```yaml title="actions/confirm-order/rule.yaml"
entryStepId: render
steps:
  - id: render
    type: GENERATE_DOCUMENT
    name: Render the confirmation
    contextKey: document
    config:
      templateId: "{{ trigger.data.templateId }}"
      data:
        title: "Order {{ trigger.data.number }}"
  - id: mail
    type: SEND_EMAIL
    name: Email the customer
    contextKey: mail
    config:
      to: "{{ trigger.data.email }}"
      subject: "Order {{ trigger.data.number }} is confirmed"
      html: "<p>Your order {{ trigger.data.number }} is confirmed.</p>"
      attachmentFileIds: ["{{ document.fileId }}"]
  - id: notify
    type: SEND_NOTIFICATION
    name: Tell a colleague
    contextKey: output
    config:
      recipients:
        userIds: ["{{ trigger.data.colleagueId }}"]
      title: "Order {{ trigger.data.number }} confirmed"
      body: "The confirmation went to {{ trigger.data.email }}."
  - id: unavailable
    type: SAVE_TO_CONTEXT
    name: Keep the reason
    contextKey: failure
    config:
      value:
        code: "{{ error.code }}"
        message: "{{ error.message }}"
edges:
  - { fromStepId: render, toStepId: mail }
  - { fromStepId: mail, toStepId: notify }
  - { fromStepId: render, toStepId: unavailable, branchKey: error }
  - { fromStepId: mail, toStepId: unavailable, branchKey: error }
```

```yaml title="actions/confirm-order/tests.yaml"
- name: the confirmation is rendered, emailed with its file and announced
  input:
    templateId: tpl-1
    number: A-1
    email: customer@example.com
    colleagueId: user-2
  effects:
    - request:
        step: GENERATE_DOCUMENT
        templateId: tpl-1
        data: { title: Order A-1 }
      response:
        fileId: file-1
        documentGenerationJobId: job-1
        templateId: tpl-1
        templateVersionId: version-1
        mimeType: application/pdf
        originalName: document-job-1.pdf
    - request:
        step: SEND_EMAIL
        to: customer@example.com
        subject: Order A-1 is confirmed
        attachmentFileIds: [file-1]
    - request:
        step: SEND_NOTIFICATION
        recipients: { userIds: [user-2] }
        title: Order A-1 confirmed
      response:
        notificationId: notification-1
        recipientCount: 1
        collapsed: false
        suppressed: false
  succeeds: true
```

## Gdy krok danych się nie powiedzie [#when-a-data-step-fails]

Nieudany krok danych kończy twoją akcję błędem jak każdy krok, chyba że przechwyci go krawędź `error`; krok tej krawędzi odczytuje `{{ error.code }}` i `{{ error.message }}`. Reguła organizacji, która używa twojego kroku, widzi `EXTENSION_ACTION_FAILED`, gdy akcja się nie powiedzie. Krok, który przy uruchomieniu sięgnąłby poza zadeklarowane zakresy, kończy się błędem `EXTENSION_SCOPE_DENIED` i nic nie robi. `UPDATE_RECORD`, którego identyfikator rekordu wychodzi pusty, jak wtedy, gdy wcześniejszy krok niczego nie znalazł, kończy się błędem `EXTENSION_STEP_NO_TARGET`.

## Skrypty nie dostają danych [#scripts-get-no-data]

Krok **Uruchom skrypt** ani skrypt uruchamiany przez akcję nie może odczytywać ani zapisywać danych ani wysyłać powiadomień: w paczce skrypty nie dostają pomocników danych. Najpierw pobierz dane krokiem, przekaż je skryptowi przez kontekst, a wynik skryptu zapisz kolejnym krokiem.

## Problemy [#problems]

| Kod | Przyczyna | Rozwiązanie |
| --- | --- | --- |
| `step.scope_missing` | Krok danych, którego zakresu paczka nie deklaruje. | Dodaj zakres do `permissions.data`, z powodem. |
| `step.target_not_own` | Krok wskazuje moduł inny niż `x-<key>`, obiekt, którego paczka nie ma, albo klucz zapytania, który nie jest kluczem `x_<key z _>_<name>` zapytania paczki. | Wskaż własny obiekt albo zapytanie paczki. |
| `step.target_not_literal` | Klucz modułu, obiektu albo zapytania pochodzi z szablonu, także z ustawienia. | Wpisz klucz wprost. |
| `step.config_not_allowed` | Odrzucany klucz z tabel powyżej, aktualizacja bez identyfikatora rekordu albo z `target: self`, albo `templateId`, który nie jest dokładnie `{{ trigger.data.<field> }}`. | Usuń klucz albo zapisz go tak, jak mówi tabela. |
| `step.type_not_allowed` | Typ kroku, którego nie obejmuje żaden zakres, na przykład `ATTACH_FILE` albo `CALL_RULE`. | Przenieś tę pracę do reguły organizacji, która używa twojego kroku. |
| `action.verify_uses_data` | Akcja weryfikująca połączenie używa kroku danych. | Ogranicz akcję weryfikującą do wywołań i logiki. |
| `test.invalid` | Przypadek testowy z `effects` w paczce bez zakresów danych. | Zadeklaruj zakres albo usuń efekty. |

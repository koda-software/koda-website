title: Testy
description: Napisz przypadki testowe, których potrzebuje każda akcja. Opisują wywołania i kroki danych akcji, a Opero uruchamia je offline przy każdym przesłaniu.
---

Każda akcja ma co najmniej jeden przypadek testowy. Przypadek podaje wejście, opisuje wywołania HTTP i kroki danych, które akcja ma wykonać, i mówi, jak się kończy. Opero uruchamia wszystkie przypadki przy przesłaniu, a na żądanie przez `opero-ext test`, niczego nie wysyłając przez sieć, nie odczytując ani nie zapisując żadnych danych i nie uruchamiając żadnej reguły. [Część 3 samouczka](/docs/pl/extensions/tutorial/check-and-pack) je uruchamia.

```yaml title="actions/greet/tests.yaml"
- name: the greeting is sent
  input: { name: Ada }
  settings: { language: pl }
  connection: { token: test-token }
  http:
    - request:
        method: POST
        url: https://httpbin.org/anything?lang=pl
        headers: { authorization: Bearer test-token }
        body: { greeting: "Hello, Ada!" }
      response:
        status: 200
        headers: { content-type: application/json }
        body: { json: { greeting: "Hello, Ada!" } }
  returns:
    status: 200
    headers: { content-type: application/json }
    body: { json: { greeting: "Hello, Ada!" } }
```

## Wymiany HTTP [#http-exchanges]

Każdy wpis `http` to `request`, które akcja musi wysłać jako następne, i `response`, które dostaje w odpowiedzi.

| Klucz | Znaczenie |
| --- | --- |
| `request.method` | `GET`, `POST`, `PUT`, `PATCH` albo `DELETE`. Wymagane. |
| `request.url` | Cały adres `https://`, z parametrami zapytania. Wymagane. |
| `request.headers` | Nagłówki, które muszą zostać wysłane z tymi wartościami. Nazwy pasują bez względu na wielkość liter; pominięte nagłówki nie są porównywane. |
| `request.body` | Treść, porównywana dokładnie, gdy jest podana. Treść JSON jest porównywana jako JSON. |
| `response.status` | Status, który dostaje akcja, od `100` do `599`. Wymagane. |
| `response.headers`, `response.body` | Co jeszcze dostaje akcja. |

Wartości, które Opero wstawia za sekrety, są w żądaniu przed porównaniem, więc przypadek sprawdza `Bearer test-token` z `token`, który podaje w `connection`.

## Ustawienia w przypadku [#settings-in-a-case]

Ustawienia przypadku, z zastosowanymi wartościami domyślnymi, muszą pasować do `settings.yaml`. Wymagane ustawienie bez wartości domyślnej trzeba więc podać w każdym przypadku, także w przypadkach akcji, które go nie czytają. Zobacz [Ustawienia w testach](/docs/pl/extensions/reference/settings#settings-in-tests).

## Kroki danych i wiadomości [#data-and-messaging-steps]

Gdy reguła akcji używa [kroków danych](/docs/pl/extensions/reference/data-steps), przypadek opisuje je w `effects`, tak jak `http` opisuje wywołania. Żaden rekord nie jest odczytywany ani zapisywany i nic nie jest wysyłane: każdy krok jest porównywany ze swoim efektem i zwraca jego `response`.

```yaml title="actions/sync-order/tests.yaml"
- name: the open order gets the status the carrier answers
  input: { status: synced }
  http:
    - request:
        method: POST
        url: https://api.example.com/v1/orders
        body: { number: A-1, status: synced }
      response: { status: 200, body: { status: synced } }
  effects:
    - request: { step: FETCH_RECORDS, objectKey: orders }
      response:
        rows: [{ id: 7d1c2a34-0000-4000-8000-000000000001, number: A-1, status: open }]
        rowCount: 1
        truncated: false
    - request:
        step: UPDATE_RECORD
        targetObjectKey: orders
        fieldUpdates: { status: synced }
  succeeds: true
```

| Klucz | Znaczenie |
| --- | --- |
| `request.step` | Typ kroku: `FETCH_RECORDS`, `CREATE_RECORD`, `UPDATE_RECORD`, `RUN_QUERY`, `UPDATE_CONTRACTOR`, `SEND_EMAIL`, `SEND_NOTIFICATION` albo `GENERATE_DOCUMENT`. Wymagany. |
| Inne klucze `request` | Klucze ustawień kroku, porównywane z tym, co krok dostał po wypełnieniu szablonów. Pominięte klucze nie są porównywane. |
| `response` | Co zwraca krok, w kształcie, który zwraca prawdziwy krok. Pomiń dla `UPDATE_RECORD`, `UPDATE_CONTRACTOR` i `SEND_EMAIL`, które niczego nie zwracają. |

`effects` i `http` to dwie osobne listy, każda w kolejności, w jakiej używa ich akcja. Efekt `RUN_QUERY` wskazuje zapytanie po jego zainstalowanym kluczu, tak jak reguła: `queryKey: x_orders_ext_orders_by_day`. Każdy krok jest sprawdzany z zakresami danych paczki, zanim dostanie swój efekt, więc test nie przejdzie z krokiem, na który zakresy nie pozwalają.

## Zdarzenia [#events]

Dla akcji, której reguła używa [`EMIT_EVENT`](/docs/pl/extensions/reference/raising-events), `events` wymienia zdarzenia, które uruchomienie musi zgłosić, a `seen` mówi, co Opero już pamięta, gdy przypadek się zaczyna, żeby przetestować deduplikację.

```yaml title="actions/sync-orders/tests.yaml"
- name: an order seen before, unchanged, raises nothing
  input: { subject: { kind: company, companyId: co_1 }, lastSucceededAt: "2026-11-02T10:00:00Z", firstRun: false }
  seen:
    - { event: order_changed, key: A-1, data: { number: A-1, status: open, total: 120.5 } }
  http:
    - request:
        method: GET
        url: https://api.example.com/v1/orders?company=co_1&status=open
      response:
        status: 200
        body: { items: [{ number: A-1, status: open, total: 120.5 }] }
  events: []
  returns: { emitted: 0, unchanged: 1 }
```

| Klucz | Znaczenie |
| --- | --- |
| `events[].event` | Nazwa wyzwalacza. Wymagana. |
| `events[].key` | Klucz elementu. Porównywany, gdy jest podany. |
| `events[].data` | Dane zdarzenia. Porównywane dokładnie, gdy są podane. |
| `seen[]` | `event`, `key` i `data` elementu w takiej postaci, w jakiej był ostatnio zgłoszony. Element z tym samym kluczem i tymi samymi danymi jest niezmieniony. |

`events` jest porównywane po kolei. `events: []` mówi, że uruchomienie niczego nie zgłasza; przypadek bez `events` w ogóle nie sprawdza zdarzeń. Każde zgłoszone zdarzenie jest sprawdzane z danymi wyzwalacza, tak jak w prawdziwym uruchomieniu. Nic nie trafia do kolejki i żadna reguła się nie zaczyna. Akcja, która zgłasza zdarzenia, potrzebuje co najmniej jednego przypadku z niepustym `events`.

## Akcje członka [#member-actions]

[Akcja członka](/docs/pl/extensions/reference/member-connections#the-members-values-in-rules) używa `{{ userConnection.<field> }}`. Jej przypadek podaje te wartości w `userConnection` oraz `input`, które przekazuje zaczep albo harmonogram.

```yaml title="actions/sync-member/tests.yaml"
- name: a revoked token
  input:
    subject: { kind: userConnection, userId: u_1, credentialId: c_1, companyId: co_1, config: { companyId: co_1 }, meta: { sandboxUserId: "1234" } }
    lastSucceededAt: "2026-11-02T10:00:00Z"
    firstRun: false
  userConnection: { accessToken: revoked-token }
  http:
    - request:
        method: GET
        url: https://api.example.com/v1/activities?user=1234
        headers: { authorization: Bearer revoked-token }
      response: { status: 401 }
  credentialRevoked: true
```

`userConnection` przyjmuje `accessToken`, `refreshToken` i wyjścia `secret` z `afterConnect`. `credentialRevoked: true` to wynik, gdy żądanie z tokenem członka dostało odpowiedź `401`; w prawdziwym uruchomieniu dla tego członka nic więcej się wtedy nie uruchamia, dopóki [nie połączy się ponownie](/docs/pl/extensions/reference/member-connections#a-refused-token). Odpowiedź `401` na żądanie bez tokenu członka to zwykły błąd: oczekuj `fails: { status: 401 }`.

## Przypadki renderowania bloków [#block-render-cases]

Każdy [blok](/docs/pl/extensions/reference/blocks#render-tests) ma własny `tests.yaml` z przypadkami renderowania: danymi wejściowymi i wierszami do renderowania oraz tekstami, które HTML musi zawierać albo których nie może zawierać. Opero renderuje je przy przesłaniu, po przypadkach akcji, w tych samych limitach.

## Jak kończy się przypadek [#how-a-case-ends]

Każdy przypadek ma dokładnie jeden wynik:

| Wynik | Przechodzi, gdy |
| --- | --- |
| `returns: <output>` | Akcja zwraca dokładnie ten wynik. |
| `succeeds: true` | Akcja kończy się bez błędu, niezależnie od tego, co zwraca. |
| `fails: true` | Akcja kończy się błędem. |
| `fails: { status: 409 }` | Akcja kończy się błędem, bo usługa odpowiedziała tym statusem. |
| `rateLimited: true` | Usługa odpowiedziała `429`. |
| `rateLimited: { status: 429 }` | To samo, z wpisanym statusem. |
| `credentialRevoked: true` | Akcja członka: żądanie, które niosło token członka, dostało odpowiedź `401`. |

```yaml
- name: a valid token is accepted
```

```yaml
- name: a refused token fails

    - request: { method: GET, url: https://httpbin.org/bearer }

  fails: { status: 401 }
```

```yaml

    - request: { method: POST, url: https://httpbin.org/anything?lang=en }
      response: { status: 429, headers: { retry-after: "30" } }
```

## Kiedy przypadek nie przechodzi [#when-a-case-fails]

Nieudany przypadek jest wskazywany przez plik i pozycję, np. `actions/greet/tests.yaml#/0`, a przy wymianie albo efekcie przez miejsce wewnątrz niego, np. `…#/0/http/1`. Każdy nieudany przypadek paczki jest zgłaszany w jednym przebiegu. Kody wymienia sekcja [Problemy](#problems).

## Limity [#limits]

| Co | Limit |
| --- | --- |
| Przypadki na akcję | Od 1 do 50 |
| Przypadki na paczkę | 200, przypadki akcji i renderowania bloków razem |
| Wymiany i efekty na przypadek | Po 50 |
| `events` i `seen` na przypadek | Po 500 |
| Czas na przypadek | 10 sekund |
| Czas na wszystkie przypadki paczki | 60 sekund |

## Kilka plików testów [#several-test-files]

`tests` w `action.yaml` może wskazywać folder zamiast pliku. Każdy plik `.yaml` bezpośrednio w tym folderze jest wtedy plikiem testów:

<Files>
  <Folder name="actions" defaultOpen>
    <Folder name="greet" defaultOpen>
      <File name="action.yaml" />
      <File name="rule.yaml" />
      <Folder name="tests" defaultOpen>
        <File name="success.yaml" />
        <File name="errors.yaml" />
      </Folder>
    </Folder>
  </Folder>
</Files>

```yaml title="actions/greet/action.yaml"
tests: tests/
```

## Problemy [#problems]

Przy odczycie paczki, przez `opero-ext validate` i przy przesłaniu:

| Kod | Przyczyna | Rozwiązanie |
| --- | --- | --- |
| `test.invalid` | Przypadek w złym kształcie, bez wyniku albo z dwoma, wejście niepasujące do pól wejściowych, ustawienia niepasujące do `settings.yaml`, podane bez niego albo w `connection.config`, `effects` bez zakresów danych, `events` lub `seen` przy akcji, która niczego nie zgłasza, `userConnection` albo `credentialRevoked` przy akcji, która nie jest akcją członka, albo ponad 50 przypadków. | Popraw przypadek tak, jak mówi komunikat. |
| `action.missing_test` | Akcja bez przypadku. | Napisz przypadek. |
| `event.unknown` | `events` albo `seen` wskazuje wyzwalacz, którego paczka nie ma. | Popraw nazwę. |
| `test.event_untested` | Żaden przypadek akcji, która zgłasza zdarzenia, nie wymienia oczekiwanych zdarzeń. | Dodaj przypadek z niepustym `events`. |

Przy uruchamianiu przypadków, przy przesłaniu i w `opero-ext test`:

| Kod | Co się stało |
| --- | --- |
| `test.unexpected_request` | Akcja wysłała żądanie, którego przypadek nie opisuje. |
| `test.request_mismatch` | Metoda, URL, wymieniony nagłówek albo treść różnią się od przypadku. |
| `test.unused_exchange` | Przypadek opisuje żądanie, którego akcja nie wysłała. |
| `test.unexpected_effect` | Akcja wykonała krok danych, którego przypadek nie opisuje jako następnego. |
| `test.effect_mismatch` | Klucz podany w efekcie różni się od tego, co dostał krok, albo `response` efektu nie ma kształtu, który zwraca krok. |
| `test.unused_effect` | Przypadek opisuje krok danych, którego akcja nie wykonała. |
| `test.unexpected_event` | Akcja zgłosiła zdarzenie po tych, które wymienia przypadek. |
| `test.event_mismatch` | Zgłoszone zdarzenie różni się od wymienionego na tej pozycji: wyzwalaczem, kluczem albo danymi. |
| `test.missing_event` | Przypadek wymienia zdarzenie, którego akcja nie zgłosiła. |
| `test.outcome_mismatch` | Akcja zakończyła się inaczej, niż mówi przypadek, albo z innym statusem. |
| `test.output_mismatch` | Wynik różni się od `returns`. |
| `test.output_schema` | Wynik nie pasuje do pól wyjściowych. |
| `test.failed` | Przypadek nie mógł się zakończyć, np. zabrakło czasu, albo paczka ma ponad 200 przypadków. |

Kody przypadków renderowania bloków opisuje strona [Bloki](/docs/pl/extensions/reference/blocks#render-tests).

Harmonogram uruchamia jedną z akcji paczki samodzielnie, w stałych odstępach, bez żadnej reguły organizacji. Użyj go, żeby regularnie odczytywać usługę i [zgłaszać zdarzenia](/docs/pl/extensions/reference/raising-events) dla tego, co jest nowe albo się zmieniło. Po jednym harmonogramie budują przewodniki [Zdarzenia z usługi](/docs/pl/extensions/scheduled-events) i [Dane z konta każdego członka](/docs/pl/extensions/member-accounts).

```yaml title="schedules/sync-orders/schedule.yaml"
schedule: sync_orders
label: Sync open orders
description: Reads each company's open orders every hour.
every: 1h
forEach: company
action: sync_orders
```

Każdy harmonogram to folder `schedules/<folder>` z plikiem `schedule.yaml`, wymieniony w `schedules` w `extension.yaml` albo w `module.yaml` modułu. `opero-ext add schedule <name> --action <action>` zapisuje jedno i drugie.

## Dla czego jest jedno uruchomienie [#what-one-run-is-for]

`forEach` decyduje, ile jest uruchomień w każdym odstępie i dla kogo. Każde z nich dotyczy **podmiotu**.

| `forEach` | Podmioty | Firma uruchomienia |
| --- | --- | --- |
| `installation` | Jeden, dla całego zainstalowanego rozszerzenia. | Brak. |
| `company` | Każda aktywna firma organizacji. | Ta firma. |
| `userConnection` | Każdy członek, który połączył konto przez [połączenie członka](/docs/pl/extensions/reference/member-connections) paczki. | Firma wybrana przez członka; brak, gdy połączenie członka nie ma pola firmy. |

[Kroki danych](/docs/pl/extensions/reference/data-steps) działają w firmie uruchomienia, a zgłaszane przez nie zdarzenia trafiają do niej. Nowa firma albo nowo połączony członek dostaje pierwsze uruchomienie w pierwszym odstępie po tym, jak Opero go zauważy, czyli w ciągu minuty; firma, która staje się nieaktywna albo zostaje usunięta, i członek, który się rozłącza, nie mają kolejnych uruchomień.

`forEach: userConnection` wymaga połączenia członka, a jego akcja musi być akcją członka, czyli używać `{{ userConnection.<field> }}`.

## Wejście każdego uruchomienia [#the-input-each-run-receives]

Opero wypełnia wejście akcji. Plik reguły odczytuje je jako `{{ trigger.data.… }}`, skrypt jako `input`:

<Tab value="company">

```yaml
subject:
  kind: company
  companyId: cmp_8f2a…
lastSucceededAt: "2026-11-12T09:00:04.512Z"   # null before the first success
firstRun: false
```

</Tab>
<Tab value="installation">

```yaml
subject:
  kind: installation
  companyId: null
lastSucceededAt: null
firstRun: true
```

</Tab>
<Tab value="userConnection">

```yaml
subject:
  kind: userConnection
  companyId: cmp_8f2a…        # null without a company field
  userId: usr_51c0…
  credentialId: cred_77d1…
  config: { companyId: cmp_8f2a… }   # the member's config form
  meta: { sandboxUserId: "1234" }    # what afterConnect stored as meta
lastSucceededAt: "2026-11-12T09:00:04.512Z"
firstRun: false
```

</Tab>
</Tabs>

| Pole | Znaczenie |
| --- | --- |
| `subject.kind` | `forEach` harmonogramu. |
| `subject.companyId` | Firma uruchomienia albo `null`. |
| `subject.userId`, `credentialId`, `config`, `meta` | Tylko dla członka: kim jest, jego połączenie, jego formularz i publiczne wartości zapisane przez `afterConnect`. Nigdy jego token. |
| `lastSucceededAt` | Kiedy skończyło się ostatnie udane uruchomienie tego podmiotu albo `null` przed pierwszym. Pytaj usługę o to, co zmieniło się od tego czasu, z pewnym zapasem, a [deduplikacja](/docs/pl/extensions/reference/raising-events#dedupe) pominie to, co już zgłoszono. |
| `firstRun` | `true`, dopóki ten podmiot nie miał udanego uruchomienia, na przykład żeby za pierwszym razem odczytać dłuższy okres. |

`input` akcji musi to przyjmować. Zadeklaruj je jako listę pól albo podaj plik JSON Schema, który zostawia `subject` otwarty:

```yaml title="actions/sync-orders/action.yaml (part)"
input:
  subject:
    type: object
    label: Subject
    required: true
    fields:
      kind: { type: text, required: true }
      companyId: { type: text, nullable: true }
  lastSucceededAt: { type: datetime, nullable: true }
  firstRun: { type: boolean, required: true }
```

Lista pól zamyka obiekt, więc dla `forEach: userConnection` musi też wymieniać `userId`, `credentialId`, `config` i `meta`; otwarty plik schematu jest tam prostszy.

## Jako kto działa uruchomienie [#who-the-run-acts-as]

Uruchomienie harmonogramu to uruchomienie zainstalowanej reguły akcji, rozpoczęte przez samo rozszerzenie, widoczne w historii tej reguły. Działa jako rozszerzenie, z [zakresami danych](/docs/pl/extensions/reference/data-permissions), na które zgodził się administrator, z [ustawieniami](/docs/pl/extensions/reference/settings) i połączeniem rozszerzenia. Uruchomienie dla połączeń członków ma też wartości tego członka i tylko jego.

## Kiedy działa [#when-it-runs]

Każdy podmiot działa raz w każdym odstępie i najwyżej raz w danej chwili, także gdy Opero działa na kilku serwerach. Pierwsze uruchomienie przychodzi w pierwszym odstępie po instalacji, rozłożone tak, żeby podmioty nie startowały w tej samej minucie. Następne uruchomienie liczy się od końca poprzedniego:

| Jak zakończyło się uruchomienie | Następne uruchomienie |
| --- | --- |
| Sukces | Jeden odstęp później. |
| Limit zapytań: żądanie dostało odpowiedź `429` | Po czasie z `Retry-After` usługi, a w przeciwnym razie z `RateLimit-Reset`; po 15 minutach, gdy usługa nic nie podała; nigdy później niż za jeden odstęp. Nie liczy się jako błąd. |
| Błąd: błąd HTTP, niepasujące wejście albo wyjście, nieudany krok | Po 15 minutach, potem po 30 minutach, godzinie i tak dalej, za każdym razem dwa razy dłużej, nigdy później niż za jeden odstęp. |
| Token członka został odrzucony (`401` na żądanie, które go niosło) | Dopiero gdy członek połączy się ponownie; zobacz [Odrzucony token](/docs/pl/extensions/reference/member-connections#a-refused-token). |

Pominięte odstępy nigdy nie są nadrabiane: podmiot, który czekał przez kilka odstępów, uruchamia się raz. Członek jest pomijany, bez błędu, dopóki nie wybrał firmy, wybrana firma nie jest już jego albo jego połączenie czeka na ponowne połączenie. Dopóki rozszerzenie nie działa, jego harmonogramy niczego nie uruchamiają; gdy znów działa, każdy podmiot, na który przyszła kolej, uruchamia się raz.

## Aktualizacje [#upgrades]

| Zmiana w nowej wersji | Co się dzieje | Kod |
| --- | --- | --- |
| Usunięto harmonogram | Zatrzymuje się, a jego stan uruchomień jest usuwany. Ostrzeżenie. | `schedule.removed` |
| Zmieniło się `every`, `forEach` albo `action` harmonogramu | Od razu działa według nowego harmonogramu; zmienione `forEach` usuwa stare podmioty. Ostrzeżenie. | `schedule.changed` |
| Dodano harmonogram | Przegląd pokazuje go jako nowy, do akceptacji przez administratora. | |

Odinstalowanie zatrzymuje wszystkie harmonogramy. Co widzi administrator, opisuje strona [Aktualizacja i odinstalowanie](/docs/pl/extensions/upgrade-and-uninstall#what-a-new-version-can-change), a jak śledzi uruchomienia, sekcja [Harmonogramy](/docs/pl/extensions/after-install#schedules).

## Tłumaczenia [#translations]

Teksty trafiają do `schedules.<schedule>`: `label` i `description`. Zobacz [Tłumaczenia](/docs/pl/extensions/reference/translations#translatable-keys).

## Problemy [#problems]

| Kod | Przyczyna | Rozwiązanie |
| --- | --- | --- |
| `schedule.invalid` | Nieznany klucz, `every` albo `forEach` spoza wymienionych wartości, `forEach: userConnection` bez połączenia członka albo z akcją, która nie jest akcją członka, wejście akcji, które nie przyjmuje tego, co przekazuje harmonogram (komunikat podaje pierwszą różnicę), albo więcej niż 10 harmonogramów. | Popraw klucz albo wejście akcji. |
| `schedule.action_unknown` | `action` nie wskazuje żadnej akcji paczki. | Popraw nazwę albo dodaj akcję. |
| `schedule.action_exposed` | Akcja jest udostępniona jako krok reguły, akcja bloku albo polecenie rekordu. | Daj harmonogramowi własną akcję, której nic nie udostępnia. |
| `action.member_outside_member_run` | Akcję członka uruchamia harmonogram, który nie jest `forEach: userConnection`. | Użyj `forEach: userConnection`. |
| `name.duplicate` | Dwa harmonogramy o tej samej nazwie. | Zmień nazwę jednego z nich. |

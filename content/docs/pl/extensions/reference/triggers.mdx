title: Wyzwalacze
description: Zadeklaruj wyzwalacz w trigger.yaml, żeby reguły organizacji startowały, gdy coś dzieje się w twojej usłudze, z jego danymi, filtrami i deduplikacją.
---

Wyzwalacz pozwala regułom organizacji startować, gdy coś dzieje się w usłudze zewnętrznej. Paczka deklaruje wyzwalacz i zgłasza jego zdarzenia; organizacja buduje na nim reguły, jak na każdym innym [wyzwalaczu reguł](/docs/pl/opero/07-automatyzacja/wyzwalacze). Taki wyzwalacz buduje przewodnik [Zdarzenia z usługi](/docs/pl/extensions/scheduled-events).

```yaml title="triggers/order-changed/trigger.yaml"
trigger: order_changed
label: Order changed
description: An open order is new, or one of its values changed.
data:
  number: { type: text, label: Order number, required: true }
  status: { type: select, label: Status, options: [open, packed, shipped], required: true }
  total: { type: number, label: Total, nullable: true }
  updatedAt: { type: datetime, label: Updated at }
config:
  status: { type: select, label: Only this status, options: [open, packed, shipped], match: status }
dedupe: { retentionDays: 30 }
example: { number: A-1, status: open, total: 120.5, updatedAt: "2026-11-01T10:00:00Z" }
```

Każdy wyzwalacz to folder `triggers/<folder>` z plikiem `trigger.yaml`, wymieniony w `triggers` w `extension.yaml` albo w `module.yaml` modułu. `opero-ext add trigger <name>` zapisuje jedno i drugie.

<Callout title="Sam wyzwalacz niczego nie zgłasza">
Zdarzenia wyzwalacza zgłasza tylko paczka, krokiem [`EMIT_EVENT`](/docs/pl/extensions/reference/raising-events), z uruchomienia [harmonogramu](/docs/pl/extensions/reference/schedules) albo z haka [połączenia członka](/docs/pl/extensions/reference/member-connections). Reguła organizacji nie może ich zgłaszać.
</Callout>

## Dane [#the-data]

`data` to umowa między paczką a regułami zbudowanymi na wyzwalaczu: reguła uruchomiona przez zdarzenie odczytuje `{{ trigger.data.<field> }}`, a dane każdego zdarzenia są zachowywane w historii uruchomień reguły.

| Zasada | Szczegóły |
| --- | --- |
| [Lista pól](/docs/pl/extensions/reference/actions#field-lists) albo plik JSON Schema w folderze | Przy liście pól pole, którego lista nie wymienia, jest odrzucane. |
| `nullable: true` | Wartością pola może być też `null`. Przyjmują to tylko wejścia i wyjścia akcji oraz dane wyzwalaczy. |
| Sprawdzane przed zgłoszeniem | Zdarzenie, które nie pasuje, kończy błędem krok, który je zgłasza, i nic nie jest zgłaszane. |
| Najwyżej 32 KB | JSON-a, na jedno zdarzenie. |

Wygenerowany typ `Triggers` w `.opero/types/index.d.ts` daje skryptowi, który buduje elementy, ich kształt.

## Filtry [#filters]

`config` wymienia filtry, które może ustawić autor reguły. Każde pole ma `type` równy `text`, `number`, `boolean` albo `select` oraz `match`: pole danych najwyższego poziomu, z którym jest porównywane.

```yaml title="triggers/activity/trigger.yaml (part)"
config:
  member: { type: text, label: Only this member, match: userId }
```

Reguła startuje tylko dla zdarzeń, których pole danych jest równe ustawionej wartości; gdy pole danych jest listą, lista musi zawierać tę wartość. Pusty filtr niczego nie filtruje, a wartości są porównywane dokładnie, bez konwersji: `10` nie pasuje do `"10"`.

## Czas pamiętania deduplikacji [#dedupe-retention]

Gdy [`EMIT_EVENT`](/docs/pl/extensions/reference/raising-events#dedupe) działa z `dedupe: true`, Opero pamięta każdy zgłoszony element, żeby niezmieniony element nie był zgłaszany ponownie. `dedupe.retentionDays` mówi, jak długo: element niezgłaszany przez tyle dni zostaje zapomniany i zgłoszony jeszcze raz, jeśli usługa wciąż go zwraca.

Wybierz czas dłuższy niż okres, przez który usługa zwraca niezmieniony element, albo pytaj usługę tylko o najnowsze elementy. Pamięć jest osobna dla instalacji, wyzwalacza i podmiotu uruchomienia: to samo zamówienie widziane w dwóch firmach jest pamiętane dwa razy. Aktualizacja ją zachowuje, odinstalowanie usuwa.

## Przykład [#the-example]

`example` to dane jednego zdarzenia. Gdy reguła na wyzwalaczu jest testowana i nie ma wcześniejszego uruchomienia do odtworzenia, Opero podaje je jako przykładowe dane. Bez przykładu Opero buduje go z pól danych: ich wartości domyślnych, pierwszej opcji wyboru, daty dla pola daty, etykiety pola tekstowego, `0`, `false` i pustych list.

## W regułach organizacji [#in-the-organizations-rules]

Gdy rozszerzenie działa, wyzwalacz jest w edytorze reguł typem `x-<key>.<trigger>`, w sekcji **Integracje**, z filtrami jako formularzem:

![Wyzwalacz Order changed na liście wyzwalaczy w edytorze reguł, w sekcji Integracje](/docs/_assets/extensions/scheduled-events/trigger-picker.webp)

```json title="The trigger of one of the organization's rules"
{
  "trigger": {
    "type": "x-order-events.order_changed",
    "config": { "status": "packed" }
  }
}
```

| Zasada | Szczegóły |
| --- | --- |
| Firma | Zdarzenie zgłoszone w uruchomieniu dla firmy uruchamia reguły tej firmy. Zdarzenie zgłoszone bez firmy uruchamia tylko reguły, które nie są ograniczone do wybranych firm. |
| Wykonawca | Zdarzenie pochodzi od rozszerzenia, więc reguła działa jako rozszerzenie. |
| Co najmniej raz | To samo zdarzenie może przyjść dwa razy. Pisz reguły tak, żeby drugie uruchomienie niczego nie zmieniało: znajdź rekord po kluczu i zaktualizuj go albo utwórz, gdy go brakuje. |
| Gdy rozszerzenie nie działa | Wyzwalacza brakuje w edytorze reguł i żadne zdarzenie nie uruchamia reguły, nawet zgłoszone, zanim rozszerzenie stanęło. Reguła, która ma ten wyzwalacz, go zachowuje. Zobacz [Stany](/docs/pl/extensions/after-install#states). |

## Aktualizacje [#upgrades]

| Zmiana w nowej wersji | Co się dzieje | Kod |
| --- | --- | --- |
| Usunięto wyzwalacz, którego używa reguła organizacji | Aktualizacja jest zablokowana, dopóki żadna reguła go nie używa. | `trigger.in_use` |
| Usunięto pola danych najwyższego poziomu wyzwalacza, którego używa reguła | Ostrzeżenie. Reguły nie są przeszukiwane pod kątem miejsc, w których odczytują te pola. | `trigger.data_field_removed` |
| Dodano wyzwalacz albo zmieniły się etykiety, filtry lub przykład | Nic do potwierdzenia poza przeglądem. | |

Wyzwalacz zachowuje tożsamość, dopóki jego nazwa `trigger` się nie zmienia, więc foldery można dowolnie przemianowywać. Odinstalowanie poddaje kwarantannie aktywne reguły na wyzwalaczach rozszerzenia. Co widzi administrator, opisuje strona [Aktualizacja i odinstalowanie](/docs/pl/extensions/upgrade-and-uninstall#what-a-new-version-can-change).

## Tłumaczenia [#translations]

Teksty trafiają do `triggers.<trigger>`: `label`, `description`, `data.<field>` i `config.<field>`. Zobacz [Tłumaczenia](/docs/pl/extensions/reference/translations#translatable-keys).

## Problemy [#problems]

| Kod | Przyczyna | Rozwiązanie |
| --- | --- | --- |
| `trigger.invalid` | Nieznany klucz, brak `label`, `description` lub `data`, filtr bez `match` albo innego typu, `retentionDays` spoza zakresu od 1 do 365, przykład, który nie pasuje do danych albo ma ponad 32 KB, plik schematu, który się nie kompiluje, albo więcej niż 50 wyzwalaczy. | Popraw klucz wskazany w komunikacie. |
| `trigger.match_unknown_field` | `match` filtra nie wskazuje żadnego pola danych najwyższego poziomu. | Wskaż pole danych najwyższego poziomu. |
| `field.invalid` | Pole danych albo filtra o złej strukturze, w tym `nullable` w filtrze. | Popraw pole. |
| `name.duplicate` | Dwa wyzwalacze o tej samej nazwie. | Zmień nazwę jednego z nich. |

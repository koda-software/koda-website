---
title: Zdarzenia z usługi
description: "Zbuduj rozszerzenie Opero, które co godzinę odczytuje usługę dla każdej firmy i zgłasza zdarzenie wyzwalacza, od którego zaczynają się reguły organizacji."
---

Ten przewodnik buduje paczkę **Zdarzenia zamówień**, która obserwuje otwarte zamówienia w usłudze zewnętrznej. Co godzinę harmonogram uruchamia jedną akcję dla każdej firmy. Akcja odczytuje otwarte zamówienia firmy i zgłasza wyzwalacz **Zmiana zamówienia** (`x-order-events.order_changed`) raz dla każdego zamówienia, które jest nowe albo zmieniło się od ostatniego uruchomienia. Organizacja buduje potem na tym wyzwalaczu własne reguły.

Usługa w tym przewodniku, `api.example.com`, nie wymaga klucza, więc paczka nie ma połączenia. Przy prawdziwej usłudze dodaj je tak jak w [samouczku](/docs/pl/extensions/tutorial/call-a-service).

<Steps>
<Step>
### Napisz manifest [#write-the-manifest]

```yaml title="extension.yaml"
manifestVersion: 2
extension: order-events
version: 1.0.0
name: Order events
description: Raises an event for every new or changed open order, checked every hour for each company.
publisher: Your company
requires:
  opero: ">=2026.1.0"
  modules: [rules]
permissions:
  network:
    - host: api.example.com
      reason: Reads each company's open orders.

actions:
  - actions/sync-orders
triggers:
  - triggers/order-changed
schedules:
  - schedules/sync-orders

locales: [pl]
```

Jeśli zaczynasz od `opero-ext init order-events`, polecenie `opero-ext add trigger order_changed` zapisze folder wyzwalacza i jego wpis tutaj. Harmonogram dodaj, gdy akcja już istnieje.
</Step>

<Step>
### Zadeklaruj wyzwalacz [#declare-the-trigger]

```yaml title="triggers/order-changed/trigger.yaml"
trigger: order_changed
label: Order changed
description: An open order is new, or one of its values changed.
data:
  number: { type: text, label: Order number, required: true }
  status: { type: select, label: Status, options: [open, packed, shipped], required: true }
  total: { type: number, label: Total, nullable: true }
  updatedAt: { type: datetime, label: Updated at }
config:
  status: { type: select, label: Only this status, options: [open, packed, shipped], match: status }
dedupe: { retentionDays: 30 }
example: { number: A-1, status: open, total: 120.5, updatedAt: "2026-11-01T10:00:00Z" }
```

| Klucz | Co tu robi |
| --- | --- |
| `data` | Co niesie każde zdarzenie. Reguły odczytują to jako `{{ trigger.data.<pole> }}`, a każde zdarzenie jest z tym sprawdzane. |
| `config` | Jeden filtr dla autorów reguł: gdy ustawią **Tylko ten status**, reguła zaczyna się tylko dla zamówień w tym statusie. |
| `dedupe.retentionDays` | Zamówienie, które nie zostało zgłoszone przez 30 dni, jest zapominane. |
| `example` | Dane przykładowe proponowane przy testowaniu reguły na tym wyzwalaczu. |

Zobacz [Wyzwalacze](/docs/pl/extensions/reference/triggers).
</Step>

<Step>
### Opisz akcję [#describe-the-action]

```yaml title="actions/sync-orders/action.yaml"
action: sync_orders
label: Sync orders
description: Reads the company's open orders and raises an event for each new or changed one.

input:
  subject:
    type: object
    label: Subject
    required: true
    fields:
      kind: { type: text, required: true }
      companyId: { type: text, nullable: true }
  lastSucceededAt: { type: datetime, nullable: true }
  firstRun: { type: boolean, required: true }
output:
  emitted: { type: integer, label: Raised }
  unchanged: { type: integer, label: Unchanged }

run: rule.yaml
tests: tests.yaml
```

Wejście to to, co harmonogram przekazuje przy każdym uruchomieniu: podmiot (tutaj firmę), czas ostatniego udanego uruchomienia i informację, czy to pierwsze uruchomienie. Nie ma `expose`: akcja, która zgłasza zdarzenia, nigdy nie jest krokiem reguły. Zobacz [Wejście każdego uruchomienia](/docs/pl/extensions/reference/schedules#the-input-each-run-receives).
</Step>

<Step>
### Napisz regułę [#write-the-rule]

Reguła odczytuje, a potem zgłasza:

```yaml title="actions/sync-orders/rule.yaml"
entryStepId: fetch
steps:
  - id: fetch
    type: CALL_WEBHOOK
    name: Open orders
    contextKey: orders
    config:
      method: GET
      url: "https://api.example.com/v1/orders?company={{ trigger.data.subject.companyId }}&status=open"
  - id: emit
    type: EMIT_EVENT
    name: Raise order events
    contextKey: output
    config:
      event: order_changed
      items: "{{ orders.body.items }}"
      key: number
      dedupe: true
edges:
  - { fromStepId: fetch, toStepId: emit }
```

Każdy element `items` staje się jednym zdarzeniem i musi pasować do `data` wyzwalacza. Dzięki `key: number` i `dedupe: true` zamówienie jest zgłaszane tylko wtedy, gdy jest nowe albo coś się w nim zmieniło od ostatniego zgłoszenia w tej firmie. Wynik kroku, `{ emitted, unchanged }`, jest wynikiem akcji. Zobacz [Zgłaszanie zdarzeń](/docs/pl/extensions/reference/raising-events).
</Step>

<Step>
### Dodaj harmonogram [#add-the-schedule]

```bash title="Terminal"
opero-ext add schedule sync_orders --action sync_orders --every 1h --for-each company
```

```yaml title="schedules/sync-orders/schedule.yaml"
schedule: sync_orders
label: Sync open orders
description: Reads each company's open orders every hour.
every: 1h
forEach: company
action: sync_orders
```

Co godzinę każda aktywna firma organizacji dostaje jedno uruchomienie `sync_orders`, a jego zdarzenia należą do tej firmy. Zobacz [Harmonogramy](/docs/pl/extensions/reference/schedules).
</Step>

<Step>
### Przetestuj [#test-it]

Trzy przypadki: nowe zamówienie zgłasza zdarzenie, to samo zamówienie bez zmian nie zgłasza niczego, a zamówienie z nowym statusem jest zgłaszane ponownie.

```yaml title="actions/sync-orders/tests.yaml"
- name: a new order raises an event
  input: { subject: { kind: company, companyId: co_1 }, lastSucceededAt: null, firstRun: true }
  http:
    - request:
        method: GET
        url: https://api.example.com/v1/orders?company=co_1&status=open
      response:
        status: 200
        body: { items: [{ number: A-1, status: open, total: 120.5 }] }
  events:
    - event: order_changed
      key: A-1
      data: { number: A-1, status: open, total: 120.5 }
  returns: { emitted: 1, unchanged: 0 }

- name: an order seen before, unchanged, raises nothing
  input: { subject: { kind: company, companyId: co_1 }, lastSucceededAt: "2026-11-02T10:00:00Z", firstRun: false }
  seen:
    - { event: order_changed, key: A-1, data: { number: A-1, status: open, total: 120.5 } }
  http:
    - request:
        method: GET
        url: https://api.example.com/v1/orders?company=co_1&status=open
      response:
        status: 200
        body: { items: [{ number: A-1, status: open, total: 120.5 }] }
  events: []
  returns: { emitted: 0, unchanged: 1 }

- name: an order whose status changed raises it again
  input: { subject: { kind: company, companyId: co_1 }, lastSucceededAt: "2026-11-02T10:00:00Z", firstRun: false }
  seen:
    - { event: order_changed, key: A-1, data: { number: A-1, status: open, total: 120.5 } }
  http:
    - request:
        method: GET
        url: https://api.example.com/v1/orders?company=co_1&status=open
      response:
        status: 200
        body: { items: [{ number: A-1, status: packed, total: 120.5 }] }
  events:
    - { event: order_changed, key: A-1, data: { number: A-1, status: packed, total: 120.5 } }
  returns: { emitted: 1, unchanged: 0 }
```

`events` wymienia zdarzenia, które uruchomienie musi zgłosić, w kolejności, a `events: []` oznacza, że nie zgłasza żadnego. `seen` to to, co Opero już pamięta na początku przypadku: tutaj zamówienie `A-1` w postaci z ostatniego zgłoszenia. Podczas testów żadne zdarzenie nie trafia do kolejki i żadna reguła się nie uruchamia. Zobacz [Testy](/docs/pl/extensions/reference/tests#events).
</Step>

<Step>
### Przetłumacz [#translate-it]

```yaml title="locales/pl.yaml"
extension:
  name: Zdarzenia zamówień
  description: Zgłasza zdarzenie dla każdego nowego lub zmienionego otwartego zamówienia, sprawdzanego co godzinę w każdej firmie.
permissions:
  network:
    api.example.com: { reason: Odczytuje otwarte zamówienia każdej firmy. }
actions:
  sync_orders:
    label: Synchronizacja zamówień
    description: Odczytuje otwarte zamówienia firmy i zgłasza zdarzenie dla każdego nowego lub zmienionego.
triggers:
  order_changed:
    label: Zmiana zamówienia
    description: Otwarte zamówienie jest nowe albo zmieniła się jedna z jego wartości.
    data:
      number: { label: Numer zamówienia }
      status: { label: Status }
      total: { label: Kwota }
      updatedAt: { label: Zaktualizowano }
    config:
      status: { label: Tylko ten status }
schedules:
  sync_orders:
    label: Synchronizacja otwartych zamówień
    description: Co godzinę odczytuje otwarte zamówienia każdej firmy.
```
</Step>

## Po instalacji [#after-install]

[Zainstaluj plik zip](/docs/pl/extensions/install) jak zwykle. Przegląd pokazuje wyzwalacz z polami danych w sekcji **Co dodaje**, a harmonogram w sekcji **Działa samodzielnie**. Paczka nie ma zakresów danych, więc może ją zainstalować każdy administrator, który może instalować rozszerzenia. W ciągu pierwszej godziny każda firma dostaje pierwsze uruchomienie, a potem jedno na godzinę. Karta **Aktywność** rozszerzenia pokazuje, jak radzi sobie harmonogram; zobacz [Harmonogramy](/docs/pl/extensions/after-install#schedules).

## Reguła, która nasłuchuje [#a-rule-that-listens]

W edytorze reguł otwórz wyzwalacz, kliknij **Zmień wyzwalacz** i wybierz **Zmiana zamówienia** w grupie rozszerzenia w sekcji **Integracje**. Opcjonalnie ustaw **Tylko ten status**, a potem dodaj kroki reguły. Po zapisaniu wyzwalacz reguły wygląda tak:

```json title="Wyzwalacz jednej z reguł organizacji"
{
  "trigger": {
    "type": "x-order-events.order_changed",
    "config": { "status": "packed" }
  }
}
```

Reguła zaczyna się wtedy dla każdego spakowanego zamówienia, które cogodzinne uruchomienie uzna za nowe albo zmienione, w firmie tego zamówienia, i odczytuje je jako `{{ trigger.data.number }}`, `{{ trigger.data.total }}` i tak dalej. Gdy reguła nie ma wcześniejszych uruchomień, przy testowaniu dostaje jako dane przykładowe `example` wyzwalacza.

<Callout type="idea" title="Reguła odporna na dwa uruchomienia">
To samo zamówienie może czasem dotrzeć dwa razy. Zbuduj regułę tak, żeby drugie uruchomienie niczego nie zmieniało: znajdź rekord po `{{ trigger.data.number }}` i zaktualizuj go albo utwórz, gdy go brakuje.
</Callout>

## To samo dla każdego członka [#the-same-for-each-member]

Gdy dane należą do ludzi, a nie do firm, każdy członek łączy własne konto, a harmonogram uruchamia się raz na członka, z jego tokenem. Taką paczkę buduje przewodnik [Dane z konta każdego członka](/docs/pl/extensions/member-accounts).

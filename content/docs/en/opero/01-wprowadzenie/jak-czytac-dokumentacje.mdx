## How to use the documentation

This documentation is **reference material**, not a manual to be read from cover to cover. Every topic is a separate, self-contained whole: any one of them can be opened and understood without reading the previous ones.

To begin, the First steps section is enough. Read the rest when the need arises.

## Documentation sections

The sections follow the order in which the system is learned in practice: first getting around the screens, then working with data, and finally the areas used less often.

## Recurring elements

The same kinds of content recur across topics. It is worth recognizing them, because it speeds up reading.

- **An example** shows a thing in a concrete situation and appears in almost every topic. If a description reads abstractly, skip to the example and come back to the description.
- **A highlight** marks the thing whose omission costs the most: a trap, a boundary, or a principle that is easy to forget.
- **A symptom table** lays out the symptom, the cause, and the fix. It appears in topics where there is something to diagnose, and is then the fastest route to an answer.
- **Related**, at the end of a topic, points to neighboring topics.

The last two elements appear where they make sense, not in every topic.

> **Example.** With an invoice problem, open the invoices topic and first check the symptom table, if the topic has one. This is usually thirty seconds instead of ten minutes of reading the whole thing.

## Names in the documentation are examples

These pages describe the system's capabilities, while an instance is built for the organization's needs. Objects, fields, and stages may be named differently in a given instance than in the examples.

**The principle stays the same.** When the documentation talks about contracts and the same thing is called agreements in a given instance, everything in that topic still applies.

## What the documentation does not cover

- **System configuration.** These pages describe working in the system: what to do, what to expect, what to watch for. Direct the question "how do I set this up" to the person responsible for the system at your company.
- **A step-by-step guide for every screen.** Screens differ between instances, so we describe the principles, not the sequence of clicks.
- **A description of the processes in force in a given instance.** These arise during the implementation and are known to the person running the system at the company.
- **Accounting and tax matters.** Opero runs the document flow, not the settlements.

---
title: Start from your organization
description: "Export an Opero organization's own dictionaries, objects, saved queries, template filters, Custom Blocks, forms, Custom Lists and workspace pages as an extension package folder with opero-ext pull, read what was added and left out, write what the export cannot, then test and install it elsewhere."
---

When your organization already has what a package should bring, you do not have to write it again. `opero-ext pull` exports the organization's own configuration into a new package folder. You then write what only you can write (the description, tests, the reasons of permissions), check it, and install the package in another organization.

## What you need

- The organization's **Extension authoring** module switched on. Without it `pull` stops with exit 4.
- The `org.extensions.create` permission, and the read permission of each kind you export: dictionaries, custom modules (for objects and forms), saved queries, custom scripts (for filters), Custom Blocks, Custom Lists or pages. A missing one is refused with `EXTENSION_PERMISSION_MISSING`, which names it.
- `opero-ext` signed in to your Opero. See [Command-line tool](/docs/en/extensions/reference/cli#signing-in).

## What can be exported

| Select with | Becomes | Notes |
| --- | --- | --- |
| `dictionary:<key>` | `dictionaries/<name>/dictionary.yaml` | With its entries. |
| `object:<moduleKey>.<objectKey>` | `objects/<name>/object.yaml` | Its fields, not its records. Every exported object goes into the package's own module `x-<key>`, whatever module it came from. |
| `query:<key>` | `queries/<name>/query.yaml` and `query.sql` | The SQL's table names become `{{object.<name>}}` placeholders. |
| `filter:<key>` | `filters/<name>/filter.yaml` and its script | The template filter's script key. The script's name stands in for a missing description. |
| `block:<key>` | `blocks/<name>/` with `block.yaml`, its HTML, CSS and script | A block with a script gets `permissions.pageScript` without a reason. |
| `form:<id>` | `forms/<name>/form.yaml` and `layout.yaml` | The form by its id, with its published layout, its types and the default slots it holds. Public forms are not exported. |
| `list:<key>` | `lists/<name>/list.yaml` | Its configuration and its `OPEN_LINK` actions. |
| `page:<slug>` | `pages/<name>/page.yaml` and `layout.yaml` | Workspace pages only. The title and description keep their translations, written to `locales/`. |

Only what the organization made itself is exported: an asset an installed extension manages is left out. Rules are not exported yet. Labels are exported in the language they were written in, except page titles and descriptions; add other [translations](/docs/en/extensions/reference/translations) yourself.

Names are made from the organization's keys in the form each file needs, for example `order_summary` becomes the folder `blocks/order-summary`. When two assets would get the same name, one gets a number and the report says so (`export.name_collision`).

## Export

<Steps>
<Step>
### Run pull

Name a new or empty folder, the package's key, name and publisher, and each asset with `--select`:

```bash title="Terminal"
opero-ext pull ./orders --server https://opero.example.com/mcp --org <organizationId> \
  --key orders --name Orders --publisher "Your company" \
  --select object:sales.orders --select block:order_summary --select page:orders
```

The key is the package's, without the `x-` that Opero adds. `--version` sets the version, by default `0.1.0`. A folder that is not empty is refused (exit 2) unless you pass `--force`, which overwrites only the files the export writes and keeps the others.

Nothing changes in the organization: the export only reads.
</Step>

<Step>
### Read the report

The command prints the files it wrote and three lists. The same lists are in the folder's `README.md`.

**Added, because a selected asset needs them.** You select what you want; the export brings what it depends on:

- an object's select field brings its dictionary, and its reference field the object it points to;
- a query brings the objects whose tables it reads;
- a block brings the queries it runs, the objects of its inputs and record reads, and the blocks it renders;
- a form brings its object, and the blocks, lists, forms and queries its layout names;
- a list brings its object and the form its create button opens;
- a page brings the lists, forms, blocks and queries its layout embeds.

Every reference is renamed for the package: a query reads `{{object.<name>}}` instead of the organization's table, a block renders the package's own block, and a layout or list names the package's assets with [references](/docs/en/extensions/reference/screens#references) such as `{ $ref: "list:open-orders" }`. Each https host a form, list or page opens is added to `permissions.links`. An asset whose name was taken is packaged under another one and listed here too, with `export.name_collision` and its new name.

**Left out.** What a package cannot carry is left out, together with everything that needs it, each with a code and a message:

| Code | Left out because |
| --- | --- |
| `export.managed` | An installed extension manages it. |
| `export.unsupported_kind` | That kind is not exported, for now rules. |
| `export.query_foreign_table` | The query reads a table that is not one of the organization's objects, such as a built-in table, or names a table where the export cannot rewrite it, such as in a string or a comment. |
| `export.object_foreign_reference` | The object names something the package cannot carry: a referenced object or dictionary that is itself left out, an object that is not the organization's, or a row of the organization by id in a field's options. |
| `export.block_reference` | The block names an organization id or key the export cannot rewrite, builds a name with Liquid, or pipes through one of the organization's template filters. |
| `export.block_action` | The block writes through a form, runs a rule by id, or runs another extension's action. |
| `export.not_found` | The selection names nothing of this organization. |
| `export.layout_reference` | A form or page layout, or a list's configuration, names by id what a package cannot carry, such as a report, rule, workflow, calendar or custom field, or a block, list, form or query that is itself left out. |
| `export.list_action` | The list has an action that runs a rule or a script; a package list carries `OPEN_LINK` actions only. |
| `export.list_source` | The list reads an object that is left out. |
| `export.form_public` | The form is public; a package ships no public forms. |
| `export.form_object` | The form's object is left out. |
| `export.page_portal` | The page is a portal page; a package ships workspace pages only. |

**To write before upload.** The export never invents what only the author knows, so these are the problems `validate` would report. Typically:

- `block.test_missing`: every block needs at least one render case in its `tests.yaml`, which the export writes empty;
- `permissions.reason_required`: a block with a script needs your reason for `permissions.pageScript`, and each host in `permissions.links` needs one too;
- the description in `extension.yaml`, which the export writes as a placeholder.
</Step>

<Step>
### Finish the package

Write the description, the reasons and the [tests](/docs/en/extensions/reference/tests), and add translations if you want them. You can now add what the export does not carry, for example [actions](/docs/en/extensions/reference/actions) with `opero-ext add action`.

```bash title="Terminal"
opero-ext validate ./orders
opero-ext test ./orders --server https://opero.example.com/mcp --org <organizationId>
```
</Step>

<Step>
### Install it elsewhere

Plan and install the package in the organization that should get it, as for any package:

```bash title="Terminal"
opero-ext install ./orders --server https://opero.example.com/mcp --org <otherOrganizationId>
```

Installing needs no Extension authoring module. See [Consent](/docs/en/extensions/reference/cli#consent).

<Callout title="The original stays the organization's own">
Exporting does not turn the organization's assets into managed ones. Installing the package in the same organization creates new assets under the extension's names (`x-orders`, `x_orders_…`) next to the originals.
</Callout>
</Step>
</Steps>

## Without the command line

The export is also the MCP tool `extensions_export` and the API route `POST /v1/organizations/:orgId/extensions/export`. Both take the key, name, publisher, an optional version and a selection of 1 to 200 references, and answer the files with the same added, left-out and to-write lists. They write nothing and need the same module and permissions. An AI assistant connected to Opero's MCP server uses them for you, and plans and installs packages with `extensions_plan` and `extensions_install`, showing you the plan before it installs.

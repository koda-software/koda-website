An extension is a folder of YAML files and scripts that you check and pack with a command-line tool, then upload to an organization. This page lists what you need for each half of that work.

## To build

| You need | Why |
| --- | --- |
| The command-line tool | `opero-ext` scaffolds a package, checks it, packs the zip and uploads it. See [Install the command-line tool](#install-the-command-line-tool). |
| An editor with YAML support | Optional. The folder `init` writes tells VS Code (with the YAML extension) which schema each file follows, so keys complete as you type. |
| The service's API documentation | The exact URLs, how the service authenticates and what it answers. |
| A test credential for that service | Only for the final live check. The package's own tests do not need it. |
| The **Extension authoring** module | Only for `opero-ext test` (the tests on Opero) and `opero-ext pull` (export). Uploading and installing do not need it. |

## To install

| You need | Why |
| --- | --- |
| An administrator account | Uploading and installing need the `org.extensions.*` permissions and the permissions to create what the package brings. The built-in administrator role has them all; [Install an extension](/docs/en/extensions/install#before-you-start) lists them. |
| The Rules module | Extensions install rules. A package with objects also needs Objects, one with queries the Queries module, one that generates documents the Documents module. |
| The organization owner role | Only for a package that declares [data scopes](/docs/en/extensions/reference/data-permissions). |

## Install the command-line tool

`opero-ext` is one executable with Node.js inside. It needs no administrator rights.

<Tabs items={['Linux, macOS', 'Windows']}>
<Tab value="Linux, macOS">

```bash title="Terminal"
curl -fsSL https://hub.kodasoft.pl/extension-cli/install.sh | sh
```

</Tab>
<Tab value="Windows">

```powershell title="PowerShell"
irm https://hub.kodasoft.pl/extension-cli/install.ps1 | iex
```

</Tab>
</Tabs>

Check it with `opero-ext version`, which prints the version and the platform. Keep it current with `opero-ext update`, which checks the release's signature. [Command-line tool](/docs/en/extensions/reference/cli#install) lists the platforms and what to do when a browser download is blocked.

<Callout title="Licence">
**Extension authoring** is a separate licensed module, off by default. Without it, `opero-ext test` and `opero-ext pull` stop with exit 4; everything else works. An administrator switches it on in the organization's modules when the licence includes it.
</Callout>

## Know the rule builder first

A rule file is a rule written as text, so it helps to have built one rule in Opero with a **Call webhook** step. Read [Rules](/docs/en/opero/07-automatyzacja/reguly-wprowadzenie) and [Actions](/docs/en/opero/07-automatyzacja/akcje) if you have not.

## Choose the right tool for the job

An extension is not always the lightest answer.

| You want to | Use |
| --- | --- |
| Convert or format a single value in templates | A [template filter](/docs/en/extensions/reference/filters) in an extension, or a custom script if only your organization needs it. |
| Run a bit of logic in one rule only | A **Run script** step written directly in that rule. No extension needed. |
| Give many rules, or many organizations, one clean step that calls a service | An extension with a [connection](/docs/en/extensions/reference/connection-and-secrets) and actions. |
| React to something that happens in the outside service | An extension with a [trigger](/docs/en/extensions/reference/triggers) and a [schedule](/docs/en/extensions/reference/schedules) that reads the service and raises an event for what changed. |
| Work with each member's own account at a service | An extension with a [member connection](/docs/en/extensions/reference/member-connections). |
| Bring dictionaries, objects, queries, filters or blocks you already built in one organization to others | An extension [exported from that organization](/docs/en/extensions/start-from-your-organization). |

## What an extension cannot do yet

| You cannot | Do this instead |
| --- | --- |
| Reach the organization's own objects | A package reads and writes only its own objects and contractors. The rule that uses your step does other record work with the result. |
| Place anything in a menu | An administrator adds the package's pages to a menu. |
| Bring forms for objects that are not its own, public forms, portal pages, or list actions that run a rule or a script | Build them in the organization. |
| Send from a mailbox, or bring email and document templates | Email goes through the installation's email service; documents use a template the organization picks. |
| Receive webhooks | Read the service on a [schedule](/docs/en/extensions/reference/schedules). Incoming webhooks are planned. |
| Raise events from a step | Raise them from a schedule run or a member connection hook. |
| Run on a cron expression, or at an interval the administrator picks | Choose one of the seven fixed intervals of a schedule. |
| Renew a member's token | The member connects again when the service stops accepting it. |
| Bring images, fonts or other files for its blocks | Use images the service hosts. |
| Use form actions in its blocks (`open-form`, `set-field`, `<opero-rating>`), or run a rule by id | Block buttons run the package's own actions. |
| Raise events or use a member's connection from a block action or a record command, or run a command in the background | Use a schedule for background work. |
| Offer block actions, commands and links to API tokens, the external API or MCP | Members use them in the app. |
| Call a host it did not declare, or anything that is not HTTPS | Declare every host under `permissions.network`. |

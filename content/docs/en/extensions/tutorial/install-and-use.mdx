---
title: "Part 4: Install and use"
description: "Upload and install the Hello extension, connect it to httpbin.org, use its Greet step in a rule, run the rule and ship a new version."
---

In this part you install the zip from Part 3 in an organization and use its step. At the end a rule of yours calls httpbin.org through Hello, and Hello runs a second version.

<Steps>
<Step>
### Upload the zip

In the organization's administration, open **Integrations** → **Extensions**, press **Upload package** and choose `hello-ext-0.1.0.zip`. Opero checks the package and runs its five tests before it stores anything.

![The upload dialog after the check: ready to upload, every contract test passed](/docs/_assets/extensions/install/upload-checked.webp)

Press **Upload and review**. When the check finds problems instead, fix them, pack again and choose the new zip.
</Step>

<Step>
### Install it

The review shows what Hello adds and that it calls `httpbin.org`, with your reason. [The install review](/docs/en/extensions/install#the-install-review) explains each part.

![The install review: what it adds, what it can reach and what to do after installing](/docs/_assets/extensions/install/review-dialog.webp)

Press **Install**. Hello is now **Inactive**, because installing never sets up a connection.
</Step>

<Step>
### Check the setting

Open the **Configuration** tab. The **General** section from `settings.yaml` shows **Language** at its default, `en`.

![Hello's settings: the language used for greetings](/docs/_assets/extensions/tutorial/hello-settings.webp)

Choose `pl` and press **Save changes** if you want greetings sent with `lang=pl`.
</Step>

<Step>
### Set up the connection

In the **Connection** section, enter any text as the **API token** (httpbin.org accepts every token) and press **Create**. Press **Test connection**, which runs your `verify` action, then **Activate**.

![Hello's connection after a successful test, ready to activate](/docs/_assets/extensions/tutorial/hello-connection.webp)

Hello is now **Running**. [Run an installed extension](/docs/en/extensions/after-install#configuration) covers the rest of this tab.
</Step>

<Step>
### Add the step to a rule

Open **Configuration** → **Rules**, press **Create**, name the rule and press **Create**. Under **Pipeline**, press **Add Step**: **Greet** is under **Hello** in the **Integrations** group.

![The step list with Hello's Greet step in the extension's own group](/docs/_assets/extensions/tutorial/step-picker.webp)

The **Hello** step declared `category: data`, so it is under **Data**. Searching for "hello" finds both.
</Step>

<Step>
### Fill in the step

The form comes from the action's input. Set **Name** to `{{ trigger.user.firstName }}`, press **Done**, then **Save changes**.

![The Greet step's form, generated from the action's input](/docs/_assets/extensions/tutorial/greet-step.webp)

The step saves its result as `greet`, so later steps read `{{ greet.status }}` and `{{ greet.body.json.greeting }}`.
</Step>

<Step>
### Run the rule

Press **Run**, open the menu next to **Dry run** and choose **Execute rule**. **Execution Result** shows **Success**, and the Greet step's state holds httpbin.org's answer.

A **Dry run** shows what the rule would do without calling the service. If the action fails, the step fails; see [When a step fails](/docs/en/extensions/reference/actions#when-a-step-fails).
</Step>

<Step>
### Describe it for the catalog

The extension's **Overview** still shows the placeholder text that `init` wrote. Replace `listing/description.md`; it is Markdown, and the [listing](/docs/en/extensions/reference/listing) explains what it may hold.

```md title="listing/description.md"
# Hello

Hello is the extension the Opero tutorial builds. It adds two rule steps and a
template filter:

- **Greet** sends a greeting for a name to httpbin.org and returns its answer.
- **Hello** builds a greeting without calling anything.
- `x_hello_ext_shout` upper-cases a text in any template.

Connect it with any token: httpbin.org accepts every one.
```
</Step>

<Step>
### Ship a new version

Raise `version` in `extension.yaml` to `0.1.1`, and say what changed at the top of the changelog:

```md title="listing/changelog.md"
## 0.1.1

- A real description for the catalog.

## 0.1.0

- First version.
```

Run `opero-ext validate .` and `opero-ext pack .`:

```txt title="Output"
hello-ext 0.1.1 is valid.
Wrote …/hello-ext-0.1.1.zip (5731 bytes; listing images 1325 bytes)
```

Upload the new zip and press **Upload and review**. The review is now **Upgrade Hello**, with **New in this version** from your changelog; press **Upgrade**. The connection and the rule keep working, because the step keeps its name.
</Step>
</Steps>

## Other ways to upload

<Tabs items={['Command-line tool', 'AI assistant']}>
<Tab value="Command-line tool">

```bash title="Terminal"
opero-ext push . --server https://opero.example.com/mcp
```

`opero-ext install .` uploads, prints the review, asks for your consent and installs; `opero-ext upgrade .` does the same for a new version. See [Consent](/docs/en/extensions/reference/cli#consent).

</Tab>
<Tab value="AI assistant">

An AI assistant connected to Opero's MCP server can upload the zip, review it, install it and upgrade it. It must show you the review first and install only once you agree.

</Tab>
</Tabs>

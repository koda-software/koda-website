In this part you scaffold the `hello-ext` package and read what the tool wrote. At the end you have a valid package with one step that builds a greeting.

The tutorial builds `hello-ext` against [httpbin.org](https://httpbin.org), a public service that echoes requests back. Every file shown is the complete file as the finished package holds it.

| Part | What you do |
| --- | --- |
| 1. Start the package | Scaffold with `init` and read what it wrote. |
| 2. [Call a service](/docs/en/extensions/tutorial/call-a-service) | Add a connection, a setting, a step that calls httpbin.org, a filter and a translation. |
| 3. [Check and pack](/docs/en/extensions/tutorial/check-and-pack) | Validate, pack the zip and run the tests on Opero. |
| 4. [Install and use](/docs/en/extensions/tutorial/install-and-use) | Upload, install, connect, use the step in a rule and ship a new version. |

<Steps>
<Step>
### Create the folder

Let the command-line tool write a working package. The folder name gives the extension its key; `--key` chooses another.

```bash title="Terminal"
opero-ext init hello-ext --name Hello
```

```txt title="Output"
  extension.yaml
  actions/hello/action.yaml
  actions/hello/tests.yaml
  actions/hello/run.js
  listing/description.md
  listing/changelog.md
  listing/icon.png
  README.md
  .gitignore
  jsconfig.json
  .vscode/settings.json
Wrote 11 files in …/hello-ext.
```

Only what `extension.yaml` reaches goes into the zip, plus the `listing/` folder that the catalog shows. `README.md`, `.gitignore`, `jsconfig.json` and `.vscode/` are for you and your editor.
</Step>

<Step>
### Describe the package

`extension.yaml`, the manifest, holds the package's identity and lists every part it installs. Replace the placeholder description:

```yaml title="extension.yaml"
# The package's contents: every feature it installs is listed here.
manifestVersion: 2
extension: hello-ext
version: 0.1.0
name: Hello
description: A starter extension with a greeting, a call to httpbin.org and a filter. # [!code highlight]
publisher: Your company
requires:
  modules: [rules]

actions:
  - actions/hello

# What the catalog shows is under listing/: icon.png, description.md and
# changelog.md. Screenshots are listed here, in order, with their captions:
# listing:
#   screenshots:
#     - file: listing/screenshots/main.png
#       caption: The main screen
```

| Key | What it is |
| --- | --- |
| `extension` | The key that names everything the extension adds. An organization cannot install two extensions whose keys overlap, such as `order` and `order-sync`. |
| `version` | Three numbers. Each upload needs a new one. |
| `name`, `description` | What the extension list shows, in English. Part 2 translates them. |
| `actions` | The action folders. A folder that is not listed is not part of the package. |

Every key is in [extension.yaml](/docs/en/extensions/reference/manifest); the catalog files are in [The listing](/docs/en/extensions/reference/listing).
</Step>

<Step>
### Describe the action

An action is one operation, here exposed as a rule step. Replace the placeholder description in `action.yaml`:

```yaml title="actions/hello/action.yaml"
action: hello
label: Hello
description: Builds a greeting for a name. # [!code highlight]

input:
  name: { type: text, label: Name, required: true }
output:
  greeting: { type: text, label: Greeting }

run: run.js
tests: tests.yaml

expose:
  ruleStep: { category: data }
```

| Key | What it is |
| --- | --- |
| `action` | The action's name. The folder name does not matter. |
| `input`, `output` | [Field lists](/docs/en/extensions/reference/actions#field-lists). The input becomes the step's form in the rule builder. |
| `run` | The logic: a script, or a rule file as in Part 2. |
| `expose.ruleStep` | Publishes the action as the step `x-hello-ext.hello`, listed under the `data` category. |

See [Actions and field lists](/docs/en/extensions/reference/actions) for every key.
</Step>

<Step>
### Read the script

The script exports one function. It receives the input and returns the action's output.

<Tabs items={['JavaScript', 'TypeScript']}>
<Tab value="JavaScript">

```js title="actions/hello/run.js"
/** @type {import('../../.opero/types').Action<'hello'>} */
const run = ({ input }) => {
  return { greeting: 'Hello, ' + input.name + '!' };
};
export default run;
```

The first-line comment types the function from `action.yaml`, so your editor completes `input.name`.

</Tab>
<Tab value="TypeScript">

```ts title="actions/hello/run.ts"
import type { Action } from '../../.opero/types';

const run: Action<'hello'> = ({ input }) => {
  return { greeting: 'Hello, ' + input.name + '!' };
};
export default run;
```

Scaffold with `--typescript` to get `run.ts`. The tool removes the types when it packs, so the zip carries a `run.js`.

</Tab>
</Tabs>

The argument also holds `settings`, `company`, `user` and `context`; see [Scripts](/docs/en/extensions/reference/scripts).
</Step>

<Step>
### Read the test

A test case gives an input and the exact output expected. Opero runs it at every upload.

```yaml title="actions/hello/tests.yaml"
- name: a name gets a greeting
  input:
    name: Ada
  returns:
    greeting: Hello, Ada!
```
</Step>

<Step>
### Validate

The check works offline and takes a moment, so run it after every edit. It also writes `.opero/`, the types and schemas your editor uses.

```bash title="Terminal"
opero-ext validate hello-ext
```

```txt title="Output"
hello-ext 0.1.0 is valid.
```
</Step>
</Steps>

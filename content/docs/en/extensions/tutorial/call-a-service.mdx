title: "Part 2: Call a service"
description: "Give the Hello extension a token connection, a language setting, a connection check, a step that calls httpbin.org, a filter and a Polish translation."
---

In this part the package learns to call httpbin.org with a secret token. At the end it has a connection, a setting, a check of the token, the `greet` step, the `shout` filter and a Polish translation.

<Steps>
<Step>
### Add two actions and a filter

Run these from inside the package folder. Each command writes a working example and adds its line to `extension.yaml`; `--rule` starts the action from a rule file.

```bash title="Terminal"
cd hello-ext
opero-ext add action verify --rule
opero-ext add action greet --rule
opero-ext add filter shout
```

```txt title="Output of the first command"
  actions/verify/action.yaml
  actions/verify/tests.yaml
  actions/verify/rule.yaml
  actions/verify/step.js
  extension.yaml
Wrote 5 files in …/hello-ext.
```

You replace the examples in the next steps. Delete `actions/verify/step.js` and `actions/greet/step.js`, which the rules below do not use.
</Step>

<Step>
### Describe the connection

The connection is the form where the administrator enters the service's credentials. Create `connection/connection.yaml`:

```yaml title="connection/connection.yaml"
methods:
  - method: token
    kind: api_token
    label: API token
    fields:
      token: { type: text, label: API token, required: true, hint: true }
verify: verify
```

Every field of a method is secret; `hint: true` lets Opero show the last four characters of the saved token. `verify` names the action that **Test connection** runs. See [Connection and secrets](/docs/en/extensions/reference/connection-and-secrets).
</Step>

<Step>
### Add a setting

The greeting's language is not secret, so it is a setting, not part of the connection. Create `settings.yaml`:

```yaml title="settings.yaml"
groups:
  - group: general
    label: General
    description: How the greetings are sent.
    fields:
      language: { type: select, label: Language, options: [en, pl], default: en }
```

Each group is a section of the settings form. With `default: en` the extension runs before anyone opens the form; see [Settings](/docs/en/extensions/reference/settings).
</Step>

<Step>
### Write the check

The check is an action that nothing publishes as a step. It takes no input and returns what the service answers.

```yaml title="actions/verify/action.yaml"
# The connection check: connection.yaml names it. It exposes nothing.
action: verify
label: Verify
description: Checks the connection's token with httpbin.org.

run: rule.yaml
tests: tests.yaml
```

Its logic is a [rule file](/docs/en/extensions/reference/rule-files): the steps and edges the rule builder saves, with step ids you choose.

```yaml title="actions/verify/rule.yaml"
# The rule-save graph; the reader supplies its name and MANUAL trigger.
entryStepId: call
steps:
  - id: call
    type: CALL_WEBHOOK
    name: Check token
    contextKey: output
    config:
      url: https://httpbin.org/bearer
      method: GET
      headers: { Authorization: "Bearer {{ connection.token }}" } # [!code highlight]
edges: []
```

`{{ connection.token }}` is the secret: Opero puts in the real value only while it sends the request. Whatever the rule leaves under `output` is the action's result, and an error status fails the check.
</Step>

<Step>
### Test the check

A test case lists the requests the action makes, the answer to give each, and how the case ends. Opero runs every case at upload without sending anything.

```yaml title="actions/verify/tests.yaml"
- name: a valid token is accepted
  connection: { token: test-token }
  http:
    - request:
        method: GET
        url: https://httpbin.org/bearer
        headers: { authorization: Bearer test-token }
      response: { status: 200, body: { authenticated: true, token: test-token } }
  succeeds: true

- name: a refused token fails
  connection: { token: wrong-token }
  http:
    - request: { method: GET, url: https://httpbin.org/bearer }
      response: { status: 401 }
  fails: { status: 401 }
```

`connection` gives the case's credential values. Only the headers you name are compared, in lower case; see [Tests](/docs/en/extensions/reference/tests).
</Step>

<Step>
### Write the greet step

This is the step rule authors use. It takes a name and posts a greeting.

```yaml title="actions/greet/action.yaml"
action: greet
label: Greet
description: Sends a greeting for a name to httpbin.org and returns its answer.

input:
  name: { type: text, label: Name, required: true }
output:
  status: { type: integer, label: HTTP status }
  body: { type: object, label: Answer, fields: {} }

run: rule.yaml
tests: tests.yaml

expose:
  ruleStep: { category: integrations }
```

```yaml title="actions/greet/rule.yaml"
# The rule-save graph; the reader supplies its name and MANUAL trigger.
entryStepId: call
steps:
  - id: call
    type: CALL_WEBHOOK
    name: Greet
    contextKey: output
    config:
      url: "https://httpbin.org/anything?lang={{ trigger.settings.language }}"
      method: POST
      headers: { Authorization: "Bearer {{ connection.token }}" }
      body: { greeting: "Hello, {{ trigger.data.name }}!" }
edges: []
```

| Write | To get |
| --- | --- |
| `{{ trigger.data.name }}` | A field of the action's input. |
| `{{ trigger.settings.language }}` | A setting, with its default applied. |
| `{{ connection.token }}` | A secret field. Only in a header value or a URL query value of a **Call webhook** step. |
</Step>

<Step>
### Test the greet step

The first case proves the request carries the setting, the token and the name. The second proves a `429` is reported as rate limiting, so the calling rule can wait and retry.

```yaml title="actions/greet/tests.yaml"
- name: the greeting is sent
  input: { name: Ada }
  settings: { language: pl }
  connection: { token: test-token }
  http:
    - request:
        method: POST
        url: https://httpbin.org/anything?lang=pl
        headers: { authorization: Bearer test-token }
        body: { greeting: "Hello, Ada!" }
      response:
        status: 200
        headers: { content-type: application/json }
        body: { json: { greeting: "Hello, Ada!" } }
  returns:
    status: 200
    headers: { content-type: application/json }
    body: { json: { greeting: "Hello, Ada!" } }

- name: a 429 is reported as rate limited
  input: { name: Ada }
  connection: { token: test-token }
  http:
    - request: { method: POST, url: https://httpbin.org/anything?lang=en }
      response: { status: 429, headers: { retry-after: "30" } }
  rateLimited: { status: 429 }
```

The second case gives no `settings`, so the language is the default, `en`.
</Step>

<Step>
### Write the filter

A filter's function receives the value piped into it and returns at once; it may not be `async`.

```yaml title="filters/shout/filter.yaml"
filter: shout
description: Upper-cases a text and adds an exclamation mark.
script: filter.js
```

```js title="filters/shout/filter.js"
/** @type {import('../../.opero/types').Filter} */
const filter = (value) => String(value ?? '').toUpperCase() + '!';
export default filter;
```

After install, any template can write `{{ "hi" | x_hello_ext_shout }}` and get `HI!`. See [Template filters](/docs/en/extensions/reference/filters).
</Step>

<Step>
### Translate

English is written in the descriptors; each other language is one file. Leave out what you do not translate, and it shows in English.

```yaml title="locales/pl.yaml"
extension:
  name: Hello
  description: Rozszerzenie startowe z powitaniem, wywołaniem httpbin.org i filtrem.
permissions:
  network:
    httpbin.org: { reason: Sprawdza token i wysyła powitania do testowej usługi httpbin.org. }
connection:
  methods:
    token:
      label: Token API
      fields: { token: { label: Token API } }
settings:
  groups:
    general:
      label: Ogólne
      description: Jak wysyłane są powitania.
  fields:
    language: { label: Język }
actions:
  hello:
    label: Powitanie
    description: Tworzy powitanie dla imienia.
    input: { name: { label: Imię } }
    output: { greeting: { label: Powitanie } }
  greet:
    label: Pozdrów
    description: Wysyła powitanie dla imienia do httpbin.org i zwraca jego odpowiedź.
    input: { name: { label: Imię } }
filters:
  shout: { description: Zamienia tekst na wielkie litery i dodaje wykrzyknik. }
```

A key that names nothing in the package is refused, so a typo cannot hide. See [Translations](/docs/en/extensions/reference/translations).
</Step>

<Step>
### List the new parts in extension.yaml

The `add` commands already listed the actions and the filter. Add the host the package calls with your reason, the connection, the settings and the language:

```yaml title="extension.yaml"
# The package's contents: every feature it installs is listed here.
manifestVersion: 2
extension: hello-ext
version: 0.1.0
name: Hello
description: A starter extension with a greeting, a call to httpbin.org and a filter.
publisher: Your company
requires:
  modules: [rules]
permissions: # [!code ++]
  network: # [!code ++]
    - host: httpbin.org # [!code ++]
      reason: Checks the token and sends greetings to the httpbin.org test service. # [!code ++]
connection: connection # [!code ++]
settings: settings.yaml # [!code ++]

actions:
  - actions/hello
  - actions/verify
  - actions/greet
filters:
  - filters/shout

locales: [pl] # [!code ++]

# What the catalog shows is under listing/: icon.png, description.md and
# changelog.md. Screenshots are listed here, in order, with their captions:
# listing:
#   screenshots:
#     - file: listing/screenshots/main.png
#       caption: The main screen
```

The administrator sees each host with its reason before installing. A call to any other host is refused, and so is a permission without a reason.
</Step>
</Steps>

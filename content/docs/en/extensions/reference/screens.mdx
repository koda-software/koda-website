A package can bring the screens members work with: **forms** on its own objects, **Custom Lists** that list records, and **workspace pages** that put lists, forms, blocks and counters together. They are installed as the organization's Dynamic Forms, Custom Lists and Custom Pages, managed by the extension. The guide [Forms, lists and pages](/docs/en/extensions/workspace-screens) builds all three.

```yaml title="extension.yaml"
  - blocks/order-summary

  - pages/orders

```

List the folders under `forms`, `lists` and `pages` in `extension.yaml` or an included module's `module.yaml`. `opero-ext add form <name> --object <object>`, `add list <name> [--object <object>]` and `add page <name>` write a starting folder and list it; see [Command-line tool](/docs/en/extensions/reference/cli#options).

## form.yaml

A form is a Dynamic Form on one of the package's own [objects](/docs/en/extensions/reference/objects): the screen that opens, edits or creates its records. A package has at most 100 forms.

```yaml title="forms/order/form.yaml"
form: order                      # referenced as orders.order
object: orders
name: Order
types: [view, edit, create]
default: [view, edit, create]    # claims the object's slots when they are empty
config:
  title: New order
  successMessage: Saved
layout: layout.yaml
```

`config` takes only these keys. A package form is never public.

The layout is a View Layout document, as the form editor saves it. Field nodes name the object's field keys; the package's blocks, lists, forms and queries are named with [references](#references):

```yaml title="forms/order/layout.yaml"
schemaVersion: 2
regions:
  main:
    - id: details
      kind: card
      children:
        - { id: f_title, kind: field, field: { source: dynamic, key: title } }
        - { id: f_status, kind: field, field: { source: dynamic, key: status } }
    - id: summary
      kind: component
      component: custom_block
      config:
        customBlockId: { $ref: "block:order_summary" }
        inputs: { title: "Order {{ record.title }}" }
    - id: lines
      kind: component
      component: layout.customList
      config:
        customListId: { $ref: "list:order-lines" }
        params: { order: "{{ record.id }}" }
```

### Default forms

Each object has a default form for viewing, editing and creating its records. A form with `default` takes each slot it names when the slot is empty or held by a form of this extension. A slot the organization filled with its own form is kept, and the install review says so (`form.default_taken`, not blocking). An upgrade and a reinstall do the same: they never take over a default the organization chose.

## list.yaml

A list is a Custom List over one of the package's objects or over a built-in list source. Members see it where a page or a form embeds it. A package has at most 50 lists.

```yaml title="lists/open-orders/list.yaml"
list: open-orders                # installed as x-shop-open-orders
name: Open orders
description: Orders that are not closed yet.
source: { object: orders }
config:
  columns: [{ field: title }, { field: status }]
  baseFilter:
    op: AND
    items: [{ field: status, operator: neq, value: closed }]
  modes: [table]
  views: [{ id: default, name: Default, default: true, config: { schemaVersion: 2 } }]
  builtInActions: [create, open]
  create: { formId: { $ref: "form:orders.order" } }
actions:
  - key: open_in_shop
    type: OPEN_LINK
    label: Open in shop
    config: { url: "https://shop.example.test/orders/{{ row.external_id }}" }
```

A list over a built-in source lists records of that source, for example contractors:

```yaml title="lists/suppliers/list.yaml"
list: suppliers
name: Suppliers
source: { builtIn: contractors }
config:
  columns: [{ field: fullName }]
  modes: [table]
  views: [{ id: default, name: Default, default: true, config: { schemaVersion: 2 } }]
```

The reader checks the shape and the references. Whether the configuration fits its source (its columns, filters and create form) is checked by Opero as the list's own save would: in the install review (`list.save_validation`), or, for a list over an object the same install creates, when the list is installed.

### Actions

A packaged list carries only `OPEN_LINK` actions, which open an address for a row. A rule or script action is refused with `list.action_unsupported`: their ids cannot travel with a package.

| Key | Meaning |
| --- | --- |
| `key` | A lower-case letter, then lower-case letters, digits and `_`, up to 80 characters. Unique in the list. |
| `label` | Up to 160 characters. |
| `type` | `OPEN_LINK`. |
| `isActive` | Optional. |
| `config.url` | A path, or an https address on a host of `permissions.links`, with Liquid over `row`. See [URLs](#urls). |
| `config.openIn` | `same_tab` or `new_tab`. `new_tab` when left out. |
| `config.isDefault` | Optional. Show the action as the row's shortcut beside its actions menu. |

## page.yaml

A page is a workspace Custom Page: a screen of its own that members open from a menu. A package has at most 50 pages, and places none in a menu itself.

![The Shop workspace page: the open orders counter, the list, a summary block and the new order form](/docs/_assets/extensions/workspace-screens/shop-page.webp)

```yaml title="pages/orders/page.yaml"
page: orders                     # installed with the slug x-shop-orders
title: Orders
description: Open orders and how many there are.
surface: workspace
layout: layout.yaml
```

## References

A screen never names something by id, because ids differ in every organization. It names the package's own blocks, lists, forms and queries with a reference, which Opero replaces with the installed id:

```yaml
customListId: { $ref: "list:open-orders" }
```

| Kind | Names | Example |
| --- | --- | --- |
| `block` | A [block](/docs/en/extensions/reference/blocks) by its `block` name. | `{ $ref: "block:order_summary" }` |
| `list` | A list by its `list` name. | `{ $ref: "list:open-orders" }` |
| `form` | A form as `<object>.<form>`. | `{ $ref: "form:orders.order" }` |
| `query` | A [query](/docs/en/extensions/reference/queries) by its `query` name. | `{ $ref: "query:open_count" }` |

A reference may stand only where Opero stores an id of its kind:

| Where | Kind |
| --- | --- |
| `config.customBlockId` of a `custom_block` component | `block` |
| `config.customListId` of a `layout.customList` component | `list` |
| `config.formId` of a `page.form` component | `form` |
| `config.savedQueryId` of a `counter` or `page.counter` component | `query` |
| `owned.rowForms.<operation>` of a `field` or `relationTable` node | `form` |
| `config.create.formId` of a list | `form` |

A reference anywhere else, a reference that is not exactly `{ $ref: "<kind>:<name>" }`, a name the package does not have, and any other key that holds an id (a rule, report, workflow, calendar, SQL list or custom field: every key ending in `Id` or `Ids`) are refused; see [Problems](#problems). Leave such a key out, or empty.

Field keys and relation keys are written as they are: they are the same in every organization that installs the package.

## URLs

A `url` in a layout, a list action's `config.url` and a form's `config.redirectUrl` must be either a path of Opero, starting with `/`, or an https address whose host is written out and listed in [`permissions.links`](/docs/en/extensions/reference/manifest#link-hosts-page-scripts-and-company-permissions). Liquid may fill in the path, never the host. Anything else is refused with `layout.host_not_declared`. A host the screens open counts as used, so it needs no record link.

## Translations

A page's `title` and `description` go under `pages.<page>`, and a form's `config.title` and `successMessage` under `forms.<object>.<form>.config`; the form is installed with its English texts. Form and list names, column labels and action labels are English only. See [Translations](/docs/en/extensions/reference/translations#translatable-keys).

## Reserved names

The organization cannot create a Custom List whose key starts with `x-`, or create or rename a page to a slug that starts with `x-`, so these keys can only be an extension's. The screens are read-only and change only with an upgrade; who may use each form, the object's default forms, a page's exposure and audience, and menus stay the organization's. See [Managed assets](/docs/en/extensions/after-install#managed-assets) and, for who sees the screens after install, [After install](/docs/en/extensions/workspace-screens#after-install).

## Upgrades

| Change in a new version | What happens | Code |
| --- | --- | --- |
| A form or page layout changes | It is published as a new version. | |
| A list changes | It is saved over the old one. | |
| A form claims a default slot the organization filled | The organization's form keeps the slot. A warning. | `form.default_taken` |
| A form the organization's layouts, lists or blocks name is dropped | The form is deleted; its default slots go to another form of the extension of the same type, or stay empty. A warning. | `form.in_use` |
| The last form of a type of an object is dropped | Members cannot open or create its records until an administrator builds a form. A warning. | `object.formless` |
| A list the organization's layouts embed is dropped | It is archived, and the embeds show that the extension removed it. A warning. | `list.in_use` |
| A page the organization's menus open is dropped | It is archived, and the menu items are hidden. A warning. | `page.in_use` |

An uninstall deletes the forms and archives the lists and pages; installing again revives the lists and pages under the same ids. What the administrator sees is in [Upgrade and uninstall](/docs/en/extensions/upgrade-and-uninstall#what-a-new-version-can-change).

## Problems

| Code | Cause | Fix |
| --- | --- | --- |
| `form.invalid` | An unknown key, a key of the wrong shape, no `types`, a `default` slot that is not one of its types, a layout that is not a `.yaml` file of the folder with `schemaVersion: 2` and `regions`, or more than 100 forms. | Fix the key the message names. |
| `form.unknown_object` | `object` names no object of the package. | Fix the key, or add the object. |
| `list.invalid` | An unknown key, a key of the wrong shape, a `builtIn: dynamicObject` source, or more than 50 lists. | Fix the key; write `source: { object: <key> }` for an object. |
| `list.unknown_object` | `source.object` names no object of the package. | Fix the key, or add the object. |
| `list.name_too_long` | The installed key `x-<key>-<list>` is over 64 characters. | Shorten the list's name. |
| `list.action_unsupported` | A list action that is not `OPEN_LINK`. | Open a link, or move the work to a block action. |
| `page.invalid` | An unknown key, a key of the wrong shape, a layout that is not a `.yaml` file of the folder with `schemaVersion: 2` and `regions`, or more than 50 pages. | Fix the key the message names. |
| `layout.ref_invalid` | A reference that is not exactly `{ $ref: "<kind>:<name>" }`. | Write it in that form. |
| `layout.ref_position` | A reference outside the places in the table, or of the wrong kind for its place. | Move it, or use the kind its place takes. |
| `layout.ref_unknown` | A reference names something the package does not have. | Fix the name. |
| `layout.reference_unsupported` | A key that holds an id the package cannot carry, or an id where a reference belongs. | Leave the key out, or use a reference. |
| `layout.host_not_declared` | A URL that is neither an Opero path nor an https address on a host of `permissions.links`. | Add the host with a reason, or use a path. |
| `form.save_validation`, `layout.save_validation`, `list.save_validation` | In the install review: a form, a layout or a list would not save as its editor saves it. Blocks the install. | Fix it as the message says. |

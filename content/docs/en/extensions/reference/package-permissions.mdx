---
title: Package permissions
description: Decide who may use the package's block actions, record commands and links with company permissions declared in permissions.company.
---

A package decides who may use its block actions, record commands and record links by asking for its own **company permissions**. Each one becomes an ordinary company permission, `company.x-<key>.<name>`, that the organization grants in its [roles](/docs/en/opero/11-konto-i-dostep/role-i-uprawnienia) like any other. The guide [A block, a button and a link](/docs/en/extensions/blocks-and-actions) declares two.

```yaml title="extension.yaml"
permissions:
  company:
    track:
      label: Track parcels
      description: Ask the carrier where a parcel is, from its page or its card.
      reason: Each question counts against the organization's carrier quota.
    openTracking:
      label: Open tracking pages
      description: Open a parcel's tracking page at the carrier.
      reason: The link sends the parcel number to the carrier's site.
```

Each permission is named by at least one `expose.blockAction`, `expose.recordCommand` or link `permission`.

## In the organization

While the extension runs, the role editor lists the permissions in a group named after the package, with your labels in the member's language:

![A company role's permissions filtered by parcel, with Track parcels ticked](/docs/_assets/extensions/blocks-and-actions/role-permissions.webp)

| Rule | Detail |
| --- | --- |
| Granted by the organization | Installing adds a package permission to no role. Only a role that grants every permission holds them from the start. |
| Not for API tokens | API tokens never receive package permissions, and block actions, record commands and links are not offered to them. |
| The last of four checks | A member passes the other three first: see [Who may use them](/docs/en/extensions/reference/member-actions#who-may-use-them). |
| While the extension is disabled | Roles keep their grants; the group leaves the role editor until the extension runs again. |

## Upgrades

| Change in a new version | What happens | Code |
| --- | --- | --- |
| A permission is added | It is shown as new in the review, for the administrator to agree to. | |
| A permission is removed | It is removed from every role. When roles grant it, a warning says how many. | `permission.grants_removed` |

An uninstall removes every grant of the extension's permissions. What the administrator sees is in [Upgrade and uninstall](/docs/en/extensions/upgrade-and-uninstall#what-a-new-version-can-change).

## Translations

The texts go under `permissions.company.<name>`: `label`, `description` and `reason`. See [Translations](/docs/en/extensions/reference/translations#translatable-keys).

## Problems

| Code | Cause | Fix |
| --- | --- | --- |
| `permissions.reason_required` | A permission without a reason. | Add one sentence. |
| `permissions.unused_company_permission` | A permission no block action, record command or link names. | Name it in an exposure, or remove it. |
| `action.permission_undeclared` | An exposure or a link names a permission `permissions.company` does not declare. | Declare it, or fix the name. |
| `manifest.invalid` | A name of the wrong form, a missing `label`, or more than 30 permissions. | Fix the entry the message names. |

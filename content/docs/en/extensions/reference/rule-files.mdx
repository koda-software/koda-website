---
title: Rule files
description: Write an action's logic as a rule file, the steps and edges the rule builder saves, and learn which steps and values a packaged rule may use.
---

A rule file is an action's logic written as a rule: the steps and edges the rule builder saves. `run: rule.yaml` in [action.yaml](/docs/en/extensions/reference/actions) names it. The rule's name, description and trigger come from `action.yaml`, so the file does not say them.

```yaml title="actions/lookup/rule.yaml"
entryStepId: call
steps:
  - id: call
    type: CALL_WEBHOOK
    name: Find customer
    contextKey: answer
    config:
      url: "https://api.example.com/v1/customers?email={{ trigger.data.email }}"
      method: GET
      headers: { Authorization: "Bearer {{ connection.token }}" }
  - id: shape
    type: RUN_SCRIPT
    name: Keep the first match
    contextKey: output
    config:
      code: { $file: shape.js }
edges:
  - { fromStepId: call, toStepId: shape, branchKey: default }
```

Any other key at the top of the file, `name`, `description` and `trigger` among them, is refused with `rule.invalid`.

## The result

Whatever the rule leaves under the context key `output` is the action's result, and is checked against the action's output fields. Give the step that produces it `contextKey: output`.

A **Call Webhook** step's result is `{ status, headers, body }`. An error status fails the step, and so the action, unless the step's error port is connected.

## Step ids

Step ids are local names such as `call` or `map_items`, and Opero gives each step its own id at install. Keep a step's id the same across versions and the step keeps its identity.

## Call Webhook URLs

A **Call Webhook** URL starts with `https://` and a host written out in full, one of the hosts in [`permissions.network`](/docs/en/extensions/reference/manifest#network-hosts). The host cannot come from a template, and the URL carries no port, user name or password. The path and query may use templates.

`auth: connection` sends the connection's credentials as HTTP Basic, when every method of the connection declares a `scheme`. No other `auth` is accepted. See [HTTP Basic from the connection](/docs/en/extensions/reference/connection-and-secrets#http-basic-from-the-connection).

## Script files

A **Run Script** step may keep its code in a script file of the action's folder: `code: { $file: shape.js }`. That is the only place `$file` is accepted. The file is a module, as [Scripts](/docs/en/extensions/reference/scripts) describes.

## Values available in a rule file

| Write | To get |
| --- | --- |
| `{{ trigger.data.<field> }}` | A field of the action's input. In an action a [schedule](/docs/en/extensions/reference/schedules) runs, the schedule's input: `subject`, `lastSucceededAt` and `firstRun`. |
| `{{ trigger.settings.<field> }}` | One of the extension's [settings](/docs/en/extensions/reference/settings), with its default applied. Not secret, so usable anywhere. |
| `{{ connection.<field> }}` | A secret field of the connection, only in a **Call Webhook** header value or URL query value, and also in the URL path and body when `connection.yaml` sets `secretsInBody`. See [Secrets](/docs/en/extensions/reference/connection-and-secrets#secrets). |
| `{{ userConnection.<field> }}` | A member's token or secret value, in a member action only, with the same limits as a connection secret. See [Member connections](/docs/en/extensions/reference/member-connections#the-members-values-in-rules). |
| `{{ trigger.record.id }}` | The record a [block action or record command](/docs/en/extensions/reference/member-actions#the-record-the-action-runs-for) runs for; also `type`, `moduleKey` and `objectKey`. |
| `{{ <contextKey>.… }}` | The result of an earlier step, under its context key. |

Inside an action, templates get Opero's built-in filters only. Filters from other extensions, from the organization's own scripts, or from this package are not available.

## Steps a rule file may use

| Step type | Use it to |
| --- | --- |
| `CALL_WEBHOOK` | Call the outside service. |
| `RUN_SCRIPT` | Run sandboxed JavaScript between calls. |
| `CONDITION`, `SWITCH` | Branch on the answer. |
| `LOOP` | Repeat steps for each item of a list. |
| `FILTER`, `TRANSFORM`, `AGGREGATE`, `SORT`, `DEDUPE` | Reshape lists. |
| `SAVE_TO_CONTEXT` | Keep a value for later steps. |
| `LOG_OUTPUT` | Write to the run log. |
| `WAIT` | Pause. |
| `STOP` | End the rule. |
| `x-<key>.<action>` | Run another action of the package that is published as a rule step. Actions may not call each other in a circle. |
| `EMIT_EVENT` | Raise events of the package's own triggers, in an action a schedule or a member connection hook runs. See [Raising events](/docs/en/extensions/reference/raising-events). |

### Data steps

These steps are allowed when the package declares the [data scope](/docs/en/extensions/reference/data-permissions) each one needs, and only on the package's own objects and queries. See [Data steps](/docs/en/extensions/reference/data-steps).

| Step type | Use it to | Scope |
| --- | --- | --- |
| `FETCH_RECORDS` | Read records of the package's objects. | `records:read` |
| `CREATE_RECORD`, `UPDATE_RECORD` | Create or change records of the package's objects. | `records:write` |
| `RUN_QUERY` | Run a query of the package. | `queries:run` or `queries:mutate` |
| `UPDATE_CONTRACTOR` | Change a contractor. | `contractors:write` |
| `SEND_EMAIL` | Send an email. | `email:send` |
| `SEND_NOTIFICATION` | Notify members of the organization. | `notifications:send` |
| `GENERATE_DOCUMENT` | Generate a document from a template the rule author picks. | `documents:generate` |

Any other step type, such as attaching files, calling another rule or starting a workflow, is refused. That work belongs in the organization's rule that uses your step.

## From the rule builder to a rule file

You can build the logic in the rule builder first, export the rule as JSON and paste it into the rule file, since JSON is valid YAML. Then:

<Steps>
<Step>
Remove `name`, `description`, `trigger` and any other key but `entryStepId`, `steps` and `edges`.
</Step>
<Step>
Replace the step UUIDs with short local ids, in the steps and in the edges.
</Step>
<Step>
Replace hard-coded credentials with `{{ connection.<field> }}`.
</Step>
<Step>
Give the step that produces the result `contextKey: output`.
</Step>
</Steps>

## Problems

| Code | Cause | Fix |
| --- | --- | --- |
| `rule.invalid` | A key other than `entryStepId`, `steps` and `edges`, `steps` or `edges` that is not a list, a step without a `type`, or an edge that is not an object. | Keep only the three keys, in the shape above. |
| `rule.invalid_step_id` | A step id that is a UUID or has other characters. | Use a short local name. |
| `rule.duplicate_step_id` | Two steps with the same id. | Rename one. |
| `rule.unknown_step` | `entryStepId` or an edge names no step of the file. | Fix the id. |
| `rule.file_reference_misplaced` | `$file` anywhere but the `code` of a `RUN_SCRIPT` step. | Move the script to a `RUN_SCRIPT` step. |
| `rule.host_not_literal` | A **Call Webhook** URL that is not `https://`, or whose host is a template or has a port or user name. | Write the host out. |
| `rule.host_not_declared` | A **Call Webhook** host missing from `permissions.network`. | Add the host with a reason. |
| `rule.own_filter_unsupported` | A template of the rule uses one of the package's own filters. | Do the conversion in a script. |
| `rule.connection_unsupported` | `{{ userConnection.<field> }}` in a package without a member connection. | Add `connection/member.yaml`, or use `connection.*`. |
| `step.type_not_allowed` | A step type outside the lists above. | Move that work to the rule that uses your step. |
| `manifest.missing_file` | `run` names a rule file that is not in the action's folder. | Add the file, or fix the name. |
| `script.invalid_path`, `script.missing_file` | `$file` names no `.js` or `.ts` file of the action's folder. | See [Scripts](/docs/en/extensions/reference/scripts#problems). |

The codes about secrets in a rule (`connection.*`) are under [Connection and secrets](/docs/en/extensions/reference/connection-and-secrets), and the ones about data steps (`step.scope_missing`, `step.target_not_own`, `step.target_not_literal`, `step.config_not_allowed`) under [Data steps](/docs/en/extensions/reference/data-steps).

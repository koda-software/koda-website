Settings are values the administrator chooses for an installed extension, such as a region, a language or how many records to send in one call. They are not secret: a secret belongs in the [connection](/docs/en/extensions/reference/connection-and-secrets). The administrator fills them in on the extension's [Configuration](/docs/en/extensions/after-install#configuration) tab.

![The Configuration tab with a settings section and the connection](/docs/_assets/extensions/after-install/configuration.webp)

```yaml title="settings.yaml"
groups:
  - group: general
    label: General
    fields:
      region: { type: select, label: Region, options: [eu, us], default: eu }
      sandbox: { type: boolean, label: Use the sandbox }
  - group: sync
    label: Synchronisation
    description: How much is sent in one call.
    fields:
      batchSize: { type: integer, label: Batch size, help: Parcels per call., default: 50 }
      owner: { type: text, label: Owner e-mail, required: true }
```

The file sits at the top of the package, next to `extension.yaml`, which names it with `settings: settings.yaml`. That is the only accepted value.

## settings.yaml

The file holds one key, `groups`: a list of 1 to 20 groups. Each group is one section of the settings form.

<TypeTable
  type={{
    group: {
      type: 'string',
      description: 'The group\'s key: a lower-case letter, then lower-case letters, digits and _, up to 41 characters. Unique in the file.',
      required: true,

    label: {
      type: 'string',

      required: true,

    fields: {
      type: 'field list',
      description: 'At least one field, as in an action\'s input, without secret and hint. No schema file.',
      required: true,
    },
  }}
/>

`fields` is a [field list](/docs/en/extensions/reference/actions#field-lists). A value that must stay secret is a credential field of the connection, so `secret` and `hint` are refused here.

## Field keys are unique in the file

A group only arranges the form. The values are one flat set of at most 100 fields, so two groups cannot declare the same field key, and moving a field to another group changes nothing for the actions that read it.

## Defaults

A field without a stored value reads as its `default`. Opero stores only what the administrator sets, so a default changed by a new version applies at once to every setting the administrator has not set. A field with neither a stored value nor a default is missing from what actions read.

## Required settings

While a field with `required: true` has no value, stored or default, the extension does not run: its steps are missing from the rule builder, and a saved rule that reaches one fails with `extension_inactive`. It runs again as soon as the value is saved. See [States](/docs/en/extensions/after-install#states).

<Callout type="idea" title="Give a default when one makes sense">
A required field with a default never stops the extension. Leave the default out only for a value nobody can guess, such as an account number or an e-mail address.
</Callout>

## Reading settings

Actions read the values with the defaults applied. Settings are not secret, so they can be used anywhere a template or a script can.

<Tabs items={['Rule file', 'Script']}>
<Tab value="Rule file">

Write `{{ trigger.settings.<field> }}`. A setting cannot supply the host of a **Call Webhook** URL.

```yaml title="actions/quote/rule.yaml"
entryStepId: call
steps:
  - id: call
    type: CALL_WEBHOOK
    name: Ask for a quote
    contextKey: output
    config:
      url: "https://api.example.com/v1/quotes?region={{ trigger.settings.region }}" # [!code highlight]
      method: POST
      body: { weight: "{{ trigger.data.weight }}", contact: "{{ trigger.settings.owner }}" } # [!code highlight]
edges: []
```

</Tab>
<Tab value="Script">

The argument's `settings` holds them:

```js title="actions/split/run.js"
/** @type {import('../../.opero/types').Action<'split'>} */
const run = ({ input, settings }) => {
  const batches = [];
  for (let i = 0; i < input.parcels.length; i += settings.batchSize) { // [!code highlight]
    batches.push(input.parcels.slice(i, i + settings.batchSize));
  }
  return { batches };
};
export default run;
```

</Tab>
</Tabs>

A package without `settings.yaml` gets an empty object. The connection's verify action gets the settings too. The generated `Settings` type in `.opero/types/index.d.ts` makes a field with a default never optional, because it always has a value.

## Settings in tests

A test case gives settings under `settings:`, at the top level of the case. Defaults apply to the fields the case leaves out, and the result must match `settings.yaml`, so a required setting without a default is given in every case.

```yaml title="actions/quote/tests.yaml"
- name: the region and the owner come from the settings
  input: { weight: "2" }
  settings: { owner: ops@example.com, region: us } # [!code highlight]
  http:
    - request:
        method: POST
        url: https://api.example.com/v1/quotes?region=us
        body: { weight: "2", contact: ops@example.com }
      response: { status: 200, body: { price: 12 } }
  succeeds: true
```

## Upgrades

| Change in a new version | What happens | Code |
| --- | --- | --- |
| A field with a stored value is removed | The value is dropped. A warning. | `settings.value_dropped` |
| A field changes so that its stored value no longer fits | The value is dropped. A warning. | `settings.value_dropped` |
| A required field without a default is added | The extension stops after the upgrade until the administrator fills it in. A warning. | `settings.incomplete_after_upgrade` |
| A default changes | The new default applies to every setting the administrator has not set. | |

Changing settings never switches the connection off. Uninstalling removes the stored values. What the administrator sees is in [Upgrade and uninstall](/docs/en/extensions/upgrade-and-uninstall#what-a-new-version-can-change).

## Translations

Group texts go under `settings.groups.<group>`, field texts under `settings.fields.<field>`, by the field's key without its group. See [Translations](/docs/en/extensions/reference/translations#translatable-keys).

## Problems

| Code | Cause | Fix |
| --- | --- | --- |
| `settings.invalid` | An unknown key, no groups or more than 20, a group without `label` or `fields`, or more than 100 fields. | Keep to the keys and limits above. |
| `name.duplicate` | Two groups, or two fields anywhere in the file, with the same key. | Rename one. |
| `field.invalid` | A field of the wrong shape, including `secret` or `hint` on a setting. | Move a secret value to the connection. |
| `layout.unlisted_feature` | A `settings.yaml` that `extension.yaml` does not name. | Add `settings: settings.yaml`. |
| `layout.missing_descriptor` | `extension.yaml` says `settings: settings.yaml`, but the file is missing. | Add the file, or remove the key. |
| `connection.invalid` | `connection.yaml` still has a `settings` block. | Move it to `settings.yaml`. |
| `test.invalid` | A test case whose settings do not match `settings.yaml`, or that gives settings under `connection.config`. | Give them under `settings:`, as the file declares them. |

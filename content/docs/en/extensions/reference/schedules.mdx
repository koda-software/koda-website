title: Schedules
description: "Reference for schedule.yaml in Opero extensions: intervals, running once for the installation, for each company or for each connected member, the input each run receives, rate limits, failures, and what happens when the extension is disabled, upgraded or uninstalled."

A schedule runs one of the package's actions on its own, at a fixed interval, without any rule of the organization. Use it to read a service regularly and [raise events](/docs/en/extensions/reference/raising-events) for what is new or changed.

```yaml title="schedules/sync-orders/schedule.yaml"
schedule: sync_orders
label: Sync open orders
description: Reads each company's open orders every hour.
every: 1h
forEach: company
action: sync_orders
```

Each schedule is a folder `schedules/<folder>` with a `schedule.yaml`, listed in `extension.yaml` (or a module's `module.yaml`):

```yaml title="extension.yaml"
schedules:
  - schedules/sync-orders
```

`opero-ext add schedule <name> --action <action>` writes the folder and the list entry; see [Command-line tool](/docs/en/extensions/reference/cli).

The interval is fixed by the package: the administrator cannot change it, and there are no cron expressions. A package has at most 10 schedules.

## What one run is for

`forEach` decides how many runs there are per interval, and for whom. Each of them is a **subject**.

| `forEach` | Subjects | The run's company |
| --- | --- | --- |
| `installation` | One, for the whole installed extension. | None. |
| `company` | Each active company of the organization. | That company. |
| `userConnection` | Each member who connected their account through the package's [member connection](/docs/en/extensions/reference/member-connections). | The company the member chose in the connection's company field; none when the member connection has no company field. |

The company matters for what the run does: [data steps](/docs/en/extensions/reference/data-steps) work in it, and events raised by the run go to it. An event raised with no company starts only the organization's rules that are not limited to particular companies.

A new company, or a newly connected member, gets its first run within the first interval after Opero notices it (within a minute). A company that becomes inactive or is deleted, and a member who disconnects, have no more runs.

`forEach: userConnection` needs a member connection (`schedule.invalid` otherwise) and its action must be a member action, one that uses `{{ userConnection.<field> }}`. The other way round, a member action runs only from such a schedule or from a connection hook (`action.member_outside_member_run`).

## The input each run receives

Opero fills in the action's input. A rule file reads it as `{{ trigger.data.… }}`, a script as `input`:

```yaml
subject:

firstRun: false
```

</Tab>
<Tab value="installation">

```yaml
subject:
  kind: installation
  companyId: null
lastSucceededAt: null
firstRun: true
```

</Tab>
<Tab value="userConnection">

```yaml
subject:
  kind: userConnection
  companyId: cmp_8f2a…        # null without a company field
  userId: usr_51c0…
  credentialId: cred_77d1…
  config: { companyId: cmp_8f2a… }   # the member's config form
  meta: { sandboxUserId: "1234" }    # what afterConnect stored as meta
lastSucceededAt: "2026-11-12T09:00:04.512Z"
firstRun: false
```

</Tab>
</Tabs>

| Field | Meaning |
| --- | --- |
| `subject.kind` | The schedule's `forEach`. |
| `subject.companyId` | The run's company, or `null`. |
| `subject.userId`, `credentialId`, `config`, `meta` | For a member only: who it is, their connection, their config form and the public values `afterConnect` stored. Never their token. |
| `lastSucceededAt` | When this subject's last successful run finished, or `null` before the first one. Use it to ask the service only for what changed since; ask with some overlap, for example an hour earlier, and let [dedupe](/docs/en/extensions/reference/raising-events#dedupe) leave out what was already raised. |
| `firstRun` | `true` until this subject has had a successful run. Use it, for example, to read a longer period the first time. |

The action's `input` must accept this. Either declare it as a field list:

```yaml title="actions/sync-orders/action.yaml (part)"
input:
  subject:
    type: object
    label: Subject
    required: true
    fields:
      kind: { type: text, required: true }
      companyId: { type: text, nullable: true }
  lastSucceededAt: { type: datetime, nullable: true }
  firstRun: { type: boolean, required: true }
```

or give a JSON Schema file that leaves `subject` open:

```yaml title="actions/sync-member/input.yaml"
type: object
properties:
  subject: { type: object }
  lastSucceededAt: { type: [string, "null"] }
  firstRun: { type: boolean }
required: [subject, firstRun]
```

A field list closes the object, so for `forEach: userConnection` it must also name `userId`, `credentialId`, `config` and `meta`; the open schema file is simpler there. The input is checked against what the schedule passes when the package is checked, and an input that refuses it is reported as `schedule.invalid` with the first difference.

## Who the run acts as

A schedule run is a run of the action's installed rule, started by the extension itself. It acts as the extension, with the [data scopes](/docs/en/extensions/reference/data-permissions) the administrator agreed to, the extension's [settings](/docs/en/extensions/reference/settings) as `{{ trigger.settings.<field> }}` and its connection. A run over member connections also has that member's values as `{{ userConnection.<field> }}`, and only that member's. The run shows in the history of the action's rule.

## When it runs

- Each subject runs once per interval. Its first run comes at some point within the first interval after install, spread so that subjects do not all start at the same minute.
- A subject runs at most once at a time, also when Opero runs on several servers.
- Each interval is counted from the end of the previous run, by its outcome:

| How the run ended | Next run |
| --- | --- |
| Success | One interval later. |
| Rate limit: a request was answered `429` | After the time the service asked for in `Retry-After`, or else `RateLimit-Reset`; 15 minutes when it gave none; never later than one interval. This is not counted as a failure. |
| Failure: an HTTP error, an input or output that does not match, a failed step | After 15 minutes, then 30 minutes, 1 hour and so on, doubling, but never later than one interval. The subject counts as failing until a run succeeds. |
| A member's token was refused (`401` to a request that carried it) | Not until the member connects again; see [Member connections](/docs/en/extensions/reference/member-connections#a-refused-token). |

Missed intervals are never made up: a subject that waited for several intervals runs once.

A member is skipped, without a failure, while their connection cannot be used: they have not chosen a company yet, the chosen company is no longer theirs, or their connection waits for them to connect again.

## When the extension does not run

While the extension is [not running](/docs/en/extensions/after-install#states), for any reason, its schedules run nothing. When it runs again, each subject that is due runs once, and the schedule continues from there.

## Upgrades and uninstalling

- An upgrade that removes a schedule, or changes its `forEach`, drops the subjects of the old one. A shortened interval applies at once.
- The schedules appear in the [install plan](/docs/en/extensions/after-install#the-install-plan), so an upgrade that adds a schedule, or changes its interval, `forEach` or action, needs the administrator's consent like any other change in the plan.
- Uninstalling stops every schedule.

## What the administrator sees

The install plan lists each schedule with its label, how often it runs and for what, and the action it runs. After install, the extension's page shows each schedule's status: how many subjects it has, how many are due, running, failing or waiting for a member, and when it last succeeded. See [After install](/docs/en/extensions/after-install#schedules-and-connected-members).

## Problems

| Code | What is wrong |
| --- | --- |
| `schedule.invalid` | An unknown key, an `every` that is not one of the seven intervals, a `forEach` that is not one of the three, `forEach: userConnection` without a member connection or with an action that is not a member action, an action input that does not accept what the schedule passes, or more than 10 schedules. |
| `schedule.action_unknown` | `action` names no action of the package. |
| `schedule.action_exposed` | The action is exposed as a rule step. |
| `action.member_outside_member_run` | A member action is run by a schedule that is not `forEach: userConnection`. |
| `name.duplicate` | Two schedules with the same name. |

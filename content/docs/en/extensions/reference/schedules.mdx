title: Schedules
description: Run an action of the package on its own at a fixed interval with schedule.yaml, once for the installation, for each company or for each connected member.
---

A schedule runs one of the package's actions on its own, at a fixed interval, without any rule of the organization. Use it to read a service regularly and [raise events](/docs/en/extensions/reference/raising-events) for what is new or changed. The guides [Events from a service](/docs/en/extensions/scheduled-events) and [Data from each member's account](/docs/en/extensions/member-accounts) each build one.

```yaml title="schedules/sync-orders/schedule.yaml"
schedule: sync_orders
label: Sync open orders
description: Reads each company's open orders every hour.
every: 1h
forEach: company
action: sync_orders
```

Each schedule is a folder `schedules/<folder>` with a `schedule.yaml`, listed under `schedules` in `extension.yaml` or a module's `module.yaml`. `opero-ext add schedule <name> --action <action>` writes both.

A package has at most 10 schedules.

## What one run is for

`forEach` decides how many runs there are per interval, and for whom. Each of them is a **subject**.

| `forEach` | Subjects | The run's company |
| --- | --- | --- |
| `installation` | One, for the whole installed extension. | None. |
| `company` | Each active company of the organization. | That company. |
| `userConnection` | Each member who connected their account through the package's [member connection](/docs/en/extensions/reference/member-connections). | The company the member chose; none when the member connection has no company field. |

[Data steps](/docs/en/extensions/reference/data-steps) work in the run's company, and events the run raises go to it. A new company or a newly connected member gets its first run within the first interval after Opero notices it, within a minute; one that becomes inactive, is deleted or disconnects has no more runs.

`forEach: userConnection` needs a member connection, and its action must be a member action, one that uses `{{ userConnection.<field> }}`.

## The input each run receives

Opero fills in the action's input. A rule file reads it as `{{ trigger.data.… }}`, a script as `input`:

```yaml
subject:
  kind: company
  companyId: cmp_8f2a…
lastSucceededAt: "2026-11-12T09:00:04.512Z"   # null before the first success
firstRun: false
```

</Tab>
<Tab value="installation">

```yaml
subject:
  kind: installation
  companyId: null
lastSucceededAt: null
firstRun: true
```

</Tab>
<Tab value="userConnection">

```yaml
subject:
  kind: userConnection
  companyId: cmp_8f2a…        # null without a company field
  userId: usr_51c0…
  credentialId: cred_77d1…
  config: { companyId: cmp_8f2a… }   # the member's config form
  meta: { sandboxUserId: "1234" }    # what afterConnect stored as meta
lastSucceededAt: "2026-11-12T09:00:04.512Z"
firstRun: false
```

</Tab>
</Tabs>

| Field | Meaning |
| --- | --- |
| `subject.kind` | The schedule's `forEach`. |
| `subject.companyId` | The run's company, or `null`. |
| `subject.userId`, `credentialId`, `config`, `meta` | For a member only: who it is, their connection, their form and the public values `afterConnect` stored. Never their token. |
| `lastSucceededAt` | When this subject's last successful run finished, or `null` before the first one. Ask the service for what changed since, with some overlap, and let [dedupe](/docs/en/extensions/reference/raising-events#dedupe) leave out what was already raised. |
| `firstRun` | `true` until this subject has had a successful run, for example to read a longer period the first time. |

The action's `input` must accept this. Declare it as a field list, or give a JSON Schema file that leaves `subject` open:

```yaml title="actions/sync-orders/action.yaml (part)"
input:
  subject:
    type: object
    label: Subject
    required: true
    fields:
      kind: { type: text, required: true }
      companyId: { type: text, nullable: true }
  lastSucceededAt: { type: datetime, nullable: true }
  firstRun: { type: boolean, required: true }
```

A field list closes the object, so for `forEach: userConnection` it must also name `userId`, `credentialId`, `config` and `meta`; an open schema file is simpler there.

## Who the run acts as

A schedule run is a run of the action's installed rule, started by the extension itself, and it shows in that rule's history. It acts as the extension, with the [data scopes](/docs/en/extensions/reference/data-permissions) the administrator agreed to, the extension's [settings](/docs/en/extensions/reference/settings) and its connection. A run over member connections also has that member's values, and only that member's.

## When it runs

Each subject runs once per interval, at most once at a time, also when Opero runs on several servers. Its first run comes within the first interval after install, spread so that subjects do not all start at the same minute. The next run is counted from the end of the previous one:

| How the run ended | Next run |
| --- | --- |
| Success | One interval later. |
| Rate limit: a request was answered `429` | After the service's `Retry-After`, or else `RateLimit-Reset`; 15 minutes when it gave none; never later than one interval. Not counted as a failure. |
| Failure: an HTTP error, an input or output that does not match, a failed step | After 15 minutes, then 30 minutes, 1 hour and so on, doubling, never later than one interval. |
| A member's token was refused (`401` to a request that carried it) | Not until the member connects again; see [A refused token](/docs/en/extensions/reference/member-connections#a-refused-token). |

Missed intervals are never made up: a subject that waited for several intervals runs once. A member is skipped, without a failure, while they have not chosen a company, the chosen company is no longer theirs, or their connection waits for them to connect again. While the extension does not run, its schedules run nothing; when it runs again, each due subject runs once.

## Upgrades

| Change in a new version | What happens | Code |
| --- | --- | --- |
| A schedule is removed | It stops, and its run state is deleted. A warning. | `schedule.removed` |
| A schedule's `every`, `forEach` or `action` changes | It follows the new schedule at once; a changed `forEach` drops the old subjects. A warning. | `schedule.changed` |
| A schedule is added | It is shown as new in the review, for the administrator to agree to. | |

Uninstalling stops every schedule. What the administrator sees is in [Upgrade and uninstall](/docs/en/extensions/upgrade-and-uninstall#what-a-new-version-can-change), and how they follow the runs in [Schedules](/docs/en/extensions/after-install#schedules).

## Translations

The texts go under `schedules.<schedule>`: `label` and `description`. See [Translations](/docs/en/extensions/reference/translations#translatable-keys).

## Problems

| Code | Cause | Fix |
| --- | --- | --- |
| `schedule.invalid` | An unknown key, an `every` or `forEach` that is not one of the listed values, `forEach: userConnection` without a member connection or with an action that is not a member action, an action input that does not accept what the schedule passes (the message gives the first difference), or more than 10 schedules. | Fix the key, or the action's input. |
| `schedule.action_unknown` | `action` names no action of the package. | Fix the name, or add the action. |
| `schedule.action_exposed` | The action is exposed as a rule step, a block action or a record command. | Give the schedule its own action that nothing exposes. |
| `action.member_outside_member_run` | A member action is run by a schedule that is not `forEach: userConnection`. | Use `forEach: userConnection`. |
| `name.duplicate` | Two schedules with the same name. | Rename one. |

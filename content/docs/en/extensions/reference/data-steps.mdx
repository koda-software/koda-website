title: Data steps
description: "Use data and messaging steps in Opero extension rule files: fetch, create and update the package's records, run its queries, update contractors, send email with an attachment, notify members and generate documents, each with its test."
---

Data steps are the rule steps that touch Opero's data or send something: records, queries, contractors, email, notifications and documents. A rule file of your package may use them when the package declares the [data scope](/docs/en/extensions/reference/data-permissions) each one needs. This page shows each step as it is written in a rule file, with the effect a [test case](/docs/en/extensions/reference/tests#data-and-messaging-steps) scripts for it.

<Callout title="Before you write one">
- The step works in the company the organization's rule that uses your step runs for. A run without a company fails at the step.
- Every module, object and query key is written out. A template in its place is refused.
- Each step publishes its result under its `contextKey`, like any step. A step with no result publishes nothing.
</Callout>

## Records

The package's objects live in the module `x-<key>`. A rule names an object by the `object` key in its `object.yaml`. The example package below has the key `shop-ext`, so its module is `x-shop-ext`.

### Fetch records

`FETCH_RECORDS` reads records of one object. Scope `records:read`.

```yaml title="actions/note-order/rule.yaml (part)"
  - id: fetch
    type: FETCH_RECORDS
    name: First open order
    contextKey: orders
    config:
      moduleKey: x-shop-ext
      objectKey: orders
      filters:
        - { field: status, operator: eq, value: open }
      sortBy: ordered_on
      sortDirection: asc
      limit: 1
```

| Key | Meaning |
| --- | --- |
| `moduleKey` | Always `x-<key>`. |
| `objectKey` | An object of the package. |
| `filters` | Optional. A list of `{ field, operator, value }`, all of which must hold. `operator` is one of `eq`, `neq`, `contains`, `startsWith`, `endsWith`, `in`, `notIn`, `gt`, `gte`, `lt`, `lte`, `between`, `isNull`, `isNotNull`, `isEmpty`, `isNotEmpty`, `hasAny`, `hasAll`, `hasNone`, `near`. |
| `sortBy`, `sortDirection` | Optional. A field key, and `asc` (the default) or `desc`. |
| `limit` | Required. 1 to 100. |

The result is `{ rows, rowCount, truncated }`. Each row has the record's `id` and its fields by key, so the next step reads `{{ orders.rows[0].id }}` and `{{ orders.rows[0].number }}`. `truncated` is true when more records matched than `limit`.

### Create a record

`CREATE_RECORD` adds one record. Scope `records:write`.

```yaml
  - id: note
    type: CREATE_RECORD
    name: Add the note
    contextKey: note
    config:
      targetModuleKey: x-shop-ext
      targetObjectKey: order-notes
      fieldMapping:
        text: "{{ trigger.data.text }}"
        order: "{{ orders.rows[0].id }}"
```

`fieldMapping` maps field keys to values; a reference field takes the id of the record it points at. The result is `{ id }`, the new record's id.

### Update a record

`UPDATE_RECORD` changes one record, named by its id. Scope `records:write`.

```yaml
  - id: mark
    type: UPDATE_RECORD
    name: Mark the order
    contextKey: output
    config:
      target: "{{ orders.rows[0].id }}"
      targetModuleKey: x-shop-ext
      targetObjectKey: orders
      fieldUpdates:
        status: noted
        last_note: "{{ note.id }}"
```

`target` is required: a step has no triggering record, so `target: self` is refused. `fieldUpdates` maps field keys to their new values. The step has no result.

### Their test

The three steps above, scripted in order:

```yaml title="actions/note-order/tests.yaml"
- name: the note is added and the order marked
  input: { text: Call back on Monday }
  effects:
    - request: { step: FETCH_RECORDS, objectKey: orders }
      response:
        rows: [{ id: 7d1c2a34-0000-4000-8000-000000000001, number: A-1, status: open }]
        rowCount: 1
        truncated: false
    - request:
        step: CREATE_RECORD
        targetObjectKey: order-notes
        fieldMapping: { text: Call back on Monday, order: 7d1c2a34-0000-4000-8000-000000000001 }
      response: { id: 9b0e1f22-0000-4000-8000-000000000002 }
    - request:
        step: UPDATE_RECORD
        targetObjectKey: orders
        fieldUpdates: { status: noted, last_note: 9b0e1f22-0000-4000-8000-000000000002 }
  succeeds: true
```

## Run a query

`RUN_QUERY` runs one of the package's [queries](/docs/en/extensions/reference/queries) by its installed key, `x_<key with _>_<name>`. A FETCH query needs the scope `queries:run`, a MUTATION query `queries:mutate`.

```yaml title="actions/count-open/rule.yaml"
entryStepId: close
steps:
  - id: close
    type: RUN_QUERY
    name: Close old orders
    contextKey: closed
    config:
      queryKey: x_shop_ext_close_old_orders
      params: { before: "{{ trigger.data.before }}" }
  - id: count
    type: RUN_QUERY
    name: Count open orders
    contextKey: output
    config:
      queryKey: x_shop_ext_open_orders
edges:
  - { fromStepId: close, toStepId: count }
```

`params` gives the query's parameters by name; templates are allowed in their values. `queryId` is refused.

A FETCH query's result is its list of rows, here `[{ open: 3 }]`. A MUTATION query's result is `{ operation, rowCount, rows }`.

```yaml title="actions/count-open/tests.yaml"
- name: the old orders are closed and the open ones counted
  input: { before: "2025-11-01" }
  effects:
    - request:
        step: RUN_QUERY
        queryKey: x_shop_ext_close_old_orders
        params: { before: "2025-11-01" }
      response: { operation: UPDATE, rowCount: 2, rows: [] }
    - request: { step: RUN_QUERY, queryKey: x_shop_ext_open_orders }
      response: [{ open: 3 }]
  succeeds: true
```

## Update a contractor

`UPDATE_CONTRACTOR` changes one of the organization's contractors. Scope `contractors:write`. Combined with a call to a service, it keeps contractor data in step with that service:

```yaml title="actions/refresh-contractor/rule.yaml"
entryStepId: lookup
steps:
  - id: lookup
    type: CALL_WEBHOOK
    name: Ask the shop
    contextKey: customer
    config:
      url: "https://api.example.com/v1/customers?email={{ trigger.data.email }}"
      method: GET
  - id: store
    type: UPDATE_CONTRACTOR
    name: Store the phone
    contextKey: output
    config:
      contractorId: "{{ trigger.data.contractorId }}"
      fields: { phone: "{{ customer.body.phone }}" }
edges:
  - { fromStepId: lookup, toStepId: store }
```

`contractorId` names the contractor, usually from the step's input. `fields` holds the contractor fields to change, such as `email`, `phone` or `website`. The step has no result, so its effect has no `response`:

```yaml title="actions/refresh-contractor/tests.yaml"
- name: the phone the shop has is stored
  input: { contractorId: c-1, email: ada@example.com }
  http:
    - request: { method: GET, url: "https://api.example.com/v1/customers?email=ada@example.com" }
      response: { status: 200, body: { phone: "+48 600 100 200" } }
  effects:
    - request:
        step: UPDATE_CONTRACTOR
        contractorId: c-1
        fields: { phone: "+48 600 100 200" }
  succeeds: true
```

## Documents, email and notifications

This action renders an order confirmation, emails it to the customer as an attachment and tells a colleague. It needs the scopes `documents:generate`, `email:send` and `notifications:send`, and the `documents` module in `requires.modules`.

```yaml title="actions/confirm-order/action.yaml"
action: confirm_order
label: Confirm order
description: Renders the confirmation, emails it to the customer and notifies a colleague.
input:
  templateId:
    type: text
    label: Document template
    help: A data document template of your organization.
    required: true
  number: { type: text, label: Order number, required: true }
  email: { type: text, label: Customer email, required: true }
  colleagueId: { type: text, label: Colleague to notify, required: true }
run: rule.yaml
tests: tests.yaml
expose:
  ruleStep: { category: messaging }
```

```yaml title="actions/confirm-order/rule.yaml"
entryStepId: render
steps:
  - id: render
    type: GENERATE_DOCUMENT
    name: Render the confirmation
    contextKey: document
    config:
      templateId: "{{ trigger.data.templateId }}"
      data:
        title: "Order {{ trigger.data.number }}"
  - id: mail
    type: SEND_EMAIL
    name: Email the customer
    contextKey: mail
    config:
      to: "{{ trigger.data.email }}"
      subject: "Order {{ trigger.data.number }} is confirmed"
      html: "<p>Your order {{ trigger.data.number }} is confirmed.</p>"
      attachmentFileIds: ["{{ document.fileId }}"]
  - id: notify
    type: SEND_NOTIFICATION
    name: Tell a colleague
    contextKey: output
    config:
      recipients:
        userIds: ["{{ trigger.data.colleagueId }}"]
      title: "Order {{ trigger.data.number }} confirmed"
      body: "The confirmation went to {{ trigger.data.email }}."
  - id: unavailable
    type: SAVE_TO_CONTEXT
    name: Keep the reason
    contextKey: failure
    config:
      value:
        code: "{{ error.code }}"
        message: "{{ error.message }}"
edges:
  - { fromStepId: render, toStepId: mail }
  - { fromStepId: mail, toStepId: notify }
  - { fromStepId: render, toStepId: unavailable, branchKey: error }
  - { fromStepId: mail, toStepId: unavailable, branchKey: error }
```

### Generate a document

`GENERATE_DOCUMENT` renders a data document template of the organization. Scope `documents:generate`.

- `templateId` is written exactly `{{ trigger.data.<field> }}`: the template is never your package's choice, the organization's rule author picks it in your step's input. Any other form is refused.
- `data` is what the template renders. `templateVersionId` and `metadata` are allowed too.
- `entityId` and `invoiceId` are refused: a package renders data templates only, never a record.
- The result has `fileId`, `documentGenerationJobId`, `templateId`, `templateVersionId`, `mimeType` and `originalName`. Pass `fileId` on to attach the file.
- When document generation is switched off for the organization, the step fails with the message "GENERATE_DOCUMENT requires document generation to be enabled".

### Send an email

`SEND_EMAIL` sends through the installation's email service. Scope `email:send`.

- `to`, `subject` and `html` are written in the step. `bodyFormat`, `locale` and `data` are allowed too.
- Attach files by id with `attachmentFileIds` (or `fileIds`), for example the document an earlier step generated. Any file of the organization can be attached this way, not only one the same run generated; see [Attachments](/docs/en/extensions/reference/data-permissions#the-scopes). This may be narrowed later.
- `accountId` (a mailbox), `templateId` (an email template) and the mailbox-only `cc`, `bcc`, `text` and `saveAsDraft` are refused.
- Without an email service on the installation, the step fails with the code `service_connection_not_configured`.
- The step has no result.

### Send a notification

`SEND_NOTIFICATION` sends the generic notification, with a `title` and a `body`, to members of the organization. Scope `notifications:send`.

- `recipients.userIds` lists the users. Only active members of the organization receive it.
- `linkUrl`, `payload`, `entityRef`, `dedupeKey` and `collapseWindowMinutes` are allowed too; `typeKey` is refused.
- The result is `{ notificationId, recipientCount, collapsed, suppressed }`.

### Their test

```yaml title="actions/confirm-order/tests.yaml"
- name: the confirmation is rendered, emailed with its file and announced
  input:
    templateId: tpl-1
    number: A-1
    email: customer@example.com
    colleagueId: user-2
  effects:
    - request:
        step: GENERATE_DOCUMENT
        templateId: tpl-1
        data: { title: Order A-1 }
      response:
        fileId: file-1
        documentGenerationJobId: job-1
        templateId: tpl-1
        templateVersionId: version-1
        mimeType: application/pdf
        originalName: document-job-1.pdf
    - request:
        step: SEND_EMAIL
        to: customer@example.com
        subject: Order A-1 is confirmed
        attachmentFileIds: [file-1]
    - request:
        step: SEND_NOTIFICATION
        recipients: { userIds: [user-2] }
        title: Order A-1 confirmed
      response:
        notificationId: notification-1
        recipientCount: 1
        collapsed: false
        suppressed: false
  succeeds: true
```

## When a data step fails

A failed data step fails your action like any step, unless an `error` edge catches it, as in the example above: the edge's step reads `{{ error.code }}` and `{{ error.message }}`. The organization's rule that uses your step then sees `EXTENSION_ACTION_FAILED` when the action fails.

A step that would reach outside the declared scopes when it runs fails with `EXTENSION_SCOPE_DENIED` and does nothing. See [Data permissions](/docs/en/extensions/reference/data-permissions#when-it-is-checked).

## Scripts get no data

A **Run script** step, or a script an action runs, cannot read or write data and cannot send notifications: in a package, scripts get no data helpers. Fetch the data with a step first and give it to the script through the context, then write the script's result with another step.

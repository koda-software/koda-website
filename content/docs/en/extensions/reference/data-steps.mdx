---
title: Data steps
description: Write the steps that read and write the package's records, run its queries, update contractors, send email and notifications, and generate documents.
---

Data steps are the rule steps that touch Opero's data or send something. A rule file of your package may use one when the package declares the [data scope](/docs/en/extensions/reference/data-permissions) it needs. Each step below comes with its keys and the effect a [test case](/docs/en/extensions/reference/tests#data-and-messaging-steps) scripts for it. The guide [A package with its own data](/docs/en/extensions/own-data) uses the record steps.

| Step | Scope | Result under its `contextKey` |
| --- | --- | --- |
| [`FETCH_RECORDS`](#fetch-records) | `records:read` | `{ rows, rowCount, truncated }` |
| [`CREATE_RECORD`](#create-a-record) | `records:write` | `{ id }` |
| [`UPDATE_RECORD`](#update-a-record) | `records:write` | None |
| [`RUN_QUERY`](#run-a-query) | `queries:run` or `queries:mutate` | The rows, or `{ operation, rowCount, rows }` |
| [`UPDATE_CONTRACTOR`](#update-a-contractor) | `contractors:write` | None |
| [`GENERATE_DOCUMENT`](#generate-a-document) | `documents:generate` | `{ fileId, … }` |
| [`SEND_EMAIL`](#send-an-email) | `email:send` | None |
| [`SEND_NOTIFICATION`](#send-a-notification) | `notifications:send` | `{ notificationId, … }` |

## Rules for every data step

- The step works in the company the organization's rule that uses your step runs for. A run without a company fails at the step.
- Every module, object and query key is written out. A template in its place is refused.
- The examples below belong to a package with the key `shop-ext`, so its module is `x-shop-ext`.

## Fetch records

`FETCH_RECORDS` reads records of one object of the package.

```yaml title="actions/note-order/rule.yaml (part)"
  - id: fetch
    type: FETCH_RECORDS
    name: First open order
    contextKey: orders
    config:
      moduleKey: x-shop-ext
      objectKey: orders
      filters:
        - { field: status, operator: eq, value: open }
      sortBy: ordered_on
      sortDirection: asc
      limit: 1
```

| Key | Required | Meaning |
| --- | --- | --- |
| `moduleKey` | Yes | Always `x-<key>`. |
| `objectKey` | Yes | An object of the package. |
| `limit` | Yes | 1 to 100. |
| `filters` | No | Up to 20 `{ field, operator, value }`, all of which must hold. `operator` is one of `eq`, `neq`, `contains`, `startsWith`, `endsWith`, `in`, `notIn`, `gt`, `gte`, `lt`, `lte`, `between`, `isNull`, `isNotNull`, `isEmpty`, `isNotEmpty`, `hasAny`, `hasAll`, `hasNone`, `near`. |
| `sortBy`, `sortDirection` | No | A field key, and `asc` (the default) or `desc`. |

Each row has the record's `id` and its fields by key, so a later step reads `{{ orders.rows[0].id }}`. `truncated` is true when more records matched than `limit`. In a test the effect is `{ step: FETCH_RECORDS, objectKey: orders }` with the rows as its `response`.

## Create a record

`CREATE_RECORD` adds one record to an object of the package.

```yaml title="actions/note-order/rule.yaml (part)"
  - id: note
    type: CREATE_RECORD
    name: Add the note
    contextKey: note
    config:
      targetModuleKey: x-shop-ext
      targetObjectKey: order-notes
      fieldMapping:
        text: "{{ trigger.data.text }}"
        order: "{{ orders.rows[0].id }}"
```

| Key | Required | Meaning |
| --- | --- | --- |
| `targetModuleKey` | Yes | Always `x-<key>`. |
| `targetObjectKey` | Yes | An object of the package. |
| `fieldMapping` | Yes | Field keys and their values. A reference field takes the id of the record it points at. |

The result is `{ id }`, the new record's id. In a test the effect's `response` is `{ id: … }`.

## Update a record

`UPDATE_RECORD` changes one record of the package's objects, named by its id.

```yaml title="actions/note-order/rule.yaml (part)"
  - id: mark
    type: UPDATE_RECORD
    name: Mark the order
    contextKey: output
    config:
      target: "{{ orders.rows[0].id }}"
      targetModuleKey: x-shop-ext
      targetObjectKey: orders
      fieldUpdates:
        status: noted
        last_note: "{{ note.id }}"
```

| Key | Required | Meaning |
| --- | --- | --- |
| `target` | Yes | The record's id. `target: self` is refused, because a packaged step has no triggering record. |
| `targetModuleKey` | Yes | Always `x-<key>`. |
| `targetObjectKey` | Yes | An object of the package. |
| `fieldUpdates` | Yes | Field keys and their new values. |

The step has no result, so its effect in a test has no `response`. The three record steps above, scripted in order:

```yaml title="actions/note-order/tests.yaml"
- name: the note is added and the order marked
  input: { text: Call back on Monday }
  effects:
    - request: { step: FETCH_RECORDS, objectKey: orders }
      response:
        rows: [{ id: 7d1c2a34-0000-4000-8000-000000000001, number: A-1, status: open }]
        rowCount: 1
        truncated: false
    - request:
        step: CREATE_RECORD
        targetObjectKey: order-notes
        fieldMapping: { text: Call back on Monday, order: 7d1c2a34-0000-4000-8000-000000000001 }
      response: { id: 9b0e1f22-0000-4000-8000-000000000002 }
    - request:
        step: UPDATE_RECORD
        targetObjectKey: orders
        fieldUpdates: { status: noted, last_note: 9b0e1f22-0000-4000-8000-000000000002 }
  succeeds: true
```

## Run a query

`RUN_QUERY` runs one of the package's [queries](/docs/en/extensions/reference/queries) by its installed key. A FETCH query needs `queries:run`, a MUTATION query `queries:mutate`.

```yaml title="actions/count-open/rule.yaml"
entryStepId: close
steps:
  - id: close
    type: RUN_QUERY
    name: Close old orders
    contextKey: closed
    config:
      queryKey: x_shop_ext_close_old_orders
      params: { before: "{{ trigger.data.before }}" }
  - id: count
    type: RUN_QUERY
    name: Count open orders
    contextKey: output
    config:
      queryKey: x_shop_ext_open_orders
edges:
  - { fromStepId: close, toStepId: count }
```

| Key | Required | Meaning |
| --- | --- | --- |
| `queryKey` | Yes | `x_<key with _>_<name>`, the installed key of a query of the package. `queryId` is refused. |
| `params` | No | The query's parameters by name. Their values may use templates. |

A FETCH query's result is its list of rows, here `[{ open: 3 }]`. A MUTATION query's result is `{ operation, rowCount, rows }`. An action that declares output fields returns an object, so pick the values out with a `SAVE_TO_CONTEXT` step under `output` rather than returning the rows.

```yaml title="actions/count-open/tests.yaml"
- name: the old orders are closed and the open ones counted
  input: { before: "2025-11-01" }
  effects:
    - request:
        step: RUN_QUERY
        queryKey: x_shop_ext_close_old_orders
        params: { before: "2025-11-01" }
      response: { operation: UPDATE, rowCount: 2, rows: [] }
    - request: { step: RUN_QUERY, queryKey: x_shop_ext_open_orders }
      response: [{ open: 3 }]
  succeeds: true
```

## Update a contractor

`UPDATE_CONTRACTOR` changes one of the organization's contractors. With a call to a service before it, it keeps contractor data in step with that service.

```yaml title="actions/refresh-contractor/rule.yaml"
entryStepId: lookup
steps:
  - id: lookup
    type: CALL_WEBHOOK
    name: Ask the shop
    contextKey: customer
    config:
      url: "https://api.example.com/v1/customers?email={{ trigger.data.email }}"
      method: GET
  - id: store
    type: UPDATE_CONTRACTOR
    name: Store the phone
    config:
      contractorId: "{{ trigger.data.contractorId }}"
      fields: { phone: "{{ customer.body.phone }}" }
edges:
  - { fromStepId: lookup, toStepId: store }
```

| Key | Required | Meaning |
| --- | --- | --- |
| `contractorId` | Yes | The contractor, usually from the step's input. |
| `fields` | Yes | The contractor fields to change, such as `email`, `phone` or `website`. |

The step has no result, so its effect has no `response`:

```yaml title="actions/refresh-contractor/tests.yaml"
- name: the phone the shop has is stored
  input: { contractorId: c-1, email: ada@example.com }
  http:
    - request: { method: GET, url: "https://api.example.com/v1/customers?email=ada@example.com" }
      response: { status: 200, body: { phone: "+48 600 100 200" } }
  effects:
    - request:
        step: UPDATE_CONTRACTOR
        contractorId: c-1
        fields: { phone: "+48 600 100 200" }
  succeeds: true
```

## Generate a document

`GENERATE_DOCUMENT` renders a data document template of the organization. The template is never the package's choice: the organization's rule author picks it in your step's input. A package with this step lists `documents` in `requires.modules`.

| Key | Required | Meaning |
| --- | --- | --- |
| `templateId` | Yes | Exactly `{{ trigger.data.<field> }}`. Any other form is refused. |
| `data` | No | What the template renders. |
| `templateVersionId` | No | A version of the template; only its current published version renders. |
| `metadata` | No | Stored with the generated file. |
| `entityId`, `invoiceId` | Refused | A package renders data templates only, never a record. |

The result has `fileId`, `documentGenerationJobId`, `templateId`, `templateVersionId`, `mimeType` and `originalName`; pass `fileId` on to attach the file. When document generation is switched off for the organization, the step fails.

## Send an email

`SEND_EMAIL` sends through the installation's email service.

| Key | Required | Meaning |
| --- | --- | --- |
| `to` | Yes | The address. |
| `subject`, `html` | No | Written in the step. `bodyFormat`, `locale` and `data` are allowed too. |
| `attachmentFileIds` | No | File ids to attach, such as the document an earlier step generated. `fileIds` is an older name for it. Any file of the organization can be attached; see [Attachments](/docs/en/extensions/reference/data-permissions#the-scopes). |
| `accountId`, `templateId`, `cc`, `bcc`, `text`, `saveAsDraft` | Refused | A package sends no mail from a mailbox and picks no email template. |

The step has no result. Without an email service on the installation, it fails with `service_connection_not_configured`.

## Send a notification

`SEND_NOTIFICATION` sends the generic notification, with a title and a body, to members of the organization.

| Key | Required | Meaning |
| --- | --- | --- |
| `recipients` | Yes | Who receives it, for example `userIds`. Only active members of the organization receive it. |
| `title`, `body` | No | The notification's texts. |
| `linkUrl`, `payload`, `entityRef`, `dedupeKey`, `collapseWindowMinutes` | No | As in the rule builder. |
| `typeKey` | Refused | A package sends only the generic notification. |

The result is `{ notificationId, recipientCount, collapsed, suppressed }`.

## A document, an email and a notification

This action renders an order confirmation, emails it to the customer as an attachment and tells a colleague. It needs the scopes `documents:generate`, `email:send` and `notifications:send`. Its error edges keep the reason when a step fails.

```yaml title="actions/confirm-order/action.yaml"
action: confirm_order
label: Confirm order
description: Renders the confirmation, emails it to the customer and notifies a colleague.
input:
  templateId:
    type: text
    label: Document template
    help: A data document template of your organization.
    required: true
  number: { type: text, label: Order number, required: true }
  email: { type: text, label: Customer email, required: true }
  colleagueId: { type: text, label: Colleague to notify, required: true }
run: rule.yaml
tests: tests.yaml
expose:
  ruleStep: { category: notifications }
```

```yaml title="actions/confirm-order/rule.yaml"
entryStepId: render
steps:
  - id: render
    type: GENERATE_DOCUMENT
    name: Render the confirmation
    contextKey: document
    config:
      templateId: "{{ trigger.data.templateId }}"
      data:
        title: "Order {{ trigger.data.number }}"
  - id: mail
    type: SEND_EMAIL
    name: Email the customer
    contextKey: mail
    config:
      to: "{{ trigger.data.email }}"
      subject: "Order {{ trigger.data.number }} is confirmed"
      html: "<p>Your order {{ trigger.data.number }} is confirmed.</p>"
      attachmentFileIds: ["{{ document.fileId }}"]
  - id: notify
    type: SEND_NOTIFICATION
    name: Tell a colleague
    contextKey: output
    config:
      recipients:
        userIds: ["{{ trigger.data.colleagueId }}"]
      title: "Order {{ trigger.data.number }} confirmed"
      body: "The confirmation went to {{ trigger.data.email }}."
  - id: unavailable
    type: SAVE_TO_CONTEXT
    name: Keep the reason
    contextKey: failure
    config:
      value:
        code: "{{ error.code }}"
        message: "{{ error.message }}"
edges:
  - { fromStepId: render, toStepId: mail }
  - { fromStepId: mail, toStepId: notify }
  - { fromStepId: render, toStepId: unavailable, branchKey: error }
  - { fromStepId: mail, toStepId: unavailable, branchKey: error }
```

```yaml title="actions/confirm-order/tests.yaml"
- name: the confirmation is rendered, emailed with its file and announced
  input:
    templateId: tpl-1
    number: A-1
    email: customer@example.com
    colleagueId: user-2
  effects:
    - request:
        step: GENERATE_DOCUMENT
        templateId: tpl-1
        data: { title: Order A-1 }
      response:
        fileId: file-1
        documentGenerationJobId: job-1
        templateId: tpl-1
        templateVersionId: version-1
        mimeType: application/pdf
        originalName: document-job-1.pdf
    - request:
        step: SEND_EMAIL
        to: customer@example.com
        subject: Order A-1 is confirmed
        attachmentFileIds: [file-1]
    - request:
        step: SEND_NOTIFICATION
        recipients: { userIds: [user-2] }
        title: Order A-1 confirmed
      response:
        notificationId: notification-1
        recipientCount: 1
        collapsed: false
        suppressed: false
  succeeds: true
```

## When a data step fails

A failed data step fails your action like any step, unless an `error` edge catches it; that edge's step reads `{{ error.code }}` and `{{ error.message }}`. The organization's rule that uses your step sees `EXTENSION_ACTION_FAILED` when the action fails. A step that would reach outside the declared scopes when it runs fails with `EXTENSION_SCOPE_DENIED` and does nothing. An `UPDATE_RECORD` whose record id renders empty, as it does when an earlier step found nothing, fails with `EXTENSION_STEP_NO_TARGET`.

## Scripts get no data

A **Run Script** step, or a script an action runs, cannot read or write data or send notifications: in a package, scripts get no data helpers. Fetch the data with a step first, give it to the script through the context, and write the script's result with another step.

## Problems

| Code | Cause | Fix |
| --- | --- | --- |
| `step.scope_missing` | A data step whose scope the package does not declare. | Add the scope to `permissions.data`, with a reason. |
| `step.target_not_own` | A step names a module other than `x-<key>`, an object the package does not have, or a query key that is not `x_<key with _>_<name>` of a package query. | Name the package's own object or query. |
| `step.target_not_literal` | A module, object or query key comes from a template, a setting included. | Write the key out. |
| `step.config_not_allowed` | A refused key from the tables above, an update without a record id or with `target: self`, or a `templateId` that is not exactly `{{ trigger.data.<field> }}`. | Remove the key, or write it as the table says. |
| `step.type_not_allowed` | A step type no scope covers, such as `ATTACH_FILE` or `CALL_RULE`. | Move that work to the organization's rule that uses your step. |
| `action.verify_uses_data` | The connection's verify action uses a data step. | Keep the verify action to calls and logic. |
| `test.invalid` | A test case with `effects` in a package without data scopes. | Declare the scope, or remove the effects. |

`opero-ext` is the command-line tool for extensions. It scaffolds a package or exports one from your organization, checks it, writes the zip, runs its tests on Opero, uploads it, and plans, installs and upgrades it. It is one executable with Node.js inside; nothing else is needed.

The tool documents itself: `opero-ext <command> --help` prints a command's options, what it changes on the server, examples and the exit codes, and `opero-ext guide` prints the whole loop for an AI agent.

## Install

<Tabs items={['Linux, macOS', 'Windows']}>
<Tab value="Linux, macOS">

```bash title="Terminal"
curl -fsSL https://hub.kodasoft.pl/extension-cli/install.sh | sh
```

A given version instead of the latest:

```bash title="Terminal"
curl -fsSL https://hub.kodasoft.pl/extension-cli/install.sh | sh -s -- --version 1.4.0
```

The tool goes to `~/.opero/extension-cli/<version>/` and the command `~/.local/bin/opero-ext` points at it. If `~/.local/bin` is not on your `PATH`, the installer prints the line to add to your shell profile.

</Tab>
<Tab value="Windows">

In PowerShell:

```powershell title="PowerShell"
irm https://hub.kodasoft.pl/extension-cli/install.ps1 | iex
```

A given version instead of the latest:

```powershell title="PowerShell"
$env:OPERO_EXT_INSTALL_VERSION = '1.4.0'; irm https://hub.kodasoft.pl/extension-cli/install.ps1 | iex
```

The tool goes to `%LOCALAPPDATA%\Opero\extension-cli\<version>\`, the command is `%LOCALAPPDATA%\Opero\bin\opero-ext.cmd`, and that folder is added to your user `PATH`. Open a new terminal to use it.

</Tab>
</Tabs>

Neither needs administrator rights or writes outside your own folders. Both download from the Kodasoft Hub over HTTPS only, check the archive's size and SHA-256 against the release manifest, and check that the new executable starts before switching to it. Earlier versions stay installed.

| Platform | Supported |
| --- | --- |
| Linux | x64 and arm64, with glibc (Debian, Ubuntu, Fedora, …). Alpine and other musl systems are not supported. |
| macOS | Apple silicon and Intel. |
| Windows | x64. |

**The release signature.** Each release manifest is signed by Kodasoft. `install.sh` checks the signature when OpenSSL 3 is installed. macOS ships LibreSSL, which cannot check it: the installer then says so and relies on the SHA-256 and HTTPS; install OpenSSL 3 (for example `brew install openssl@3`), put it first on your `PATH` and run the installer again if you want the signature checked. `install.ps1` never checks it (PowerShell cannot) and says so. `opero-ext update` always checks it.

**Downloaded with a browser.** The one-liners start the tool without a prompt. If you download an archive with a browser instead, the system may stop it the first time:

- macOS, "cannot be opened because the developer cannot be verified": run `xattr -d com.apple.quarantine opero-ext`, or choose **Open Anyway** in System Settings → Privacy & Security.
- Windows, "Windows protected your PC": choose **More info** → **Run anyway**.

## Update

```bash title="Terminal"
opero-ext version
opero-ext update
opero-ext update --version 1.4.0
```

`version` prints the version, the build, the platform and the Node.js inside; `opero-ext --version` prints the version alone.

`update` installs the release Kodasoft marked as the latest, or with `--version` a given one, also an older one to go back. It refuses a release that is unsigned, signed with a key the tool does not know, or whose archive does not match the manifest, and then changes nothing (exit 1). The new version gets its own folder and the command switches to it at once; the previous version is kept. When you already run the latest, it says so.

## Commands

| Command | Does | Server | Extension authoring module |
| --- | --- | --- | --- |
| `init <folder>` | Writes a working package with one action. | No | |
| `add action <name>` | Adds an action folder and lists it in the manifest. | No | |
| `add filter <name>` | Adds a filter folder and lists it. | No | |
| `add trigger <name>` | Adds a trigger folder and lists it. | No | |
| `add schedule <name> --action <action>` | Adds a schedule folder that runs the action, and lists it. | No | |
| `add block <name>` | Adds a block folder with its HTML, CSS and a render test, and lists it. | No | |
| `add link <name>` | Adds a record link folder and lists it. | No | |
| `add form <name> --object <object>` | Adds a form folder with its layout for an object of the package, and lists it. | No | |
| `add list <name>` | Adds a Custom List folder and lists it. | No | |
| `add page <name>` | Adds a workspace page folder with its layout, and lists it. | No | |
| `validate <folder or zip>` | Checks the package offline. | No | |
| `pack <folder>` | Checks, then writes the zip. | No | |
| `types [folder]` | Writes `.opero/types/index.d.ts`, with the `Settings` type from `settings.yaml` and the `Triggers` type with each trigger's data. | No | |
| `schema [folder]` | Writes `.opero/schemas/`, the editor schemas, including one for `settings.yaml`. | No | |
| `login` | Signs you in with Opero in the browser. | Yes | |
| `orgs` | Lists your organizations and their ids. | Yes | |
| `list` | Lists the organization's installed extensions and the versions it may install. | Yes | |
| `pull <folder>` | Exports the organization's own dictionaries, objects, saved queries, template filters, Custom Blocks, forms, Custom Lists and workspace pages as a new package folder. See [Start from your organization](/docs/en/extensions/start-from-your-organization). | Yes | Needed |
| `test <folder or zip>` | Runs every test case and block render case on the server and prints each result. Stores nothing. | Yes | Needed |
| `push <folder or zip>` | Uploads as a private package. | Yes | |
| `plan [folder or zip]` | Uploads, then prints what installing or upgrading would do, and the plan hash. | Yes | |
| `install [folder or zip]` | Uploads, plans, asks for your consent and installs. | Yes | |
| `upgrade [folder or zip]` | Uploads, plans, asks for your consent and upgrades an installed extension. | Yes | |
| `guide` | Prints the authoring loop for an AI agent. | No | |
| `version` | Prints the version, build, platform and Node.js. | No | |
| `update` | Installs the latest release, signature checked. | Kodasoft Hub | |

Only `pull` and `test` need the organization's **Extension authoring** module. Uploading, planning, installing and upgrading do not, and neither does running an installed extension. Without the module, `pull` and `test` stop with exit 4.

There is no `add` command for objects, dictionaries and queries: create their folders by hand and list them in `extension.yaml`, or export them with `pull`. See [Objects](/docs/en/extensions/reference/objects), [Dictionaries](/docs/en/extensions/reference/dictionaries) and [Queries](/docs/en/extensions/reference/queries). `validate` checks them, including the SQL file's object placeholders, and `pack` packs each query's `.sql` file. `schema` writes editor schemas for `object.yaml`, `dictionary.yaml` and `query.yaml` too.

There is no `add` command for the member connection: write `connection/member.yaml` by hand and name it in `connection.yaml` with `member: member.yaml`. See [Member connections](/docs/en/extensions/reference/member-connections). `schema` writes editor schemas for `trigger.yaml`, `schedule.yaml` and `member.yaml` too.

There is no `add` command for settings either, and `init` writes none: create `settings.yaml` by hand and name it in `extension.yaml` with `settings: settings.yaml`. See [Settings](/docs/en/extensions/reference/settings). `validate` checks it with the rest of the package and, for a valid folder, refreshes the types and editor schemas.

## Signing in

Every command that talks to Opero takes `--server <mcp-url>`, your Opero's MCP address, and `--org <organizationId>` when you belong to more than one organization (without it such a command stops with exit 2).

```bash title="Terminal"
opero-ext login --server https://opero.example.com/mcp
opero-ext orgs --server https://opero.example.com/mcp
```

`login` opens the browser for **Sign in with Opero**. A person must finish it; an AI agent cannot, and asks you to run it. The tool then acts as you, with your permissions in each organization. The sign-in is kept per server in `~/.config/opero-extension-cli/credentials.json`, readable by you only, and refreshed when it runs out. An organization that requires MFA or SSO refuses a sign-in made without it (exit 3): sign in to Opero that way, then run `login` again.

`orgs` lists the organizations you belong to with their ids, for `--org`.

## Options

<Accordions type="multiple">
<Accordion title="init">

```bash title="Terminal"
opero-ext init hello-ext --name Hello --publisher "Your company" --typescript
```

| Option | Meaning |
| --- | --- |
| `--key <key>` | The extension's key. By default the folder name. |
| `--name <name>` | The package's name. By default from the key. |
| `--publisher <name>` | Your company's name. |
| `--typescript` | Write scripts as `.ts`, with a `tsconfig.json`. |

It refuses to overwrite files that exist. Then fill in the description, the reasons of any permission, and real tests.

</Accordion>
<Accordion title="add action, add filter">

```bash title="Terminal"
opero-ext add action greet --rule
opero-ext add filter shout
```

| Option | Meaning |
| --- | --- |
| `--rule` | Start the action from a rule file with a script step instead of a script alone. Actions only. |
| `--module <folder>` | Add it to an included module instead of the manifest. |
| `--package <folder>` | The package folder, when you run the command from elsewhere. By default the current folder. |
| `--typescript` | Write the script as `.ts`. |

`add` keeps your comments in `extension.yaml`. When the file ends with a comment, it inserts one blank line before that comment.

</Accordion>
<Accordion title="add trigger, add schedule">

```bash title="Terminal"
opero-ext add trigger order_changed
opero-ext add schedule sync_orders --action sync_orders --every 1h --for-each company
```

`add trigger` writes `triggers/<name>/trigger.yaml` (the name with `-` for `_`) with one data field, one filter and an example to replace, and lists the folder.

`add schedule` writes `schedules/<name>/schedule.yaml` and lists the folder:

| Option | Meaning |
| --- | --- |
| `--action <name>` | The action it runs. Required. It must be an action of the package that is not exposed as a step, and a member action exactly when `--for-each userConnection`. |
| `--every <interval>` | `15m`, `30m`, `1h`, `2h`, `6h`, `12h` or `24h`. By default `1h`. |
| `--for-each <subject>` | `installation`, `company` or `userConnection`. By default `company`. |
| `--module <folder>` | Add it to an included module instead of the manifest. |
| `--package <folder>` | The package folder, when you run the command from elsewhere. |

Both refuse a name the package already uses and a package that is not valid to begin with.

</Accordion>
<Accordion title="add block, add link">

```bash title="Terminal"
opero-ext add block status_card
opero-ext add link open_it
```

`add block` writes `blocks/<name>/` (the name with `-` for `_`) with `block.yaml`, `block.html`, `block.css` and a `tests.yaml` with one render case, and lists the folder. Add a script yourself, with `permissions.pageScript`.

`add link` writes `links/<name>/link.yaml`, a link to a contractor's page at `app.example.com` that requires the package permission `openLinks`, and lists the folder. The package is not valid until you declare the host in `permissions.links` and the permission in `permissions.company`, or change the link to your own; the command says so.

| Option | Meaning |
| --- | --- |
| `--module <folder>` | Add it to an included module instead of the manifest. |
| `--package <folder>` | The package folder, when you run the command from elsewhere. |

Both refuse a name that is not lower-case letters, digits and `_`.

</Accordion>
<Accordion title="add form, add list, add page">

```bash title="Terminal"
opero-ext add form quick --object orders
opero-ext add list all-orders --object orders
opero-ext add page order-desk
```

`add form` writes `forms/<name>/` with `form.yaml`, for the view, edit and create types and claiming the object's default slots, and a `layout.yaml` with a card holding the object's first five fields, and lists the folder. The object must be one of the package's.

`add list` writes `lists/<name>/list.yaml` and lists the folder: with `--object`, a list over that object with a column for each of its first five fields; without it, a list over the built-in `contractors` source.

`add page` writes `pages/<name>/` with `page.yaml`, a workspace page, and an empty `layout.yaml` with a comment showing how to embed a list, and lists the folder.

| Option | Meaning |
| --- | --- |
| `--object <name>` | `add form`: the package object the form is on. Required. `add list`: the package object it lists. |
| `--module <folder>` | Add it to an included module instead of the manifest. |
| `--package <folder>` | The package folder, when you run the command from elsewhere. |

A form name is lower-case letters, digits and `_`; a list or page name is lower-case words joined by `-`. `schema` writes editor schemas for `form.yaml`, `list.yaml`, `page.yaml` and their layout files. See [Forms, lists and pages](/docs/en/extensions/reference/screens).

</Accordion>
<Accordion title="validate, pack">

```bash title="Terminal"
opero-ext validate .
opero-ext pack . --out hello.zip
```

`validate` reads a folder or a zip as Opero will and prints every problem. For a valid folder it writes `.opero/` again (script types and editor schemas).

| Option | Meaning |
| --- | --- |
| `--out <file.zip>` | `pack` only. The zip's name. By default `<key>-<version>.zip`. |
| `--json` | `validate` only. See [JSON output](#json-output). |

The zip holds only the files `extension.yaml` reaches; TypeScript is packed as the built `.js`. The same folder always produces the same zip, byte for byte.

</Accordion>
<Accordion title="pull">

```bash title="Terminal"
opero-ext pull ./orders --server https://opero.example.com/mcp --org <organizationId> \
  --key orders --name Orders --publisher "Your company" \
  --select object:sales.orders --select block:order_summary
```

| Option | Meaning |
| --- | --- |
| `--key <key>` | The package's key, without the `x-` prefix. Required. |
| `--name <name>` | The package's name. Required. |
| `--publisher <publisher>` | Who publishes the package. Required. |
| `--version <version>` | The package's version. By default `0.1.0`. |
| `--select <kind:ref>` | An asset to export; repeat it for each. Required. `dictionary:<key>`, `object:<moduleKey>.<objectKey>`, `query:<key>`, `filter:<key>`, `block:<key>`, `form:<id>`, `list:<key>` or `page:<slug>`. |
| `--force` | Write into a folder that is not empty, overwriting only the files the export writes. |

The folder must be new or empty. The command prints what it wrote, what it added because a selected asset needs it, what it left out and why, and what you must still write before uploading. [Start from your organization](/docs/en/extensions/start-from-your-organization) explains the export.

</Accordion>
<Accordion title="test, push">

```bash title="Terminal"
opero-ext test . --server https://opero.example.com/mcp --org <organizationId>
opero-ext push . --server https://opero.example.com/mcp --org <organizationId>
```

`test` prints one row per case; the **Part** column names the action, or `block <name>` for a block's render case. It needs the Extension authoring module.

`push` checks the package offline, then uploads it as a private package of the organization. Opero runs the same checks and the tests first and stores nothing when they fail. Sending the same bytes again answers the stored version; other bytes for a version that exists are refused (exit 6): raise `version` in `extension.yaml`.

</Accordion>
<Accordion title="list, plan">

```bash title="Terminal"
opero-ext list --server https://opero.example.com/mcp --org <organizationId>
opero-ext plan . --server https://opero.example.com/mcp --org <organizationId>
```

`list` shows the installed extensions (key, version, status, whether each runs and why not, and its revision) and every version the organization may install: its own private packages and the catalog packages granted to it, each with its package id.

`plan` uploads the folder or zip like `push`, or takes a stored version with `--package-id <id>`, and prints what installing or upgrading to it would do: the permissions with their reasons, what it adds, triggers, schedules, the member connection, package permissions, blocks, member actions, links, the changes, data loss, problems, and the plan hash. A blocked plan exits 1. The plan itself changes nothing.

</Accordion>
<Accordion title="install, upgrade">

```bash title="Terminal"
opero-ext install . --server https://opero.example.com/mcp --org <organizationId>
opero-ext upgrade . --server https://opero.example.com/mcp --org <organizationId>
```

| Option | Meaning |
| --- | --- |
| `--package-id <id>` | Use a stored version (from `list`) instead of a folder or zip. |
| `--plan-hash <hash>` | Consent to the plan with this hash; acts without a question. |
| `--yes` | On a terminal: consent without the y/N question. |
| `--confirm-data-loss` | `upgrade`: confirm the plan's data loss. |

Both install any version the organization may install: its own private packages and the catalog packages granted to it. Sending `install` again resumes a failed install; an extension that is already installed exits 6, so use `upgrade`. For `upgrade`, raise `version` in `extension.yaml` first. The installation's revision is read when the command starts; if it changes in between, the command exits 6. A disabled extension stays disabled after an upgrade.

</Accordion>
</Accordions>

## Consent

Installing or upgrading grants what the plan lists: the permissions the package asks for, with their reasons, what it adds, its triggers, schedules, member connection, package permissions, blocks, member actions and links, and on an upgrade the data it deletes. `install` and `upgrade` therefore print the plan and act only with your consent:

- **On a terminal** they ask y/N. A plan with data loss also asks you to type the extension's key. `--yes` skips the first question only.
- **Without a terminal, or with `--json`,** they act only with `--plan-hash <hash>` from a fresh plan, and on an upgrade that drops data also `--confirm-data-loss`. Without them they print the plan, change nothing and exit 5.
- **The hash is checked against a plan made at that moment.** If anything changed since you saw it (the package, the organization, the installed revision), the hash differs and the command exits 5: plan again.

So a script or an AI agent runs `opero-ext plan . --json`, shows you the plan, and only after you agree runs:

```bash title="Terminal"
opero-ext install --package-id <packageId> --plan-hash <planHash> \
  --server https://opero.example.com/mcp --org <organizationId>
```

The consent is always yours. An agent must not pass a `--plan-hash` whose plan it did not show you, or `--confirm-data-loss` you did not give.

## JSON output

`--json` works with `orgs`, `list`, `plan`, `install`, `upgrade`, `push`, `test`, `pull`, `validate`, `version` and `update`. The command then asks nothing and prints one JSON document:

```json title="Success"
{ "ok": true, "command": "plan", "data": { "package": {}, "plan": {} } }
```

```json title="Failure"
{
  "ok": false,
  "command": "install",
  "exitCode": 5,
  "reason": "consent_required",
  "message": "…",
  "errors": [{ "code": "…", "message": "…" }],
  "data": { "package": {}, "plan": {} }
}
```

`data` on a failure holds what was learned before it, for example the plan to show. Notes and warnings go to standard error. Branch on the exit code, not on the text.

## Exit codes

| Code | Meaning | What to do |
| --- | --- | --- |
| `0` | Done. | |
| `1` | The package or the server refused. The problems are printed (with `--json`, in `errors`). | Fix what they say. |
| `2` | Usage error: a wrong argument or option, or `--org` missing while you belong to several organizations. | Read `--help`; pass `--org`. |
| `3` | Not signed in, the sign-in expired, or the organization refused it (MFA or SSO required). | Run `opero-ext login`. |
| `4` | The organization does not have the Extension authoring module, or the licence does not allow it. Only `test` and `pull` need it. | Ask an administrator to switch it on. |
| `5` | Consent missing: no terminal and no `--plan-hash`, a `--plan-hash` that is not the current plan's, data loss not confirmed, or you declined. | Plan again, review, consent. |
| `6` | Conflict: the version exists already, the installation changed since it was read, the extension is already (or not yet) installed, or another operation is running. | Raise the version, use `upgrade` or `install`, or run it again. |
| `7` | The server could not be reached or failed. | Try again later. |

## Reading a problem

A problem prints as its code, then `file:line #/place`, then the message:

```txt title="Output"
  rule.host_not_declared  actions/greet/rule.yaml:9 #/steps/0/config/url
    Host "api.httpbin.org" is not listed in permissions.network.
```

The offline check covers the files and their shape, including the data scopes each step needs and the action keys, queries, objects and blocks a block names; only the server can run the tests and render the blocks. The fields of a link on a built-in record are checked by the server too. A query's SQL and an object's field types are checked by the install plan. [Error codes](/docs/en/extensions/error-codes) lists every code.

## The working loop

<Steps>
<Step>
Start with `init`, or with `pull` from your organization's own configuration.
</Step>
<Step>
Run `validate` after every edit. It is offline and fast, and keeps `.opero/` types in step with your descriptors.
</Step>
<Step>
Run `test` when the files are valid.
</Step>
<Step>
Run `plan` to see what the package would do, then `install`, or `upgrade` after raising the version. You can also run `push`, or upload the zip from `pack`, and install in Opero.
</Step>
</Steps>

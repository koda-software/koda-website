title: Blocks

---

A block is a piece of a page: HTML written with Liquid, with its own CSS and, when the package declares it, a script that runs in the viewer's browser. An installed block is a Custom Block of the organization, placed on record pages and custom pages like its own blocks, that shows the package's data and runs the package's actions. The guide [A block, a button and a link](/docs/en/extensions/blocks-and-actions) builds one.

```yaml title="blocks/parcel-list/block.yaml"
block: parcel_list
label: Parcels by status
description: The parcels in one status, and the five newest parcels.
html: block.html
css: block.css
inputs:
  status:
    type: select
    label: Status
    options: [new, in_transit, delivered]
    default: in_transit
queries:
  parcels:
    query: parcels_by_status
    params: { status: "{{ inputs.status }}" }
    rowLimit: 50
records:
  newest:
    object: parcels
    fields: [number, status]
    sort: [{ field: number, direction: desc }]
    limit: 5
refresh: { intervalSeconds: 300 }
tests: tests.yaml
```

List the folder under `blocks` in `extension.yaml` or an included module's `module.yaml`. `opero-ext add block <name>` writes a block with its HTML, CSS and one render test, and lists it. A package has at most 50 blocks.

## Inputs

An input is a value each placement of the block chooses: a title, a status, a record. Its key is a lower-case letter followed by letters, digits and `_`, up to 64 characters.

```yaml
inputs:
  title: { type: text, label: Title, default: Parcels }
  status: { type: select, label: Status, options: [new, in_transit, delivered], default: in_transit }
  parcel: { type: record, object: parcels, label: Parcel, required: true }
```

A value of the wrong type falls back to the default. A `rows` input holds a list of objects, usually passed by another block that renders this one.

## Queries

A block runs up to five of the package's own [queries](/docs/en/extensions/reference/queries), by their name in `query.yaml`. Only FETCH queries can be shown.

```yaml
queries:
  parcels:
    query: parcels_by_status
    params: { status: "{{ inputs.status }}" }
    rowLimit: 50
```

| Key | Meaning |
| --- | --- |
| `query` | The name of a query of the package (`block.unknown_query` otherwise). It is installed as `x_<key>_<name>`, and the block runs that query. |
| `params` | A value for each of the query's parameters: a literal, or Liquid such as `"{{ inputs.status }}"`. Strings are converted to the parameter's type. |
| `rowLimit` | 1 to 500 rows. 100 when left out. |

The result is `queries.<key>` in the HTML: `rows`, `first`, `rowCount`, `hasMore` and `state` (`ready`, or `error` or `unavailable` when the query could not run, with no rows). One query that fails never fails the block. On a company page the query runs in that company. Like every saved query, it does not apply own-record visibility.

The install review checks the parameters against the query. A block may also name a query the same install creates.

## Record reads

A record read lists records of one of the package's own [objects](/docs/en/extensions/reference/objects) through Opero's record access, as the viewer: a member sees only the records they may see, in the company of the page.

A block that shows one record, such as "this parcel", must filter its read. Without a filter, a read lists the object's records, newest first, and the block would show the newest parcel instead of the chosen one. Here the placement picks the parcel in a record input, and the read filters on it:

```yaml
inputs:
  parcel: { type: record, object: parcels, label: Parcel, required: true }
records:
  parcel:
    object: parcels
    fields: [number, status]
    limit: 1
    filter: { op: AND, items: [{ field: id, operator: eq, value: "{{ inputs.parcel }}" }] }
```

| Key | Meaning |
| --- | --- |
| `object` | An object of the package, by its key (`block.unknown_object` otherwise). |
| `fields` | 1 to 50 field keys each row carries, besides `id`, `created_at` and `updated_at`. |
| `filter` | A filter group, written as a Custom List's base filter: `{ op: AND, items: [{ field, operator, value }] }`. A `value` may be Liquid, rendered with the block's context: `inputs`, and `record`, `company` and the rest of what the HTML sees. Checked by the install review. |
| `sort` | Up to 5 `{ field, direction }` entries. Newest first when left out. |
| `limit` | 1 to 50 rows. 10 when left out. |

The result is `records.<key>`: `rows`, `first`, `total` (every match, not only the rows shown) and `state`. A read the viewer may not make is `unavailable`, with no rows. A block that reads records cannot be rendered by another block.

## The HTML

The HTML is Liquid, rendered on the server each time the page shows the block. It can use:

| Write | To get |
| --- | --- |
| `{{ inputs.<key> }}` | An input, as the placement filled it in, or its default. |
| `{{ queries.<key>.rows }}` | The rows of a query; also `first`, `rowCount`, `hasMore`, `state`. |
| `{{ records.<key>.rows }}` | The rows of a record read; also `first`, `total`, `state`. |
| `{{ record.<field> }}`, `{{ record.id }}` | On a record page: the record the page shows. Empty on a custom page. |
| `{{ company.name }}`, `{{ actor.locale }}`, `{{ today }}` | The company of the page, the viewer's language (`pl` or `en`), the company's calendar day; also `company.id`, `now` and the rest of the page's Liquid. |
| `extension_actions['x-<key>.<action>']` | Whether the viewer may run that block action. See [Buttons that run actions](#buttons-that-run-actions). |

```html title="blocks/parcel-list/block.html"
<section class="parcels">
  <ul>
    {% for parcel in queries.parcels.rows %}
      <li>{{ parcel.number }} {% render 'x_parcels_status_badge', status: parcel.status %}</li>
    {% else %}
      <li>No parcels.</li>
    {% endfor %}
  </ul>
  <p>Newest: {% for parcel in records.newest.rows %}{{ parcel.number }} {% endfor %}</p>
</section>
```

- **Opero's built-in filters only.** A package block renders with the filters every installation has. The organization's own template filters, and those of extensions, including your own package's, are not available.
- **Render another block of the package** with `{% render 'x_<key>_<block>', name: value %}`, by its installed key. The rendered block reads each argument as `inputs.<name>`, runs no queries, and blocks render each other at most three levels deep, without a cycle. Only the package's own blocks can be rendered (`block.render_not_own`), and the key must be written out (`block.reference_not_literal`).
- **One language.** The HTML is not translated. Use `actor.locale` to choose between texts.
- A name that does not exist renders as empty, without an error.

## Buttons that run actions

A button with `data-opero-action="run-action"` runs an action of the package that is exposed to blocks (`expose.blockAction`), for the record the page shows, or without a record on a custom page. `data-action` names its final key, `x-<key>.<action>`:

```html title="blocks/parcel-card/block.html"
{% if extension_actions['x-parcels.track_parcel'] %}
  <button type="button" data-opero-action="run-action"
          data-action="x-parcels.track_parcel">Track now</button>
{% endif %}
```

| Attribute | Meaning |
| --- | --- |
| `data-action` | `x-<key>.<action>`, written out. It must name an action of this package with `expose.blockAction` (`block.unknown_action`). |
| `data-input` | Optional. The action's input, as a JSON object: `data-input='{"note": "{{ inputs.note }}"}'`. Checked against the action's input fields when the button is pressed. |
| `data-confirm` | Optional. A question the member answers before the action runs. |

`extension_actions['<key>']` is `true` when the viewer may run the action and `false` otherwise, so the block can leave the button out for them. Opero checks again when the button is pressed. Who may run an action is described in [Block actions and record commands](/docs/en/extensions/reference/member-actions#who-may-use-them).

When the action finishes, its output reaches the block:

- the block's root element receives the event `opero:action-done`, with `event.detail` holding `{ action, output, message }`;
- a `message` text in the output is shown to the member;
- the block is then refreshed.

A failure shows its message to the member. A package block may run only its package's actions: the other Custom Block actions are refused. `run-rule` is `block.rule_unsupported`, and `open-form`, `set-field` and `<opero-rating>` are `block.form_unsupported`.

## The script

A block script runs in the viewer's browser after each render of the block. It needs `permissions.pageScript` in `extension.yaml`, with a reason the administrator reads before installing:

```yaml title="extension.yaml"
permissions:
  pageScript:
    reason: The parcel card keeps the carrier's last answer on screen while the page is open.
```

Like every script of a package, it is a module with one `export default` function. The function receives `ctx`, the block's context:

```js title="blocks/parcel-card/block.js"
/** @type {import('../../.opero/types').Block} */
export default function parcelCard(ctx) {
  const answer = ctx.dom.querySelector('[data-answer]');
  const last = ctx.state.get('answer');
  if (answer && typeof last === 'string') answer.textContent = last;
  ctx.dom.root.addEventListener('opero:action-done', (event) => {
    const message = event.detail?.output?.message;
    if (typeof message !== 'string' || !answer) return;
    ctx.state.set('answer', message);
    answer.textContent = message;
  });
}
```

| `ctx` member | Gives |
| --- | --- |
| `ctx.dom.root`, `ctx.dom.querySelector(…)` | The block's markup, and a search inside it. The markup is new after each refresh. |
| `ctx.inputs`, `ctx.data.queries` | The inputs and the query results the server render used. |
| `ctx.state` | `get`, `set`, `has`, `delete`, `keys`: values kept across the block's refreshes while the page is open. |
| `ctx.actions.run('run-action', { action, input })` | Runs a block action from the script. It resolves with `{ outcome, output, message }`, and is rejected with the message of a failure. The key must be written out as a whole text in the script. |
| `ctx.record`, `ctx.user` | The page's record (saved values) and the viewer. |
| `ctx.notifications` | `success`, `warning`, `error`: a message to the viewer. |

The function may return a function that cleans up before the next run. A script cannot reach `document`, `window`, timers or the network. `.opero/types` declares `Block`, the type of the function.

## Render tests

Each block has a `tests.yaml` with 1 to 20 render cases. Opero renders every case at upload, and `opero-ext test` does on the server, after the action tests. `opero-ext validate` checks only their shape.

```yaml title="blocks/parcel-list/tests.yaml"
- name: lists the parcels of the chosen status
  inputs: { status: delivered }
  queries:
    parcels: [{ number: P-1, status: delivered }]
  records:
    newest: [{ number: P-2, status: new }]
  contains: ["P-1", "badge--delivered", "Newest: P-2"]
- name: says so when there are none
  contains: ["No parcels."]
```

Nothing is read or run: no query, no record read, no script. Blocks of the package rendered with `{% render %}` work. A case fails with `test.render_mismatch` at the text that did not match, or with `test.render_failed` when the template does not render, for example because it uses a filter outside Opero's built-in ones. Render cases count toward the 200 tests of a package and share its 60 seconds.

## The installed block

A block is installed as a managed Custom Block with the key `x_<key with _>_<block>`. The organization places it and fills in its inputs, but cannot change or archive it, and its own blocks cannot use keys that start with `x_`. While the extension is disabled, the block shows a notice instead of its HTML and runs no queries. See [Managed assets](/docs/en/extensions/after-install#managed-assets).

## Upgrades

| Change in a new version | What happens | Code |
| --- | --- | --- |
| A block keeps its `block` name | It keeps its identity and its placements. | |
| A placed block is dropped | It is archived, and its placements show that the extension removed it. A version that has the block again brings it back. A warning. | `block.removed_placed` |
| A change would break the pages that place the block or the blocks that render it | Blocked. | `block.breaking_change` |
| A block action that one of the organization's own blocks names is dropped | Blocked until that block changes. | `block_action.in_use` |
| A block newly asks for page scripts | It is shown as new in the review, for the administrator to agree to. | |

An uninstall archives the blocks; their placements stay and show that the extension was removed, and installing it again brings the same blocks back. What the administrator sees is in [Upgrade and uninstall](/docs/en/extensions/upgrade-and-uninstall#what-a-new-version-can-change).

## Translations

A block's `label` and `description` go under `blocks.<block>`. Its HTML is not translated: use `actor.locale` to choose between texts. See [Translations](/docs/en/extensions/reference/translations#translatable-keys).

## Problems

| Code | Cause | Fix |
| --- | --- | --- |
| `block.invalid` | An unknown key, a key of the wrong shape, a file that is not in the block's folder or is over its size, blocks rendering each other more than three levels deep, or more than 50 blocks. | Fix the key or the file the message names. |
| `block.name_too_long` | The installed key `x_<key with _>_<block>` is over 64 characters. | Shorten the block's name. |
| `block.test_missing` | A block without a render case. | Add a case to its `tests.yaml`. |
| `block.unknown_query` | A query the package does not have. | Fix the name, or add the query. |
| `block.unknown_object` | A record read or record input names an object the package does not have. | Fix the key, or add the object. |
| `block.unknown_action` | `data-action` names no action of the package exposed to blocks. | Add `expose.blockAction` to the action, or fix the key. |
| `block.reference_not_literal` | An action key or a rendered block's key built from a template. | Write the key out. |
| `block.render_not_own` | `{% render %}` names a block that is not the package's. | Render only `x_<key with _>_<block>` keys of the package. |
| `block.render_cycle` | Blocks of the package render each other in a circle. | Break the circle. |
| `block.rule_unsupported` | A `run-rule` button. | Run the package's action with `run-action`. |
| `block.form_unsupported` | `open-form`, `set-field` or `<opero-rating>`. | Change the record with a block action. |
| `block.script_undeclared` | A block with a script in a package without `permissions.pageScript`. | Declare it, with a reason. |
| `permissions.unused_page_script` | `permissions.pageScript` in a package whose blocks have no script. | Remove it. |
| `block.adopts_existing` | In the install review: a block with that key exists and is not the extension's. Blocks the install. | Rename the block, or ask the organization to rename theirs. |
| `block.save_validation` | In the install review: the block would not save as a Custom Block. Blocks the install. | Fix the block as the message says. |
| `test.render_mismatch`, `test.render_failed` | A render case found a text that did not match, or the template did not render. | See [Render tests](#render-tests). |

title: Tests
description: Write the test cases every action needs. They script the calls and data steps an action makes, and Opero runs them offline at every upload.
---

Every action has at least one test case. A case gives an input, scripts the HTTP calls and data steps the action is expected to make, and says how it ends. Opero runs every case at upload, and on demand through `opero-ext test`, without sending anything over the network, reading or writing any data, or starting any rule. [Part 3 of the tutorial](/docs/en/extensions/tutorial/check-and-pack) runs them.

```yaml title="actions/greet/tests.yaml"
- name: the greeting is sent
  input: { name: Ada }
  settings: { language: pl }
  connection: { token: test-token }
  http:
    - request:
        method: POST
        url: https://httpbin.org/anything?lang=pl
        headers: { authorization: Bearer test-token }
        body: { greeting: "Hello, Ada!" }
      response:
        status: 200
        headers: { content-type: application/json }
        body: { json: { greeting: "Hello, Ada!" } }
  returns:
    status: 200
    headers: { content-type: application/json }
    body: { json: { greeting: "Hello, Ada!" } }
```

## A test case

A test file is a list of cases. Each case has a name, what the action runs with, and exactly one [outcome](#how-a-case-ends).

## HTTP exchanges

Each entry of `http` is a `request` the action must send next and the `response` it gets back.

| Key | Meaning |
| --- | --- |
| `request.method` | `GET`, `POST`, `PUT`, `PATCH` or `DELETE`. Required. |
| `request.url` | The whole `https://` URL, query included. Required. |
| `request.headers` | Headers that must be sent with these values. Names match in any case; headers you leave out are not compared. |
| `request.body` | The body, compared exactly when given. A JSON body is compared as JSON. |
| `response.status` | The status the action gets, `100` to `599`. Required. |
| `response.headers`, `response.body` | What else the action gets back. |

The values Opero puts in for secrets are in the request before it is compared, so a case checks `Bearer test-token` with the `token` it gives under `connection`.

## Settings in a case

The settings of a case, with the defaults applied, must match `settings.yaml`. A required setting without a default is therefore given in every case, also in the cases of actions that do not read it. See [Settings in tests](/docs/en/extensions/reference/settings#settings-in-tests).

## Data and messaging steps

When the action's rule uses [data steps](/docs/en/extensions/reference/data-steps), the case scripts them in `effects`, the way `http` scripts the calls. No record is read or written and nothing is sent: each step is compared with its effect and returns the effect's `response`.

```yaml title="actions/sync-order/tests.yaml"
- name: the open order gets the status the carrier answers
  input: { status: synced }
  http:
    - request:
        method: POST
        url: https://api.example.com/v1/orders
        body: { number: A-1, status: synced }
      response: { status: 200, body: { status: synced } }
  effects:
    - request: { step: FETCH_RECORDS, objectKey: orders }
      response:
        rows: [{ id: 7d1c2a34-0000-4000-8000-000000000001, number: A-1, status: open }]
        rowCount: 1
        truncated: false
    - request:
        step: UPDATE_RECORD
        targetObjectKey: orders
        fieldUpdates: { status: synced }
  succeeds: true
```

| Key | Meaning |
| --- | --- |
| `request.step` | The step type: `FETCH_RECORDS`, `CREATE_RECORD`, `UPDATE_RECORD`, `RUN_QUERY`, `UPDATE_CONTRACTOR`, `SEND_EMAIL`, `SEND_NOTIFICATION` or `GENERATE_DOCUMENT`. Required. |
| Other `request` keys | Keys of the step's settings, compared with what the step was given after its templates were filled in. Keys you leave out are not compared. |
| `response` | What the step returns, in the shape the real step returns. Leave it out for `UPDATE_RECORD`, `UPDATE_CONTRACTOR` and `SEND_EMAIL`, which return nothing. |

`effects` and `http` are two separate lists, each in the order the action uses them. A `RUN_QUERY` effect names the query by its installed key, as the rule does: `queryKey: x_orders_ext_orders_by_day`. Each step is checked against the package's data scopes before it takes its effect, so a test cannot pass with a step the scopes do not allow.

## Events

For an action whose rule uses [`EMIT_EVENT`](/docs/en/extensions/reference/raising-events), `events` lists the events the run must raise, and `seen` says what Opero already remembers when the case starts, to test dedupe.

```yaml title="actions/sync-orders/tests.yaml"
- name: an order seen before, unchanged, raises nothing
  input: { subject: { kind: company, companyId: co_1 }, lastSucceededAt: "2026-11-02T10:00:00Z", firstRun: false }
  seen:
    - { event: order_changed, key: A-1, data: { number: A-1, status: open, total: 120.5 } }
  http:
    - request:
        method: GET
        url: https://api.example.com/v1/orders?company=co_1&status=open
      response:
        status: 200
        body: { items: [{ number: A-1, status: open, total: 120.5 }] }
  events: []
  returns: { emitted: 0, unchanged: 1 }
```

| Key | Meaning |
| --- | --- |
| `events[].event` | The trigger's name. Required. |
| `events[].key` | The item's key. Compared when given. |
| `events[].data` | The event's data. Compared exactly when given. |
| `seen[]` | `event`, `key` and `data` of an item as it was last raised. An item with the same key and the same data is unchanged. |

`events` is compared in order. `events: []` says the run raises nothing; a case without `events` does not check events at all. Each raised event is checked against the trigger's data, as in a real run. Nothing is queued and no rule starts. An action that raises events needs at least one case whose `events` is not empty.

## Member actions

A [member action](/docs/en/extensions/reference/member-connections#the-members-values-in-rules) uses `{{ userConnection.<field> }}`. Its case gives those values under `userConnection`, and the `input` the hook or the schedule passes.

```yaml title="actions/sync-member/tests.yaml"
- name: a revoked token
  input:
    subject: { kind: userConnection, userId: u_1, credentialId: c_1, companyId: co_1, config: { companyId: co_1 }, meta: { sandboxUserId: "1234" } }
    lastSucceededAt: "2026-11-02T10:00:00Z"
    firstRun: false
  userConnection: { accessToken: revoked-token }
  http:
    - request:
        method: GET
        url: https://api.example.com/v1/activities?user=1234
        headers: { authorization: Bearer revoked-token }
      response: { status: 401 }
  credentialRevoked: true
```

`userConnection` takes `accessToken`, `refreshToken` and the `secret` outputs of `afterConnect`. `credentialRevoked: true` is the outcome when a request that carried the member's token was answered `401`; in a real run, that member is then [parked](/docs/en/extensions/reference/member-connections#a-refused-token). A `401` to a request without the member's token is an ordinary failure: expect `fails: { status: 401 }`.

## Block render cases

Each [block](/docs/en/extensions/reference/blocks#render-tests) has its own `tests.yaml` of render cases: the inputs and rows to render with, and texts the HTML must or must not contain. Opero renders them at upload, after the action cases, within the same limits.

## How a case ends

Each case has exactly one outcome:

| Outcome | Passes when |
| --- | --- |
| `returns: <output>` | The action returns exactly this output. |
| `succeeds: true` | The action ends without an error, whatever it returns. |
| `fails: true` | The action fails. |
| `fails: { status: 409 }` | The action fails because the service answered with that status. |
| `rateLimited: true` | The service answered `429`. |
| `rateLimited: { status: 429 }` | The same, with the status written out. |
| `credentialRevoked: true` | A member action: a request that carried the member's token was answered `401`. |

## When a case fails

A failing case is named by its file and position, for example `actions/greet/tests.yaml#/0`, and for an exchange or an effect by the place inside it, such as `…#/0/http/1`. Every failing case of the package is reported in one run. The codes are listed under [Problems](#problems).

## Limits

| What | Limit |
| --- | --- |
| Cases per action | 1 to 50 |
| Cases per package | 200, action cases and block render cases together |
| Exchanges and effects per case | 50 each |
| `events` and `seen` per case | 500 each |
| Time per case | 10 seconds |
| Time for all cases of a package | 60 seconds |

## Several test files

`tests` in `action.yaml` may name a folder instead of a file. Every `.yaml` file directly in that folder is then a test file:

<Files>

    </Folder>
  </Folder>

```yaml title="actions/greet/action.yaml"
tests: tests/
```

## Problems

When the package is read, by `opero-ext validate` and at upload:

| Code | Cause | Fix |
| --- | --- | --- |
| `test.invalid` | A case of the wrong shape, no outcome or two, an input that does not match the input fields, settings that do not match `settings.yaml` or given without it or under `connection.config`, `effects` without data scopes, `events` or `seen` on an action that raises none, `userConnection` or `credentialRevoked` on an action that is not a member action, or more than 50 cases. | Fix the case as the message says. |
| `action.missing_test` | An action without a case. | Write one. |
| `event.unknown` | `events` or `seen` names no trigger of the package. | Fix the name. |
| `test.event_untested` | No case of an action that raises events lists the events it expects. | Add a case with a non-empty `events`. |

When the cases run, at upload and in `opero-ext test`:

| Code | What happened |
| --- | --- |
| `test.unexpected_request` | The action made a request the case did not script. |
| `test.request_mismatch` | The method, URL, a named header or the body differs from the case. |
| `test.unused_exchange` | The case scripted a request the action never made. |
| `test.unexpected_effect` | The action ran a data step the case did not script next. |
| `test.effect_mismatch` | A key an effect names differs from what the step was given, or the effect's `response` does not have the shape the step returns. |
| `test.unused_effect` | The case scripted a data step the action never ran. |
| `test.unexpected_event` | The action raised an event after those the case lists. |
| `test.event_mismatch` | A raised event differs from the one listed at that position: its trigger, key or data. |
| `test.missing_event` | The case lists an event the action did not raise. |
| `test.outcome_mismatch` | The action ended differently than the case says, or with another status. |
| `test.output_mismatch` | The output differs from `returns`. |
| `test.output_schema` | The output does not match the output fields. |
| `test.failed` | The case could not finish, for example it ran out of time, or the package has more than 200 cases. |

The codes of block render cases are under [Blocks](/docs/en/extensions/reference/blocks#render-tests).

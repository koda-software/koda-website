A dictionary is a fixed list of values, such as statuses or priorities, that select fields offer. A package can bring its own dictionaries and use them in the fields of its [objects](/docs/en/extensions/reference/objects).

```yaml title="dictionaries/status/dictionary.yaml"
dictionary: status
name: Order status
description: Where an order is.
entries:
  - { key: open, label: Open }
  - { key: noted, label: Noted, color: "#2563EB" }
  - { key: closed, label: Closed, isActive: false }
```

Each dictionary has its own folder in `dictionaries/`, listed in `extension.yaml`:

```yaml title="extension.yaml"
dictionaries:
  - dictionaries/status
```

## The installed dictionary

The dictionary is installed as an organization dictionary with the key `x-<key>-<name>`: `status` of the extension `shop-ext` is `x-shop-ext-status`. The organization cannot create a dictionary whose key starts with `x-`.

A field of the package names the dictionary by its name, not by the installed key:

```yaml title="objects/orders/object.yaml (part)"
  - key: status
    name: Status
    type: SELECT
    options: { dictionary: status }
```

A select field stores the entry's `key`, so a [query](/docs/en/extensions/reference/queries) compares with it: `WHERE f_status = 'open'`.

## Translating entry labels

Entry labels are the only texts of a dictionary that can be translated. They go in `locales/<lang>.yaml` under `dictionaries.<name>.entries.<key>.label`:

```yaml title="locales/pl.yaml"
dictionaries:
  status:
    entries:
      open: { label: Otwarte }
      noted: { label: Z notatką }
      closed: { label: Zamknięte }
```

The dictionary's `name` and `description` are English only.

## Where the administrator sees them

The install plan lists each dictionary under **What will change**. The extension's **Installed data** tab lists them read-only under **Dictionaries it installed**, with the name, the installed key and the number of entries. They are left out of the **Dictionaries** management list, and stay available wherever a dictionary is picked, for example for a select field of the organization's own objects.

The entries belong to the extension: they cannot be added, changed, reordered or removed, except by an upgrade. A dictionary opened by a link, for example from **Managed by this extension** on the extension's **Details** tab, starts with "Read-only: managed by the extension `<key>`." and a link **Open the extension**, and offers no editing and no delete.

## Upgrades and uninstalling

- **Entries are matched by key.** An entry whose key stays the same keeps its identity, and records keep their values. An entry the new version leaves out is removed.
- **A dictionary the new version drops** is deleted. If something of the organization still uses it, it is kept as the organization's own dictionary instead, and the plan says so (`dictionary.released`).
- **Uninstalling** keeps the dictionaries by default, as the organization's own. When the administrator chooses to delete the data, they are deleted for good, except one that something else still uses.

## Problems

| Code | What is wrong |
| --- | --- |
| `dictionary.invalid` | An unknown key, a name of the wrong form, an entry without `key` or `label`, two entries with the same key, a colour not written `#RRGGBB`, more than 1,000 entries, or more than 50 dictionaries. |
| `name.duplicate` | Two dictionaries with the same name. |
| `object.unknown_reference` | A field names a dictionary the package does not have. |
| `dictionary.save_validation` | In the install plan: the dictionary would not save, for example because an entry the organization's fields still use would be removed. Blocks the install. |
| `dictionary.adopts_existing` | In the install plan: a dictionary kept by an earlier uninstall is taken over. A warning. |
| `dictionary.released` | In an upgrade's plan: a dropped dictionary is kept because something still uses it. A warning. |

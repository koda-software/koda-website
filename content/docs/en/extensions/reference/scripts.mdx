A script is a JavaScript or TypeScript module with exactly one `export default` function, no `import` and no other export. It runs on its own in a sandbox, without network or database access. Actions, rule file steps, template filters and blocks use scripts; [A step that only calculates](/docs/en/extensions/calculating-step) is built on one.

<Tabs items={['JavaScript', 'TypeScript']}>
<Tab value="JavaScript">

```js title="actions/lookup/run.js"
/** @type {import('../../.opero/types').Action<'lookup'>} */
const run = async ({ input, settings, user }) => {
  const email = input.email.trim().toLowerCase();
  return {
    email,
    language: settings.language ?? 'en',
    requestedBy: user.email,
  };
};
export default run;
```

</Tab>
<Tab value="TypeScript">

```ts title="actions/lookup/run.ts"
import type { Action } from '../../.opero/types';

const run: Action<'lookup'> = async ({ input, settings, user }) => {
  const email = input.email.trim().toLowerCase();
  return {
    email,
    language: settings.language ?? 'en',
    requestedBy: user.email,
  };
};
export default run;
```

</Tab>
</Tabs>

Write `export default function name(…)`, or a constant followed by `export default name;` as the scaffold does.

## Kinds of script

| Script | Named by | Receives | Returns |
| --- | --- | --- | --- |
| Action script | `run: run.js` in `action.yaml` | The argument below | The action's output. May be `async`. |
| Step script | `code: { $file: step.js }` in a rule file | The argument below | The step's result, under its `contextKey`. May be `async`. |
| Filter script | `script` in `filter.yaml` | `(value, args, context)` | The filtered value, at once: not `async`. See [Template filters](/docs/en/extensions/reference/filters#the-function). |
| Block script | `script` in `block.yaml` | `ctx`, in the viewer's browser. See [Blocks](/docs/en/extensions/reference/blocks#the-script). | Nothing, or a function that cleans up before the block's next run. |

## The argument

An action script and a step script receive one object:

    },
    context: {

    },
  }}
/>

<Callout title="No data helpers in a package">
A script of a package cannot read or write records, run queries or send notifications: it gets no data helpers. Fetch what it needs with a [data step](/docs/en/extensions/reference/data-steps) first and read it from `context`; write its result with another step.
</Callout>

## Errors

Throwing an error fails the action, and so the step that called it:

```js
if (!Number.isFinite(price)) {
  throw new Error('The price is not a number.');
}
```

A problem found when the package is read is reported at its line in your script: Opero keeps every line where you wrote it.

<Callout type="warn">
When a script throws while it runs, the step reports "Script execution failed" without a line number. Cover your error paths with [tests](/docs/en/extensions/reference/tests).
</Callout>

## Generated types

`opero-ext types` writes `.opero/types/index.d.ts` from the descriptors. `init` and `add` write it too, and `validate` and `pack` refresh it when the package is valid and already has a `.opero/` folder.

| Type | For |
| --- | --- |
| `Action<'name'>` | An action script. |
| `StepScript<'name'>` | A step script of that action's rule file. |
| `Filter` | A filter script. |
| `Block` | A [block](/docs/en/extensions/reference/blocks#the-script)'s script, a function of `ctx`. Only in a package with blocks. |
| `Settings` | The extension's settings, from `settings.yaml`. A field with a default is not optional. |
| `ScriptArgument<'name'>` | The argument of an action's scripts. |
| `Triggers` | The data of each trigger's events. |

In JavaScript, apply one with the JSDoc line the scaffold writes, and check the scripts with:

```bash title="Terminal"
npx tsc -p jsconfig.json
```

A field from a [schema file](/docs/en/extensions/reference/actions#schema-files) is not typed.

## TypeScript

A descriptor may name a `.ts` file. `opero-ext` strips the types and packs a `.js` with the same lines beside it.

Only TypeScript that becomes JavaScript by removing types is accepted:

- no `enum`, `namespace`, parameter properties or `<T>` casts;
- `import type` lines are removed with the types; any other `import` is refused;
- a `.js` you keep beside a `.ts` is not used.

A module problem, such as a missing default export, is reported at the `.js` the tool built. What the type stripping refuses is reported at the `.ts`.

<Callout type="warn" title="The module check reads lines">
A line inside a template literal or a block comment that starts with `export` or `import` at the first column is read as a module statement, and refused. Indent such lines.
</Callout>

## Problems

| Code | Cause | Fix |
| --- | --- | --- |
| `script.invalid` | No line or more than one line starts with `export default`, a line imports or exports something else, the file is empty, a filter's default export is `async`, or TypeScript that cannot be stripped. | Keep one `export default` function and no other `import` or `export`. |
| `script.not_built` | A zip names a `.ts` script without the `.js` beside it. | Pack with `opero-ext pack`. |
| `script.missing_file` | A `$file` script that is not in the package. | Add the file, or fix the name. |
| `script.invalid_path` | A `$file` value that is not a `.js` or `.ts` file of the action's folder. | Name a script file in that folder, relative to it. |
| `manifest.missing_file` | `run` or a filter's `script` names a `.js` file that is not in the package. | Add the file, or fix the name. |

A trigger lets the organization's own rules start when something happens at the outside service. The package declares the trigger and raises its events; the organization builds rules on it, as on any other [rule trigger](/docs/en/opero/07-automatyzacja/wyzwalacze). The guide [Events from a service](/docs/en/extensions/scheduled-events) builds one.

```yaml title="triggers/order-changed/trigger.yaml"
trigger: order_changed
label: Order changed
description: An open order is new, or one of its values changed.
data:
  number: { type: text, label: Order number, required: true }
  status: { type: select, label: Status, options: [open, packed, shipped], required: true }
  total: { type: number, label: Total, nullable: true }
  updatedAt: { type: datetime, label: Updated at }
config:
  status: { type: select, label: Only this status, options: [open, packed, shipped], match: status }
dedupe: { retentionDays: 30 }
example: { number: A-1, status: open, total: 120.5, updatedAt: "2026-11-01T10:00:00Z" }
```

Each trigger is a folder `triggers/<folder>` with a `trigger.yaml`, listed under `triggers` in `extension.yaml` or a module's `module.yaml`. `opero-ext add trigger <name>` writes both.

<Callout title="A trigger alone raises nothing">
Only the package raises a trigger's events, with the [`EMIT_EVENT`](/docs/en/extensions/reference/raising-events) step, from a [schedule](/docs/en/extensions/reference/schedules) run or a [member connection](/docs/en/extensions/reference/member-connections) hook. A rule of the organization cannot raise them.
</Callout>

## The data

`data` is the contract between the package and the rules built on the trigger: a rule started by an event reads `{{ trigger.data.<field> }}`, and the data of every event is kept in the rule's run history.

| Rule | Detail |
| --- | --- |
| A [field list](/docs/en/extensions/reference/actions#field-lists), or a JSON Schema file in the folder | With a field list, a field the list does not name is refused. |
| `nullable: true` | The field's value may also be `null`. Only action inputs and outputs and trigger data accept it. |
| Checked before it is raised | An event that does not fit fails the step that raises it, and nothing is raised. |
| At most 32 KB | Of JSON, per event. |

The generated `Triggers` type in `.opero/types/index.d.ts` gives a script that builds the items their shape.

## Filters

`config` lists the filters a rule author may set. Each field has a `type` of `text`, `number`, `boolean` or `select`, and `match`: the top-level data field it is compared with.

```yaml title="triggers/activity/trigger.yaml (part)"
config:
  member: { type: text, label: Only this member, match: userId }
```

A rule starts only for events whose data field equals the value set; when the data field is a list, the list must contain the value. A filter left empty does not filter, and values are compared exactly, without conversion: `10` does not match `"10"`.

## Dedupe retention

When [`EMIT_EVENT`](/docs/en/extensions/reference/raising-events#dedupe) runs with `dedupe: true`, Opero remembers each item it raised so that an unchanged item is not raised again. `dedupe.retentionDays` says for how long: an item not raised for that many days is forgotten, and raised once more if the service still returns it.

Choose a retention longer than the time the service keeps returning an unchanged item, or ask the service only for recent items. The memory is per installation, trigger and run subject: the same order seen in two companies is remembered twice. An upgrade keeps it; uninstalling forgets it.

## The example

`example` is one event's data. When a rule on the trigger is tested and has no past run to replay, Opero offers it as sample data. Without one, Opero builds it from the data fields: their defaults, the first option of a select, a date for a date field, the label of a text field, `0`, `false` and empty lists.

## In the organization's rules

While the extension runs, the trigger is the type `x-<key>.<trigger>` in the rule builder, under **Integrations**, with its filters as a form:

![The Order changed trigger in the rule builder's trigger list, under Integrations](/docs/_assets/extensions/scheduled-events/trigger-picker.webp)

```json title="The trigger of one of the organization's rules"
{
  "trigger": {
    "type": "x-order-events.order_changed",
    "config": { "status": "packed" }
  }
}
```

| Rule | Detail |
| --- | --- |
| Company | An event raised by a run for a company starts that company's rules. An event raised with no company starts only rules that are not limited to particular companies. |
| Actor | The event comes from the extension, so the rule runs as the extension. |
| At least once | The same event can arrive twice. Write rules that receive it so that a second run changes nothing: find the record by a key and update it, or create it when it is missing. |
| While the extension does not run | The trigger is missing from the rule builder, and no event starts a rule, not even one raised before it stopped. A rule that has the trigger keeps it. See [States](/docs/en/extensions/after-install#states). |

## Upgrades

| Change in a new version | What happens | Code |
| --- | --- | --- |
| A trigger an organization rule uses is removed | The upgrade is blocked until no rule uses it. | `trigger.in_use` |
| Top-level data fields of a trigger a rule uses are removed | A warning. Rules are not scanned for where they read the fields. | `trigger.data_field_removed` |
| A trigger is added, or labels, filters or the example change | Nothing to confirm beyond the review. | |

A trigger keeps its identity while its `trigger` name stays the same, so folders can be renamed freely. An uninstall quarantines the active rules on the extension's triggers. What the administrator sees is in [Upgrade and uninstall](/docs/en/extensions/upgrade-and-uninstall#what-a-new-version-can-change).

## Translations

The texts go under `triggers.<trigger>`: `label`, `description`, `data.<field>` and `config.<field>`. See [Translations](/docs/en/extensions/reference/translations#translatable-keys).

## Problems

| Code | Cause | Fix |
| --- | --- | --- |
| `trigger.invalid` | An unknown key, a missing `label`, `description` or `data`, a filter without `match` or of another type, `retentionDays` outside 1 to 365, an example that does not match the data or is over 32 KB, a schema file that does not compile, or more than 50 triggers. | Fix the key the message names. |
| `trigger.match_unknown_field` | A filter's `match` names no top-level data field. | Name a top-level data field. |
| `field.invalid` | A data or filter field of the wrong shape, including `nullable` on a filter. | Fix the field. |
| `name.duplicate` | Two triggers with the same name. | Rename one. |

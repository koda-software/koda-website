title: Data permissions
description: Ask for the data scopes your packaged rules need in permissions.data, and learn who can install such a package and when the scopes are checked.
---

A rule of your package reads and writes data, runs queries and sends messages only through [data steps](/docs/en/extensions/reference/data-steps), and each data step needs a **data scope** the package declares in `permissions.data`. The administrator agrees to every scope, with your reason, in the [install review](/docs/en/extensions/install#access-to-data).

```yaml title="extension.yaml"
permissions:
  data:
    - scope: records:read
      reason: Reads the open orders.
    - scope: records:write
      reason: Stores the status the carrier answers.
```

## permissions.data

Ask only for what you use: a declared scope no packaged rule uses is refused.

## The scopes

| Scope | Lets a packaged rule | With the step |
| --- | --- | --- |
| `records:read` | Read records of the package's own objects. | `FETCH_RECORDS` |
| `records:write` | Create and change records of the package's own objects. | `CREATE_RECORD`, `UPDATE_RECORD` |
| `queries:run` | Run the package's own FETCH queries. | `RUN_QUERY` |
| `queries:mutate` | Run the package's own MUTATION queries. | `RUN_QUERY` |
| `contractors:write` | Change the organization's contractors. | `UPDATE_CONTRACTOR` |
| `email:send` | Send emails to any address through the installation's email service, with any file of the organization attached by its id. | `SEND_EMAIL` |
| `notifications:send` | Send notifications to members of the organization. | `SEND_NOTIFICATION` |
| `documents:generate` | Generate documents from a document template the organization's rule author picks. Also needs `documents` in `requires.modules`. | `GENERATE_DOCUMENT` |

<Callout type="warn" title="Attachments: any file of the organization">
A `SEND_EMAIL` step may attach any file of the organization by its id: not only a document the same run generated, and not only files of the company the rule runs in or files its author can open. Only files whose source keeps them from rules, such as some email attachments, are refused. So a step that takes a file id from its input lets any rule author of the organization mail that file to any address. This may be narrowed later, for example to documents the same run generates.
</Callout>

## Who can install it

The steps of your package run on the **installation's** authority: whoever wrote the organization's rule that uses your step, the step does what the scopes allow, in the company that rule runs for, without that person's own permissions. The consent is therefore the whole authorization.

<Callout type="warn" title="Only an organization owner installs a package with data scopes">
A package that declares any data scope can be installed, upgraded or repaired only by an organization owner, a member with a role that grants every permission, or a system administrator. For anyone else the install review is blocked with `permission.owner_required`.
</Callout>

## What each step may name

A package reaches only what it brings with it: its own objects in the module `x-<key>` and its own queries, each written out, never built from a template or a setting. Contractors, email addresses and notification recipients are the exceptions the scopes name. Each step's keys, and the keys a packaged rule may not set, are on [Data steps](/docs/en/extensions/reference/data-steps).

## When it is checked

| When | What is checked | Code on failure |
| --- | --- | --- |
| When the package is read, by `opero-ext validate` and at upload | Every step of every packaged rule, against the declared scopes and its targets. | The `step.*` codes on [Data steps](/docs/en/extensions/reference/data-steps#problems) |
| In the install review | Whether the person installing is an owner, and whether this Opero serves every declared scope. | `permission.owner_required`, `manifest.unsupported_by_server` |
| Every time a step runs | The step's settings again, after their templates are filled in. A package that passed upload does not fail here; it is a second line of defence. | `EXTENSION_SCOPE_DENIED` |

The [contract tests](/docs/en/extensions/reference/tests#data-and-messaging-steps) run the same check, so a test cannot pass with a step the scopes do not allow.

## Upgrades

| Change in a new version | What happens | Code |
| --- | --- | --- |
| A scope is added | It is shown as new in the review, for the administrator to agree to. Only an owner can install the upgrade. | |

What the administrator sees is in [Upgrade and uninstall](/docs/en/extensions/upgrade-and-uninstall#what-a-new-version-can-change).

## Problems

| Code | Cause | Fix |
| --- | --- | --- |
| `permissions.invalid_scope` | A scope that is not one of the eight. | Use a scope from the table. |
| `permissions.reason_required` | A scope without a reason. | Add one sentence. |
| `permissions.unused_scope` | A declared scope no packaged rule uses. | Remove it. |
| `requires.module_undeclared` | The `documents:generate` scope without `documents` in `requires.modules`. | Add `documents`. |
| `test.invalid` | A test case with `effects` in a package without data scopes. | Declare the scope, or remove the effects. |
| `permission.owner_required` | In the install review: the person installing is not an organization owner. Blocks the install. | Ask an owner to install it. |
| `manifest.unsupported_by_server` | At upload or in the install review: this Opero does not serve one of the scopes yet. | Wait for an Opero that serves it, or drop the scope. |

The connection holds the outside service's credentials. The administrator enters them after installing, tests them and activates the connection on the [Configuration](/docs/en/extensions/after-install#configuration) tab; until then the extension does not run. The [tutorial](/docs/en/extensions/tutorial/call-a-service) builds one.

```yaml title="connection/connection.yaml"
methods:
  - method: token
    kind: api_token
    label: API token
    fields:
      token: { type: text, label: API token, required: true, hint: true }
verify: verify
```

`extension.yaml` points at the folder with `connection: connection` and lists at least one host under `permissions.network`.

Every credential field is secret unless it says `secret: false`. `hint: true` lets Opero show the last four characters of a stored value; without it the value shows only as `***`. Values that are not secret, such as a language or an account number, are [settings](/docs/en/extensions/reference/settings).

## Organization or company credentials

`scopes` decides whether there is one credential for the whole organization or one per company.

| `supported` | `active` | Result |
| --- | --- | --- |
| `[organization]` | `organization` | One credential for all companies. The default. |
| `[company]` | `company` | One credential per company. |
| `[organization, company]` | `selectable` | The administrator chooses. |

With company credentials, a step uses the credential of the company the calling rule runs for, and the package's tests give a `companyId`.

## Verification

`verify` names an action of the package, usually one that nothing exposes. It runs with the credentials being tested and the extension's settings, and until it succeeds, the connection cannot be activated. Write it as a cheap, read-only call that proves the credential works:

```yaml title="actions/verify/rule.yaml"
entryStepId: call
steps:
  - id: call
    type: CALL_WEBHOOK
    name: Check token
    contextKey: output
    config:
      url: https://api.example.com/v1/me
      method: GET
      headers: { Authorization: "Bearer {{ connection.token }}" }
edges: []
```

The verify action runs without a company, so it cannot use a [data step](/docs/en/extensions/reference/data-steps). It cannot raise events or use a member's values either.

## Secrets

A secret is written `{{ connection.<field> }}`, alone inside the braces, in a header value or a URL query value of a **Call Webhook** step. With `secretsInBody: true` it may also stand in the URL path and the body.

| Example | Accepted |
| --- | --- |
| `Authorization: "Bearer {{ connection.token }}"` | Yes |
| `url: "https://api.example.com/v1/items?key={{ connection.token }}"` | Yes |
| `X-Key: "{{ connection.token \| upcase }}"` | No: a filter is applied |
| `body: { key: "{{ connection.token }}" }` | Only with `secretsInBody: true` |
| In a script, a condition, a log or a transform | No |
| `{{ connection.other }}` for a field no method declares | No |

<Callout type="success" title="What Opero guarantees">
- The real value is put in only while the request is sent, so it never appears in a log, a run history or a script.
- The secret goes only to hosts in `permissions.network`, and only while your own action runs.
- A rule the organization writes cannot reference your connection, and running one of your installed rules by hand never sends the secret.
- An error message never quotes what the service sent back, because an error body could repeat a secret.
</Callout>

## HTTP Basic from the connection

Some services want the credentials as HTTP Basic, the base64 of `id:secret`. A placeholder cannot be encoded, so a method declares a `scheme` that names two of its fields, and the **Call Webhook** step writes `auth: connection` with no placeholder:

```yaml title="connection/connection.yaml"
methods:
  - method: client
    kind: custom
    label: API client
    fields:
      clientId: { type: text, label: Client ID, required: true, secret: false }
      clientSecret: { type: text, label: Client secret, required: true }
    scheme: { kind: basic, username: clientId, password: clientSecret }
verify: verify_client
```

```yaml title="actions/verify-client/rule.yaml"
entryStepId: check
steps:
  - id: check
    type: CALL_WEBHOOK
    name: Check the client
    config:
      method: GET
      url: https://api.example.com/v1/client
      auth: connection
edges: []
```

`basic` is the only `kind`. `auth: connection` needs a `scheme` on every method, so the step works whichever method the administrator chooses; it sends the first method whose two fields are filled in. No other `auth` value is accepted on a packaged step. In a test case, give the two fields under `connection` and expect the encoded header, for example `authorization: Basic Y2xpZW50LTE6c2VjcmV0LTE=` for `client-1` and `secret-1`.

## Member connections

`member: member.yaml` lets each member also connect their own account at the service, by OAuth. The OAuth client's id and secret are then credential fields of one of the methods. See [Member connections](/docs/en/extensions/reference/member-connections).

## Upgrades

| Change in a new version | What happens | Code |
| --- | --- | --- |
| The credential fields change | The connection is switched off after the upgrade until it passes a test again. A warning. | `connection.reverify_required` |
| Anything else in `connection.yaml`, or the settings | The connection stays on. | |

What the administrator sees is in [Upgrade and uninstall](/docs/en/extensions/upgrade-and-uninstall#what-a-new-version-can-change).

## Translations

A method's label goes under `connection.methods.<method>.label`, its fields under `fields.<field>`. See [Translations](/docs/en/extensions/reference/translations#translatable-keys).

## Problems

| Code | Cause | Fix |
| --- | --- | --- |
| `connection.invalid` | An unknown key, a `settings` block, a method key of the wrong form or used twice, an `active` scope not among `supported`, a `verify` that names no action, or a `scheme` field the method does not have. | Fix the key the message names; move settings to `settings.yaml`. |
| `connection.schema_invalid` | A method's schema file is not an object schema, does not compile, or uses text keys. | Write a valid JSON Schema in English, or use a field list. |
| `connection.hosts_required` | A package with a connection lists no host in `permissions.network`. | Add the service's host with a reason. |
| `connection.undeclared` | `{{ connection.<field> }}` or `auth: connection` in a package without a connection. | Add `connection/connection.yaml`. |
| `connection.placeholder_position` | A secret outside a **Call Webhook** header value or URL query value, or outside the path and body with `secretsInBody`. | Move it, or set `secretsInBody: true` if the service needs it. |
| `connection.placeholder_not_bare` | A secret with a filter, a tag or other text inside the braces. | Write exactly `{{ connection.<field> }}`. |
| `connection.unknown_field` | A field no method of the connection declares. | Fix the name, or add the field. |
| `step.config_not_allowed` | An `auth` other than `connection`, or `auth: connection` with a method that has no `scheme`. | Give every method a `scheme`, or send the secret in a header. |
| `action.verify_uses_data` | The verify action uses a data step. | Check the credential with a **Call Webhook** step only. |
| `event.emitted_from_step` | The verify action raises events. | Raise events from a schedule's action instead. |
| `action.member_outside_member_run` | The verify action uses `{{ userConnection.<field> }}`. | Verify with the organization's credentials. |
| `layout.missing_descriptor` | `extension.yaml` says `connection: connection`, but `connection/connection.yaml` is missing. | Add the file. |

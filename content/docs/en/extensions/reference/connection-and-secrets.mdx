title: Connection and secrets
description: "Reference for connection.yaml in Opero extensions: sign-in methods, credential fields, organization or company scopes, verification, and where a secret may appear."

The connection holds the outside service's credentials. The administrator fills it in after installing, presses **Verify**, and switches it on. Until then the extension does not run.

```yaml title="connection/connection.yaml"
methods:
  - method: token
    kind: api_token
    label: API token
    fields:
      token: { type: text, label: API token, required: true, hint: true }
verify: verify
```

`extension.yaml` points at the folder with `connection: connection`, and lists at least one host under `permissions.network`.

Values that are not secret, such as a language or an account number, are not part of the connection: they are [settings](/docs/en/extensions/reference/settings), in `settings.yaml`. A `settings` key in `connection.yaml` is refused with `connection.invalid`.

Every field of a method is secret unless it says `secret: false`. `hint: true` lets Opero show the last four characters of a stored value so the administrator can tell which one is saved; without it the value shows only as `***`.

## Organization or company credentials

`scopes` decides whether there is one credential for the whole organization or one per company.

| `supported` | `active` | Result |
| --- | --- | --- |
| `[organization]` | `organization` | One credential for all companies. The default. |
| `[company]` | `company` | One credential per company. |
| `[organization, company]` | `selectable` | The administrator chooses. |

```yaml title="connection/connection.yaml"
scopes:
  supported: [organization, company]
  active: selectable
```

With company credentials, the step uses the credential of the company the calling rule runs for. Tests of such a package give a `companyId`.

## Verification

`verify` names an ordinary action, usually one that nothing exposes. When the administrator presses **Verify**, Opero runs it with the saved credentials and the extension's settings. If it fails, the connection cannot be switched on.

Write it as a cheap, read-only call that proves the credential works, such as fetching the current account:

```yaml title="actions/verify/rule.yaml"
entryStepId: call
steps:
  - id: call
    type: CALL_WEBHOOK
    name: Check token
    contextKey: output
    config:
      url: https://api.example.com/v1/me
      method: GET
      headers: { Authorization: "Bearer {{ connection.token }}" }
edges: []
```

If a new version changes the credential fields, the connection is switched off after the upgrade until it passes verification again. Changes to the settings never do this.

## Secrets

Write a secret as `{{ connection.<field> }}`, alone inside the braces, in a header value or a URL query value of a **Call webhook** step.

| Example | Accepted |
| --- | --- |
| `Authorization: "Bearer {{ connection.token }}"` | Yes |
| `url: "https://api.example.com/v1/items?key={{ connection.token }}"` | Yes |
| `X-Key: "{{ connection.token \| upcase }}"` | No: a filter is applied |
| `body: { key: "{{ connection.token }}" }` | Only with `secretsInBody: true` |
| In a script, a condition, a log or a transform | No |
| `{{ connection.other }}` for a field no method declares | No |

<Callout type="success" title="What Opero guarantees">
- The real value is put in only while sending the request, so it never appears in a log, a run history or a script.
- The secret is sent only to hosts in `permissions.network`, and only while your own action runs.
- A rule the organization writes cannot reference your connection, and running one of your installed rules by hand never sends the secret.
- An error message never quotes what the service sent back, because an error body could repeat a secret.
</Callout>

Settings are not secret and need none of this. Read them as `{{ trigger.settings.<field> }}` in a rule file and as `settings` in a script; see [Settings](/docs/en/extensions/reference/settings#reading-settings).

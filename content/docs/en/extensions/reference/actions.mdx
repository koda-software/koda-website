title: Actions and field lists
description: "Reference for action.yaml in Opero extensions: name, label, input and output field lists, field types, the run logic, tests, publishing a rule step, offering the action to members from blocks and records, and how installed parts are named."

An action is a folder with an `action.yaml`, its logic (a rule file or a script) and its tests. Exposed as a rule step, it is what rule authors use.

```yaml title="actions/greet/action.yaml"
action: greet
label: Greet
description: Sends a greeting for a name to httpbin.org and returns its answer.

input:
  name: { type: text, label: Name, required: true }
output:
  status: { type: integer, label: HTTP status }
  body: { type: object, label: Answer, fields: {} }

run: rule.yaml
tests: tests.yaml

expose:
  ruleStep: { category: integration }
```

Top-level input fields of type `text`, `number`, `integer`, `boolean` and `select` also become the parameters of the installed rule's manual trigger. The first 20 such fields are used. A field of another type, a field whose key has an upper-case letter (write `order_id`, not `orderId`), and an input given as a schema file give no parameter.

The installed rule runs only through its step. Running, testing or replaying it by hand, or calling it from another rule with **Call rule**, is refused with `EXTENSION_MANAGED_RULE_RUN`. To try an action, use it as a step in a rule of the organization, or run its [tests](/docs/en/extensions/reference/tests).

<Callout type="warn" title="Extra outcome ports">
`expose.ruleStep.branches` lists extra outcome ports. They are shown on the step, but today only the default and error ports are ever taken.
</Callout>

## Actions that are not steps

An action without `expose` is still installed, and runs when something of the package runs it:

| Run by | Example |
| --- | --- |
| **Test connection** on the connection | `verify: verify` in `connection.yaml`. |
| A [schedule](/docs/en/extensions/reference/schedules) | `action: sync_orders` in `schedule.yaml`. |
| A [member connection](/docs/en/extensions/reference/member-connections) hook | `afterConnect` or `beforeDisconnect` in `member.yaml`. |

Two kinds of action can never be exposed as a rule step:

- **An action that raises events**, one whose rule uses [`EMIT_EVENT`](/docs/en/extensions/reference/raising-events): only schedule runs and member connection hooks raise a package's events (`event.emitted_from_step`). It cannot be the verify action either.
- **A member action**, one whose rule uses `{{ userConnection.<field> }}`: it runs only for one member, from a member connection hook or a schedule over members (`action.member_outside_member_run`). It cannot be the verify action either.

A schedule's action and a hook's action may not be exposed either (`schedule.action_exposed`, `member.invalid`), as a rule step, a block action or a record command. An action that raises events, or one that uses `{{ userConnection.<field> }}`, cannot be a block action or a record command.

<Callout title="Two meanings of “member”">
A *member action* on this page is one that uses a member's own connection. The actions members run themselves from blocks and records are [block actions and record commands](/docs/en/extensions/reference/member-actions).
</Callout>

## Field lists

A field list maps field keys (letters, digits and `_`, not starting with a digit) to definitions. Input and output, connection credentials, the extension's [settings](/docs/en/extensions/reference/settings), a [trigger](/docs/en/extensions/reference/triggers)'s data and filters, and a [member connection](/docs/en/extensions/reference/member-connections)'s form are all field lists.

```yaml
input:
  orderId: { type: text, label: Order number, required: true, help: As shown on the order. }
  priority: { type: select, label: Priority, options: [low, normal, high], default: normal }
  lines:
    type: list
    label: Lines
    items:
      type: object
      fields:
        sku: { type: text, label: SKU }
        quantity: { type: integer, label: Quantity }
```

### Field types

| Type | Value |
| --- | --- |
| `text` | A text. |
| `number` | A number. |
| `integer` | A whole number. |
| `boolean` | `true` or `false`. |
| `date` | A text such as `2026-11-12`. |
| `datetime` | An ISO 8601 date and time. |
| `select` | One of `options`. |
| `list` | A list of `items`. |
| `object` | An object with `fields`. |
| `company` | One of the member's companies. Only at the top of a [member connection](/docs/en/extensions/reference/member-connections#the-members-form)'s `config`, at most once. |

Lists nest up to five levels and hold up to 100 fields.

<Callout type="warn" title="Number and boolean inputs take fixed values">
The values a rule gives a step are checked against its input fields when the rule is saved, so a `number` or `boolean` input accepts only a fixed value, not a template such as `{{ record.price }}`. Declare such inputs as `text` and convert them in a script. The [calculating recipe](/docs/en/extensions/calculating-step) shows how.
</Callout>

### Schema files

A JSON Schema file in the action's folder can stand in place of a field list when you need more than field lists offer:

```yaml title="actions/create-shipment/action.yaml"
input: input.schema.json
```

A schema file is written in English only, and its fields are not typed in scripts.

## How things are named after install

| Thing | Name | For key `polar-eu` |
| --- | --- | --- |
| Rule step | `x-<key>.<action>` | `x-polar-eu.sync` |
| Template filter | `x_<key with _>_<filter>` | `x_polar_eu_pace` |
| Connection | `x-<key>` | `x-polar-eu` |
| Rule trigger | `x-<key>.<trigger>` | `x-polar-eu.daily_activity` |
| Block | `x_<key with _>_<block>` | `x_polar_eu_week_card` |
| Block action, record command | `x-<key>.<action>` | `x-polar-eu.sync` |
| Record link | `x-<key>.<link>` | `x-polar-eu.open_profile` |
| Package permission | `company.x-<key>.<name>` | `company.x-polar-eu.sync` |
| Installed rule | `<name>: <action label>` | `Polar: Sync` |

A step keeps its identity across versions as long as the action's name stays the same, so rules that use it keep working after an upgrade.

An action is a folder with an `action.yaml`, its logic (a rule file or a script) and its tests. Exposed as a rule step, it is what rule authors use.

```yaml title="actions/greet/action.yaml"
action: greet
label: Greet
description: Sends a greeting for a name to httpbin.org and returns its answer.

input:
  name: { type: text, label: Name, required: true }
output:
  status: { type: integer, label: HTTP status }
  body: { type: object, label: Answer, fields: {} }

run: rule.yaml
tests: tests.yaml

expose:
  ruleStep: { category: integration }
```

Top-level input fields of type `text`, `number`, `integer`, `boolean` and `select` also become the parameters of the installed rule's manual trigger, so the rule can be run by hand with a form. The first 20 such fields are used. A field of another type, a field whose key has an upper-case letter (write `order_id`, not `orderId`), and an input given as a schema file give no parameter.

<Callout type="warn" title="Extra outcome ports">
`expose.ruleStep.branches` lists extra outcome ports. They are shown on the step, but today only the default and error ports are ever taken.
</Callout>

## Field lists

A field list maps field keys (letters, digits and `_`, not starting with a digit) to definitions. Input and output, connection credentials and the extension's [settings](/docs/en/extensions/reference/settings) are all field lists.

```yaml
input:
  orderId: { type: text, label: Order number, required: true, help: As shown on the order. }
  priority: { type: select, label: Priority, options: [low, normal, high], default: normal }
  lines:
    type: list
    label: Lines
    items:
      type: object
      fields:
        sku: { type: text, label: SKU }
        quantity: { type: integer, label: Quantity }
```

### Field types

| Type | Value |
| --- | --- |
| `text` | A text. |
| `number` | A number. |
| `integer` | A whole number. |
| `boolean` | `true` or `false`. |
| `date` | A text such as `2026-11-12`. |
| `datetime` | An ISO 8601 date and time. |
| `select` | One of `options`. |
| `list` | A list of `items`. |
| `object` | An object with `fields`. |

Lists nest up to five levels and hold up to 100 fields.

<Callout type="warn" title="Number and boolean inputs take fixed values">
The values a rule gives a step are checked against its input fields when the rule is saved, so a `number` or `boolean` input accepts only a fixed value, not a template such as `{{ record.price }}`. Declare such inputs as `text` and convert them in a script. The [calculating recipe](/docs/en/extensions/calculating-step) shows how.
</Callout>

### Schema files

A JSON Schema file in the action's folder can stand in place of a field list when you need more than field lists offer:

```yaml title="actions/create-shipment/action.yaml"
input: input.schema.json
```

A schema file is written in English only, and its fields are not typed in scripts.

## How things are named after install

| Thing | Name | For key `polar-eu` |
| --- | --- | --- |
| Rule step | `x-<key>.<action>` | `x-polar-eu.sync` |
| Template filter | `x_<key with _>_<filter>` | `x_polar_eu_pace` |
| Connection | `x-<key>` | `x-polar-eu` |
| Installed rule | `<name>: <action label>` | `Polar: Sync` |

A step keeps its identity across versions as long as the action's name stays the same, so rules that use it keep working after an upgrade.

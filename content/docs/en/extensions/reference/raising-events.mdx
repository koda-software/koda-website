---
title: Raising events
description: Raise the events of the package's own triggers with the EMIT_EVENT step, with keys and dedupe so an unchanged item starts no rule twice.
---

A packaged rule raises the events of the package's own [triggers](/docs/en/extensions/reference/triggers) with the step `EMIT_EVENT`. Each item of a list becomes one event, and each event can start the organization's rules on that trigger. The guide [Events from a service](/docs/en/extensions/scheduled-events) uses it.

```yaml title="actions/sync-orders/rule.yaml"
entryStepId: fetch
steps:
  - id: fetch
    type: CALL_WEBHOOK
    name: Open orders
    contextKey: orders
    config:
      method: GET
      url: "https://api.example.com/v1/orders?company={{ trigger.data.subject.companyId }}&status=open"
  - id: emit
    type: EMIT_EVENT
    name: Raise order events
    contextKey: output
    config:
      event: order_changed
      items: "{{ orders.body.items }}"
      key: number
      dedupe: true
edges:
  - { fromStepId: fetch, toStepId: emit }
```

## Settings

<TypeTable
  type={{
    event: {
      type: 'string',
      description: 'The name of one of the package\'s triggers, written out. Never a template or another extension\'s trigger.',
      required: true,
    },
    items: {
      type: 'string',
      description: 'One {{ expression }} and nothing around it, resolving to a list of objects: one event per object.',
      required: true,
    },
    key: {
      type: 'string',
      description: 'A top-level data field of the trigger, written out, that identifies an item, such as an order number. Required with dedupe.',
    },
    dedupe: {
      type: 'boolean',
      description: 'Raise an item only when it is new or changed since it was last raised.',
      default: 'false',
    },
  }}
/>

Nothing else is accepted. The step sets no company and no actor: an event belongs to the company of the run that raises it, comes from the extension, and carries the run's chain of rules, so a rule already in that chain does not start again.

## Items

Each element of `items` is an object that must match the trigger's `data`: a field the field list does not name, a missing required field or a value of the wrong type is refused, and a field marked `nullable` may be `null`. When the service's answer has another shape, reshape it first with a **Run Script** step or the list steps (`TRANSFORM`, `FILTER` and others).

`key` names the field whose value identifies the item. In every item, that value is a text of 1 to 200 characters or a number.

The step returns `{ emitted, unchanged }`: how many events it raised, and how many items it left out because they had not changed.

## Dedupe

Without `dedupe`, every item is raised on every run. With `dedupe: true` and a `key`, an item is raised when Opero has no memory of its key, or when its content differs from what was last raised for that key.

| Rule | Detail |
| --- | --- |
| Unchanged | All of the item's data is the same as when it was last raised for that key. The order of the fields does not matter; any other difference counts as a change, even in a field no rule reads. |
| Per run subject | The memory is kept per installation, company or connected member. The same key in two companies is two items. |
| Within one step | A key that repeats is compared with what the step itself just raised. |
| How long | The trigger's [`dedupe.retentionDays`](/docs/en/extensions/reference/triggers#dedupe-retention). |

## Delivered at least once

Opero raises an event first and remembers it afterwards, so if something stops in between, the next run raises the same item again. The organization's rules on the trigger should therefore treat a second event as harmless: look the record up by the item's key and update it, or create it when it is missing.

## Where it may be used

`EMIT_EVENT` runs only in runs Opero starts for the extension itself:

| The action that uses it is run by | Allowed |
| --- | --- |
| A [schedule](/docs/en/extensions/reference/schedules) | Yes |
| The `afterConnect` or `beforeDisconnect` hook of a [member connection](/docs/en/extensions/reference/member-connections) | Yes |
| An organization rule, as a rule step | No |
| A member, as a block action or a record command | No |
| **Test connection**, as the verify action | No |

The organization's own rules cannot use `EMIT_EVENT` either: the rule builder does not offer it, and saving a rule that contains it is refused (`step_type_managed_only`). An action that uses it needs at least one test case that lists the events it expects; see [Tests](/docs/en/extensions/reference/tests#events).

## Limits and failures

| What | Limit |
| --- | --- |
| Items in one step | 500 |
| Events in one run | 2,000 |
| One item | 32 KB of JSON |

Every item is checked before any is raised. When a check fails, the step fails and raises nothing, and the run stops there unless the step's error port is connected. Events raised by earlier steps of the run stay raised. For a schedule, it counts as a failed run.

| Code when it runs | Cause |
| --- | --- |
| `EXTENSION_EVENT_INVALID` | `items` is not a list, or an item is not an object, does not match the trigger's data, is over 32 KB, or has no usable key. |
| `EXTENSION_EVENT_LIMIT` | More than 500 items in the step, or more than 2,000 events in the run. |
| `EXTENSION_EVENT_NOT_ALLOWED` | The run is not one Opero started for the extension, or the trigger is not one the installed version declares. A package that passed its checks does not meet it. |

## Problems

| Code | Cause | Fix |
| --- | --- | --- |
| `event.unknown` | `event` names no trigger of the package. | Fix the name, or add the trigger. |
| `event.not_literal` | `event` is a template. | Write the trigger's name out. |
| `event.key_required` | `dedupe: true` without `key`. | Add the field that identifies an item. |
| `event.emitted_from_step` | An action that raises events is exposed in any way, or is the connection's verify action. | Run it from a schedule or a member connection hook. |
| `step.config_not_allowed` | A setting other than the four above, `items` that is not one expression, `dedupe` that is not true or false, or a `key` that is not a data field of the trigger. | Keep to the four settings. |
| `test.event_untested` | No test case of the action lists the events it expects. | Add a case with `events`. |

An extension is a package that adds ready-made configuration to an Opero organization: rule steps that call an outside service, triggers, its own data, and screens and buttons for members. Administrators install and run extensions; authors build them as a folder of YAML files and scripts.

## What a package can bring

Each part is optional. A package brings only what its `extension.yaml` lists.

| Part | File | What the organization gets |
| --- | --- | --- |
| [Connection](/docs/en/extensions/reference/connection-and-secrets) | `connection/connection.yaml` | A form for the service's credentials, such as an API token. The secret is stored encrypted and never shown again. |
| [Settings](/docs/en/extensions/reference/settings) | `settings.yaml` | Values that are not secret, such as a language or a region, chosen by the administrator. |
| [Actions and rule steps](/docs/en/extensions/reference/actions) | `actions/<name>/action.yaml` | A step `x-<key>.<name>` in the rule builder, with a form generated from the action's input. |
| [Template filters](/docs/en/extensions/reference/filters) | `filters/<name>/filter.yaml` | A filter `x_<key>_<name>` usable in any template. |
| [Objects, dictionaries and queries](/docs/en/extensions/reference/objects) | `objects/`, `dictionaries/`, `queries/` | The package's own tables of records, lists of values and saved SQL queries, in the module `x-<key>`. |
| [Data permissions](/docs/en/extensions/reference/data-permissions) | `permissions.data` in `extension.yaml` | Steps that read and write the package's records, update contractors, send email and notifications, or generate documents. |
| [Triggers](/docs/en/extensions/reference/triggers) | `triggers/<name>/trigger.yaml` | Rule triggers `x-<key>.<name>` that start the organization's own rules. |
| [Schedules](/docs/en/extensions/reference/schedules) | `schedules/<name>/schedule.yaml` | An action that runs on its own, from every 15 minutes to once a day. |
| [Member connection](/docs/en/extensions/reference/member-connections) | `connection/member.yaml` | Each member connects their own account at the service. |
| [Blocks](/docs/en/extensions/reference/blocks) | `blocks/<name>/block.yaml` | Page blocks that show the package's data, with buttons that run its actions. |
| [Forms, lists and pages](/docs/en/extensions/reference/screens) | `forms/`, `lists/`, `pages/` | Screens to work with the package's objects. |
| [Block actions and record commands](/docs/en/extensions/reference/member-actions) | `expose` in `action.yaml` | Actions members run themselves, from a block's button or a record's actions. |
| [Record links](/docs/en/extensions/reference/record-links) | `links/<name>/link.yaml` | A record action that opens the service's page for the record. |
| [Package permissions](/docs/en/extensions/reference/package-permissions) | `permissions.company` in `extension.yaml` | Company permissions, granted in roles, that decide who may use the block actions, commands and links. |

Every file has a fixed set of keys, and a key the format does not know is refused. A package that validates today does not silently lose a part later.

## How it works

<Steps>
<Step>
### Write

The author writes a folder with `extension.yaml`, one folder per part, tests, translations and, optionally, a [listing](/docs/en/extensions/reference/listing) for the catalog.
</Step>
<Step>
### Validate and pack

The [command-line tool](/docs/en/extensions/reference/cli) checks the folder and zips what `extension.yaml` lists.
</Step>
<Step>
### Upload

Opero checks the package again and runs its tests. See [Install an extension](/docs/en/extensions/install).
</Step>
<Step>
### Install

An administrator reviews what the package adds and what it can reach, then installs it. A package that asks for data scopes is installed only by an organization owner.
</Step>
<Step>
### Set up

The administrator completes the settings and connects the service. See [Run an installed extension](/docs/en/extensions/after-install).
</Step>
<Step>
### Use

Rule authors use the steps, filters and triggers. Schedules start, members connect their accounts and use the blocks, commands and links the organization offers them.
</Step>
</Steps>

What happens each time a rule runs a step of an extension:

| # | Stage | What happens |
| --- | --- | --- |
| 1 | A rule reaches the step | For example `x-hello-ext.greet`. |
| 2 | Input check | The values the rule gives the step are checked against the action's input fields. |
| 3 | The action runs | Its rule file or script runs with the input and the extension's settings. |
| 4 | Secret added | The credential is inserted at the moment of sending, and only for declared hosts. |
| 5 | The service answers | The response goes back to the action. |
| 6 | Output check | The result is checked against the output fields, then handed back to the rule. |

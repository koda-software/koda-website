---
title: A package with its own data
description: "Build an Opero extension that brings its own object, dictionary and saved query, and a step that reads and updates those records."
---

This guide builds **Orders**, a package that keeps orders in its own object. It brings a dictionary **Priority**, an object **Order** whose priority field uses it, and a saved query **Orders by day** for the organization's lists and reports. Its step **Sync order** (`x-orders-ext.sync_order`) fetches the first open order, sends it to a carrier's API and stores the status the carrier answers.

<Steps>
<Step>
### Write the manifest

Start from `opero-ext init orders-ext`, or from an empty folder. There is no `add` command for objects, dictionaries and queries, so you create their folders by hand.

```yaml title="extension.yaml"
manifestVersion: 2
extension: orders-ext
version: 0.1.0
name: Orders
description: Keeps orders and sends the open ones to the carrier.
publisher: Your company
requires:
  modules: [rules, objects, queries]
permissions:
  network:
    - host: api.example.com
      reason: Sends each order to the carrier.
  data:
    - scope: records:read
      reason: Reads the open orders.
    - scope: records:write
      reason: Stores the status the carrier answers.

dictionaries:
  - dictionaries/priority
objects:
  - objects/orders
queries:
  - queries/orders-by-day
actions:
  - actions/sync-order

locales: [pl]
```

The step reads orders and changes one, so the package asks for exactly those two [data scopes](/docs/en/extensions/reference/data-permissions); a scope nothing uses is refused. Because it asks for data, only an organization owner can install it.
</Step>

<Step>
### Add the dictionary

```yaml title="dictionaries/priority/dictionary.yaml"
dictionary: priority
name: Priority
entries:
  - { key: low, label: Low }
  - { key: high, label: High, color: "#DC2626" }
```

It is installed as `x-orders-ext-priority`. See [Dictionaries](/docs/en/extensions/reference/dictionaries).
</Step>

<Step>
### Add the object

```yaml title="objects/orders/object.yaml"
object: orders
name: Order
namePlural: Orders
icon: package
fields:
  - { key: number, name: Number, type: TEXT }
  - { key: status, name: Status, type: TEXT }
  - { key: ordered_on, name: Ordered on, type: DATE }
  - key: priority
    name: Priority
    type: SELECT
    options: { dictionary: priority }
```

`options: { dictionary: priority }` names the package's own dictionary. The object is installed in the module `x-orders-ext`, with no form. See [Objects](/docs/en/extensions/reference/objects).
</Step>

<Step>
### Add the query

```yaml title="queries/orders-by-day/query.yaml"
query: orders_by_day
name: Orders by day
kind: FETCH
sql: query.sql
```

```sql title="queries/orders-by-day/query.sql"
SELECT f_ordered_on AS day, count(*) AS orders
FROM {{object.orders}}
GROUP BY f_ordered_on
```

`{{object.orders}}` stands for the table of the `orders` object, and `f_ordered_on` is its field `ordered_on`. The query is installed as `x_orders_ext_orders_by_day`. See [Queries](/docs/en/extensions/reference/queries).
</Step>

<Step>
### Describe the action

```yaml title="actions/sync-order/action.yaml"
action: sync_order
label: Sync order
description: Sends the first open order to the carrier and stores the status it answers.

input:
  status: { type: text, label: Status, required: true }

run: rule.yaml
tests: tests.yaml

expose:
  ruleStep: { category: data }
```
</Step>

<Step>
### Write the rule

The rule fetches, calls and updates:

```yaml title="actions/sync-order/rule.yaml"
entryStepId: fetch
steps:
  - id: fetch
    type: FETCH_RECORDS
    name: Open orders
    contextKey: orders
    config:
      moduleKey: x-orders-ext
      objectKey: orders
      filters:
        - { field: status, operator: eq, value: open }
      limit: 1
  - id: send
    type: CALL_WEBHOOK
    name: Send to the carrier
    contextKey: sent
    config:
      url: https://api.example.com/v1/orders
      method: POST
      body:
        number: "{{ orders.rows[0].number }}"
        status: "{{ trigger.data.status }}"
  - id: mark
    type: UPDATE_RECORD
    name: Mark the order
    contextKey: output
    config:
      target: "{{ orders.rows[0].id }}"
      targetModuleKey: x-orders-ext
      targetObjectKey: orders
      fieldUpdates: { status: "{{ sent.body.status }}" }
edges:
  - { fromStepId: fetch, toStepId: send }
  - { fromStepId: send, toStepId: mark }
```

The module and object are written out as `x-orders-ext` and `orders`, because a template there is refused. `UPDATE_RECORD` names the record by the id of the fetched row. See [Data steps](/docs/en/extensions/reference/data-steps).
</Step>

<Step>
### Test it

The case scripts the HTTP exchange in `http` and the two data steps in `effects`. Each list is matched in its own order.

```yaml title="actions/sync-order/tests.yaml"
- name: the open order gets the status the carrier answers
  input: { status: synced }
  http:
    - request:
        method: POST
        url: https://api.example.com/v1/orders
        body: { number: A-1, status: synced }
      response: { status: 200, body: { status: synced } }
  effects:
    - request: { step: FETCH_RECORDS, objectKey: orders }
      response:
        rows: [{ id: 7d1c2a34-0000-4000-8000-000000000001, number: A-1, status: open }]
        rowCount: 1
        truncated: false
    - request:
        step: UPDATE_RECORD
        targetObjectKey: orders
        fieldUpdates: { status: synced }
  succeeds: true
```

The fetch effect gives the step the row it would have read. The update effect checks the object and the new status; it has no `response`, because `UPDATE_RECORD` returns nothing. No record is read or written while the test runs. See [Tests](/docs/en/extensions/reference/tests#data-and-messaging-steps).
</Step>

<Step>
### Translate it

```yaml title="locales/pl.yaml"
extension:
  name: Zamówienia
  description: Przechowuje zamówienia i wysyła otwarte do przewoźnika.
permissions:
  network:
    api.example.com: { reason: Wysyła każde zamówienie do przewoźnika. }
  data:
    records:read: { reason: Odczytuje otwarte zamówienia. }
    records:write: { reason: Zapisuje status zwrócony przez przewoźnika. }
actions:
  sync_order:
    label: Synchronizuj zamówienie
    description: Wysyła pierwsze otwarte zamówienie do przewoźnika i zapisuje zwrócony status.
    input: { status: { label: Status } }
dictionaries:
  priority:
    entries:
      low: { label: Niski }
      high: { label: Wysoki }
```

Dictionary entry labels are translatable. The names of the object, its fields, the dictionary and the query are English only.
</Step>

<Step>
### Validate, test and pack

```bash title="Terminal"
opero-ext validate .
opero-ext test . --server https://opero.example.com/mcp
opero-ext pack .
```

</Step>

## After install

An organization owner [installs](/docs/en/extensions/install) the zip; for anyone else the review says that only an owner can install it, because of the [data scopes](/docs/en/extensions/install#access-to-data). There is no connection to set up. Under **What it adds**, the extension's page lists the object, the dictionary and the query. Opening one shows it read-only, and the query shows its SQL with the placeholder replaced by the installed table:

![The installed Orders by day query with its SQL, read-only and managed by the extension](/docs/_assets/extensions/own-data/query-overlay.webp)

The organization builds its own forms and lists on the object and uses the query in its SQL lists and reports. Its rules get the step **Sync order**, saved like this:

```json title="A step in one of the organization's rules"
{
  "type": "x-orders-ext.sync_order",
  "contextKey": "synced",
  "config": { "status": "sent" }
}
```

Whoever writes that rule, the step reads and writes only the `orders` records, in the company the rule runs for.

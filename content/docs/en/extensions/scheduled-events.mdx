---
title: Events from a service
description: "Build an Opero extension that reads a service every hour for each company and raises a trigger event that the organization's rules start on."
---

This guide builds **Order events**, a package that watches open orders at an outside service. Every hour, a schedule runs one action for each company. The action reads the company's open orders and raises the trigger **Order changed** (`x-order-events.order_changed`) once for each order that is new or changed since the last run. The organization then builds its own rules on that trigger.

The service in this guide, `api.example.com`, needs no key, so the package has no connection. With a real service, add one as in the [tutorial](/docs/en/extensions/tutorial/call-a-service).

<Steps>
<Step>
### Write the manifest

```yaml title="extension.yaml"
manifestVersion: 2
extension: order-events
version: 1.0.0
name: Order events
description: Raises an event for every new or changed open order, checked every hour for each company.
publisher: Your company
requires:
  opero: ">=2026.1.0"
  modules: [rules]
permissions:
  network:
    - host: api.example.com
      reason: Reads each company's open orders.

actions:
  - actions/sync-orders
triggers:
  - triggers/order-changed
schedules:
  - schedules/sync-orders

locales: [pl]
```

Starting from `opero-ext init order-events`, `opero-ext add trigger order_changed` writes the trigger's folder and its entry here. Add the schedule once the action exists.
</Step>

<Step>
### Declare the trigger

```yaml title="triggers/order-changed/trigger.yaml"
trigger: order_changed
label: Order changed
description: An open order is new, or one of its values changed.
data:
  number: { type: text, label: Order number, required: true }
  status: { type: select, label: Status, options: [open, packed, shipped], required: true }
  total: { type: number, label: Total, nullable: true }
  updatedAt: { type: datetime, label: Updated at }
config:
  status: { type: select, label: Only this status, options: [open, packed, shipped], match: status }
dedupe: { retentionDays: 30 }
example: { number: A-1, status: open, total: 120.5, updatedAt: "2026-11-01T10:00:00Z" }
```

| Key | What it does here |
| --- | --- |
| `data` | What each event carries. Rules read it as `{{ trigger.data.<field> }}`, and every event is checked against it. |
| `config` | One filter for rule authors: with **Only this status** set, a rule starts only for orders in that status. |
| `dedupe.retentionDays` | An order not raised for 30 days is forgotten. |
| `example` | The sample data offered when a rule on the trigger is tested. |

See [Triggers](/docs/en/extensions/reference/triggers).
</Step>

<Step>
### Describe the action

```yaml title="actions/sync-orders/action.yaml"
action: sync_orders
label: Sync orders
description: Reads the company's open orders and raises an event for each new or changed one.

input:
  subject:
    type: object
    label: Subject
    required: true
    fields:
      kind: { type: text, required: true }
      companyId: { type: text, nullable: true }
  lastSucceededAt: { type: datetime, nullable: true }
  firstRun: { type: boolean, required: true }
output:
  emitted: { type: integer, label: Raised }
  unchanged: { type: integer, label: Unchanged }

run: rule.yaml
tests: tests.yaml
```

The input is what a schedule passes each run: the subject (here, the company), when the last run succeeded, and whether this is the first. There is no `expose`: an action that raises events is never a rule step. See [The input each run receives](/docs/en/extensions/reference/schedules#the-input-each-run-receives).
</Step>

<Step>
### Write the rule

The rule reads, then raises:

```yaml title="actions/sync-orders/rule.yaml"
entryStepId: fetch
steps:
  - id: fetch
    type: CALL_WEBHOOK
    name: Open orders
    contextKey: orders
    config:
      method: GET
      url: "https://api.example.com/v1/orders?company={{ trigger.data.subject.companyId }}&status=open"
  - id: emit
    type: EMIT_EVENT
    name: Raise order events
    contextKey: output
    config:
      event: order_changed
      items: "{{ orders.body.items }}"
      key: number
      dedupe: true
edges:
  - { fromStepId: fetch, toStepId: emit }
```

Each item of `items` becomes one event and must match the trigger's `data`. With `key: number` and `dedupe: true`, an order is raised only when it is new, or when anything in it changed since it was last raised for this company. The step's result, `{ emitted, unchanged }`, is the action's result. See [Raising events](/docs/en/extensions/reference/raising-events).
</Step>

<Step>
### Add the schedule

```bash title="Terminal"
opero-ext add schedule sync_orders --action sync_orders --every 1h --for-each company
```

```yaml title="schedules/sync-orders/schedule.yaml"
schedule: sync_orders
label: Sync open orders
description: Reads each company's open orders every hour.
every: 1h
forEach: company
action: sync_orders
```

Every hour, each active company of the organization gets one run of `sync_orders`, and its events belong to that company. See [Schedules](/docs/en/extensions/reference/schedules).
</Step>

<Step>
### Test it

Three cases: a new order raises an event, the same order unchanged raises nothing, and the order with a new status raises it again.

```yaml title="actions/sync-orders/tests.yaml"
- name: a new order raises an event
  input: { subject: { kind: company, companyId: co_1 }, lastSucceededAt: null, firstRun: true }
  http:
    - request:
        method: GET
        url: https://api.example.com/v1/orders?company=co_1&status=open
      response:
        status: 200
        body: { items: [{ number: A-1, status: open, total: 120.5 }] }
  events:
    - event: order_changed
      key: A-1
      data: { number: A-1, status: open, total: 120.5 }
  returns: { emitted: 1, unchanged: 0 }

- name: an order seen before, unchanged, raises nothing
  input: { subject: { kind: company, companyId: co_1 }, lastSucceededAt: "2026-11-02T10:00:00Z", firstRun: false }
  seen:
    - { event: order_changed, key: A-1, data: { number: A-1, status: open, total: 120.5 } }
  http:
    - request:
        method: GET
        url: https://api.example.com/v1/orders?company=co_1&status=open
      response:
        status: 200
        body: { items: [{ number: A-1, status: open, total: 120.5 }] }
  events: []
  returns: { emitted: 0, unchanged: 1 }

- name: an order whose status changed raises it again
  input: { subject: { kind: company, companyId: co_1 }, lastSucceededAt: "2026-11-02T10:00:00Z", firstRun: false }
  seen:
    - { event: order_changed, key: A-1, data: { number: A-1, status: open, total: 120.5 } }
  http:
    - request:
        method: GET
        url: https://api.example.com/v1/orders?company=co_1&status=open
      response:
        status: 200
        body: { items: [{ number: A-1, status: packed, total: 120.5 }] }
  events:
    - { event: order_changed, key: A-1, data: { number: A-1, status: packed, total: 120.5 } }
  returns: { emitted: 1, unchanged: 0 }
```

`events` lists the events the run must raise, in order, and `events: []` says it raises none. `seen` is what Opero already remembers when the case starts: here, order `A-1` as it was last raised. No event is queued and no rule runs while the tests run. See [Tests](/docs/en/extensions/reference/tests#events).
</Step>

</Step>

## After install

[Install the zip](/docs/en/extensions/install) as usual. The review shows the trigger with its data fields under **What it adds**, and the schedule under **Runs on its own**. The package has no data scopes, so any administrator who may install extensions can install it. Within the first hour each company gets its first run, then one an hour. The extension's **Activity** tab shows how the schedule is doing; see [Schedules](/docs/en/extensions/after-install#schedules).

![A schedule on the Activity tab: its companies, runs due, failures and last success](/docs/_assets/extensions/after-install/activity-schedules.webp)

## A rule that listens

In the rule builder, open the trigger, press **Change trigger** and pick **Order changed** in the extension's group under **Integrations**. Optionally set **Only this status**, then add the rule's steps. Saved, the rule's trigger is:

```json title="The trigger of one of the organization's rules"
{
  "trigger": {
    "type": "x-order-events.order_changed",
    "config": { "status": "packed" }
  }
}
```

The rule then starts for each packed order the hourly run finds new or changed, in that order's company, and reads it as `{{ trigger.data.number }}`, `{{ trigger.data.total }}` and so on. With no past run, testing the rule offers the trigger's `example` as sample data.

<Callout type="idea" title="Make the rule safe to run twice">
The same order may occasionally arrive twice. Build the rule so that a second run changes nothing: look the record up by `{{ trigger.data.number }}` and update it, or create it when it is missing.
</Callout>
